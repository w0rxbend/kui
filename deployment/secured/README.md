# KUI against a secured broker

One command brings up a Kafka broker that speaks **SASL_SSL with SCRAM-SHA-512** behind a private
certificate authority, seeds it with the quickstart's own data, and starts KUI pointed at it using
the shipped `deployment/examples/production.yaml`.

```
./generate-certs.sh
docker compose -f docker-compose.secured.yml up -d
open http://localhost:18081
```

Tear it down with `docker compose -f docker-compose.secured.yml down -v`. Nothing is left behind;
`./certs` is regenerated by re-running the script and is git-ignored.

## Why it exists

Point 5 of `docs/DELIVERY.md` — "point it at your own cluster with a documented example
configuration, including a secured one" — was met on paper. There was a production example, and the
adapter suites in `libs/testkit` covered plaintext, SCRAM over plain text, and mutual TLS at the
port level. What nobody had ever run was **SASL and TLS together**, through the whole product, from
that example file to a rendered screen. `KafkaTopology` says so in as many words: "There is
deliberately no `SaslSsl`."

The first run of this stack found the defect that gap was hiding.

## The defect it found

`deployment/examples/production.yaml` writes the truststore password the way it writes every other
secret:

```yaml
ssl:
  truststore:
    location: "/etc/kui/certs/kafka-ca.p12"
    password: "env:KUI_ANALYTICS_TRUSTSTORE_PASSWORD"
```

The configuration loader read the SASL password through `SecretRef`, which understands `env:` and
`file:`, and read the three TLS passwords **verbatim**. So the password Kafka was handed was the
literal 33-character string `env:KUI_ANALYTICS_TRUSTSTORE_PASSWORD`, `Admin.create` threw while
opening the PKCS12 store, and the cluster sat on the dashboard reading `Unavailable` with the code
`KUI-UPSTREAM-UNAVAILABLE` — the same code a broker that is simply switched off produces.

Nothing anywhere named the store, the password or the exception. `ShippedConfigurationSuite` was
green, because it asserted that the example *loads*, and it did.

Two things changed, and both have tests:

- the TLS passwords are resolved like every other secret, so `env:` and `file:` work under
  `ssl.truststore.password`, `ssl.keystore.password` and `ssl.keyPassword`
  (`ClusterSecuritySuite`, and a new case in `ShippedConfigurationSuite` that asserts over the
  *resolved* values rather than over "it loaded");
- a cluster failure now logs the exception's class name beside the error code, so "the broker is
  off" and "the client could not be built" stop looking identical in a log.

## What is in here

| File | What it is |
| --- | --- |
| `generate-certs.sh` | Writes `./certs`: a throwaway CA, a broker keystore whose SAN names the broker, and the CA-only truststore KUI is given. Uses Docker, so no JDK is needed. |
| `docker-compose.secured.yml` | The broker, a one-shot provisioner that creates the SCRAM user and seeds data, the live consumer, and KUI. |
| `kui-secured.yaml` | `deployment/examples/production.yaml` with three lines changed. |

`kui-secured.yaml` is deliberately a near-copy. What is worth testing is the file a newcomer copies,
not one written to pass. The three differences are the two bootstrap addresses and
`server.devInsecureCookies: true`, which plain HTTP on `localhost` needs and which no real
deployment may ever set.

## The broker's shape, and the one compromise in it

Four listeners:

| Listener | Protocol | Who uses it |
| --- | --- | --- |
| `CLIENT` (9093) | `SASL_SSL` / `SCRAM-SHA-512` | **KUI's `analytics` cluster.** The one under test. |
| `ADMIN` (9095) | `PLAINTEXT` | The provisioner, the seed, the live consumer — and KUI's `staging` cluster, so the file also demonstrates a secured and an unsecured cluster side by side. |
| `BROKER` (9092) | `PLAINTEXT` | The broker talking to itself. |
| `CONTROLLER` (9094) | `PLAINTEXT` | KRaft. |

The plaintext `ADMIN` listener is the compromise, and it is there for a real reason rather than
convenience: a SCRAM credential lives in the cluster's own metadata, so creating the first one needs
a way in that does not require it. Production clusters solve the same bootstrap problem with
`kafka-storage.sh format --add-scram`, or with a second mechanism, or out of band. Nothing KUI does
touches this listener except the deliberately-unsecured `staging` entry.

Client certificates are not required (`ssl.client.auth: none`): KUI proves who it is with SCRAM.
Mutual TLS is a different configuration and is covered at the port level by
`KafkaFixture`'s `MutualTls` topology.

## What was verified

Against the running stack, through KUI's own API, on the `analytics` cluster only:

- `GET /api/v1/clusters` — `analytics`, `SASL_SSL`, `SCRAM-SHA-512`, status `ok`, one broker;
- `GET /clusters/analytics/brokers` — broker 1 at `kafka-secured:9093`, the controller;
- `GET /clusters/analytics/topics` — the eight seeded topics with their partition counts;
- `GET /clusters/analytics/topics/orders.v1` and its `/partitions` and `/config`;
- `GET /clusters/analytics/topics/orders.v1/messages/stream` — records with their JSON values
  parsed and rendered as JSON;
- `GET /clusters/analytics/consumer-groups` — `analytics-indexer` `STABLE` with one live member,
  `order-fulfilment` `EMPTY` with a total lag of 9, `payments-ledger-sync` `EMPTY`;
- `GET /clusters/analytics/consumer-groups/lag` — the same three groups and a resync token.

The startup log confirms the signing key came from configuration rather than from a per-process
random: *"plan tokens are signed with the configured kui.streaming.cursorKey"*, and the same for
browse cursors.
