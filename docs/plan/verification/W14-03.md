## 3. THE FINDING THAT MATTERS — the storybook repair's stated reason is false, and it is shipped

The packet's loudest claim, in its report (*"THE STORYBOOK IMAGE WAS PROBABLY UNBUILDABLE AND NOTHING
SAID SO"*), is written into the repository twice without the hedge:

* `deployment/storybook/Dockerfile:43-49` — *"`pnpm-lock.yaml` declares eleven importers and this
  file copied eight, so `--frozen-lockfile` below had nothing to be frozen against for
  `feature-alerts`, `feature-connect` and `feature-ksql`, and each of those three ships a
  `.stories.` file that is the entire reason this image exists. Nothing built the image, so nothing
  said so."*
* `ShippedImageManifestSuite.scala:162-164`, inside the suite's own failure clue — *"An image whose
  manifest list is short runs `pnpm install --frozen-lockfile` over a workspace the lockfile does
  not describe, so the install fails"*.

**Measured. I built both.**

```
$ sed -i '59,61d' deployment/storybook/Dockerfile     # back to the shipped 8-manifest roster
$ docker build -f deployment/storybook/Dockerfile --target build .
#16 [build 13/15] RUN … pnpm install --frozen-lockfile
#16 0.945 Lockfile is up to date, resolution step is skipped
#16 3.169 ✓ Lockfile passes supply-chain policies (382 entries in 2.2s)
…
#18 16.58 └  Storybook build completed successfully
BROKEN_BUILD_EXIT=0
```

`--frozen-lockfile` does not fail. The install succeeds. And the three packages the comment says the
image could not serve **are in the output**: `alerts.stories-CVv0lLAx.js`,
`connect.stories-Ce_10B8u.js`, `ksql.stories-Byp7uEvE.js`. Counted across both trees:

| Tree | `docker build --target build` | distinct `*.stories-*.js` bundles emitted |
| --- | --- | --- |
| shipped, 8 manifests (pre-repair) | **exit 0** | **77** |
| repaired, 11 manifests (post-repair) | **exit 0** | **77** |

`diff` of the two bundle name sets is empty. The repair changes nothing the image serves, and the
image was never unbuildable. The reason it still built is one line further down: `COPY frontend/ ./`
brings every manifest in before `storybook build` runs, and pnpm's frozen check passed on the
smaller importer set rather than refusing it.

**Why this is the finding and not a quibble.** Wave 14's entire subject is *a documented statement
that a command in this repository contradicts*. This packet found a real listing drift, derived a
real gate for it — and then wrote, into the repository, a measured-sounding consequence that a
two-command measurement disproves. It is the wave's own class, committed by the packet closing the
wave's own class.

**The row that would close it:** rewrite the comment at `deployment/storybook/Dockerfile:43-49` and
the clue at `ShippedImageManifestSuite.scala:162-164` to state what is true — the roster had drifted
by three, the drift is invisible to every gate, and the image builds anyway because `COPY frontend/
./` repairs the workspace after the install layer, which is precisely why `--frozen-lockfile`'s
guarantee was not being obtained. The honest justification for the repair is *the cache layer above
the install must be a complete workspace or `--frozen-lockfile` asserts nothing*, not *the image
fails to build*.
