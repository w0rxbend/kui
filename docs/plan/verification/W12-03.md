## 3. The two rules that were ungated, on the line a CSRF rejection writes

Neither is on W11-A1's list. Both live in `SessionMiddleware.CsrfInterceptor.forbidden`, which is the **only
place in this gateway that logs anything about a session at all**, and both were measured against the *whole*
module rather than the auth filter.

| id | The mutation | `./mill --no-daemon services.gateway.api.test` |
| --- | --- | --- |
| `G16` | `"session.ref" -> session.fold("-")(active => SessionRef.of(active.id).value)` → `… => active.id.value)` | **1270/1270, SUCCESS** — 303 cases over 31 suites, all green |
| `G17` | `logger.warn(…)` → `logger.debug(…)` | **1270/1270, SUCCESS** |

**`G16` is the serious one.** `Session.scala` states the rule the `SessionRef` type exists for — a rejected
request is logged with `session.ref`, never the id, *"so that a log file is not itself a way to hijack the
session it describes"* — and `ARCHITECTURE.md` §14 is cited beside it. Under the mutation the gateway writes
the **live cookie value** of every CSRF-rejected request into the log, and a CSRF rejection is exactly what an
attack produces: the attacker's own noise is what fills the file with replayable credentials. The CSRF secret
is a `Secret` and cannot be logged by accident; the session id is a plain `String` and can.

`G17` is smaller and is the file's own argument turned off: the scaladoc says a CSRF rejection is logged at
`WARN` because it is *"a signal worth alerting on, not a client error to note and move past"*. At `debug` it
sits under every deployment's default level.

**`G16` was also refused by the compiler first** — deleting the last use of `SessionRef` stranded its import
— and defeated by editing one import line. Two of eleven mutations refused, both defeated in one edit: 18%,
against W11-A1's 19% over 73. The rule generalises.

**Closed by one case**, `SessionMiddlewareSuite.aCsrfRejectionIsLoggedAtWarnAndNamesTheSessionByItsRefRatherThanItsId`,
which drives a real server, takes a real cookie, is refused for want of a CSRF header, and then reads what
was logged. Confirmed red under each mutation, against the filtered run:

```
G16 → kui.gateway.api.auth.SessionMiddlewareSuite 1 failed
G17 → kui.gateway.api.auth.SessionMiddlewareSuite 1 failed
      a CSRF rejection was logged at debug: LogEntry(debug,CSRF rejected: X-Csrf-Token is missing,
      Map(path -> /api/v1/auth/logout, secFetchSite -> absent, session.ref -> f9819c90b5…),None)
```

Three things the case does deliberately:

* **it asserts the absence over the whole line, not over the one field** — the id must appear in no context
  value and not in the message, so a key somebody adds later cannot reintroduce the leak past this case;
* **it recomputes the expected ref** (`SessionRef.of(SessionId.unsafe(id)).value`) rather than asserting
  "not the id", so replacing the hash with any other one-way-looking string is also red;
* **it has a vacuity guard.** With nothing logged at all — which is what deleting the log call does — every
  assertion below would hold over an empty list, so the case fails first with *"the CSRF rejection logged no
  session at all"*. W11-A2's lesson about the ledger half being green under the mutation is the same lesson.

## 5. The equivalent mutant, argued down and then measured

Because none of the eight is equivalent, the packet's "green one" is a mutant found beside them.

**`E1` — `CsrfCheck.verdict`'s `val upperMethod = method.toUpperCase` → `val upperMethod = method`.**
`./mill --no-daemon services.gateway.api.test` → **1270/1270, SUCCESS**, predicted before the run.

The algebra. `verdict` is reached from exactly one call site, `CsrfInterceptor.onDecodeSuccess`, which runs
**only after Tapir has matched an endpoint** — `onDecodeSuccess` is the name of the extension point. Matching
compares the request's method against `sttp.model.Method`'s canonical constants, which are upper-case, so
every method string that reaches `verdict` through the product is already upper-case and `toUpperCase` is the
identity on it. The only inputs it is not the identity on are ones the router has already refused with a
`404`, and on those the mutation can only turn `Allowed` into `Denied` — the fail-**closed** direction.

**Where the argument stops.** It is equivalence *by accident of the router*, exactly like W10-A1's `G10`, and
W11-A1's answer to that accident was to make the accident a case rather than to trust it. The difference is
that `G10`'s accident was a property of *KUI's own route table* — one `POST` added under `/ui/` flips it —
while this one is a property of `sttp.model.Method`'s constants, which this repository does not write and
cannot change by adding a route. It is therefore left argued rather than cased, and the line is written down
here so the next reader can disagree with a named reason rather than re-derive it. `verdict`'s own signature
already documents `method` as *"the HTTP method, upper-cased"*, so the call site's contract is stated.

| # | File and line | Exact mutation | Command | Result | The case that would close it |
| --- | --- | --- | --- | --- | --- |
| **V1** | `services/gateway/api/src/kui/gateway/api/auth/SessionMiddleware.scala:348`, `alreadyCarriesSessionCookie` | `header.value.startsWith(s"$CookieName=")` → `header.value.startsWith(s"$CookieName")` | `./mill --no-daemon services.gateway.api.test` | **GREEN**, `1270/1270, SUCCESS … 110s` | Extend `AuthRoutesSuite`'s *"a response that already carries a session cookie is recognised"* with a third negative: `assert(!SessionMiddleware.alreadyCarriesSessionCookie(responseWith(List(Header("Set-Cookie", s"${SessionMiddleware.CookieName}_backup=abc")))))`. | **V2** | `services/gateway/api/src/kui/gateway/api/auth/SessionMiddleware.scala:201`, `attachInterceptor` | `now <- Clock[F].realTimeInstant` → `now <- Sync[F].pure(Instant.EPOCH)` | `./mill --no-daemon services.gateway.api.test` | **GREEN**, `1270/1270, SUCCESS … 108s` | A case that builds a server on a `SessionConfig` with a sub-second `idleTimeout`, GETs `/auth/me`, waits past it, GETs again presenting the same cookie, and asserts the second response's `Set-Cookie` carries a **different** id. **Why V1 matters.** It is G15's rule on the other side of the same hop. G15 — closed, and re-measured by
this packet's §2 — says the *request* cookie is found by its exact name and not by substring, because
another application on the same domain can set a cookie whose name contains `kui_session`. V1 is the same
rule on the *response*: with the `=` gone, any route that sets a cookie named `kui_session`-anything makes
`SessionMiddleware` stand aside, the real session cookie is never stamped, and the browser silently keeps
whatever session it arrived with. The repository takes the exact-name rule seriously enough to have written
a case for one direction of it; the other direction has none.

**Why V2 matters, and it is the more serious of the two.** `store.get(id, now)` is the *only* expiry check
on the request path, and it does two things: it refuses a session that has passed `SessionConfig`'s
`idleTimeout` (30 minutes) or `absoluteTimeout` (12 hours), and it slides `lastSeenAt` to `now`.
`attachInterceptor` is the only caller that supplies `now` for a browser request. Freeze that clock and
`Session.isExpired(now, idleTimeout)` — `now.isAfter(absoluteExpiry) || now.isAfter(lastSeenAt.plus(idleTimeout))`
— is false forever: **no session in the deployment ever expires**, and a cookie captured once stays valid
for the life of the process. 303 cases over 31 suites do not notice, because every one of them runs inside
a few seconds of minting its own session. ADR-019's session lifetime is configuration that nothing measures.
