### 2.1 `libs/filter` — `Sync[F].interruptible` → `Sync[F].blocking` · **CLOSED**

W11-A1 filed it with the mutation written out and `./mill --no-daemon libs.filter.test` → 548/548
SUCCESS. Reproduced here: the same edit, the same green.

The rule is one word in `CelFilterEngine`'s `program`, and the comment beside it argues it — *"with
twenty thousand records queued behind it, ten milliseconds each is more than three minutes of work
nobody is waiting for any more"*. The difference between `interruptible` and `blocking` is observable
**only** when the work inside the region answers `Thread.interrupt`, and a CEL evaluation over a plain
record does not: it finishes in microseconds. That is why the row survived a wave.

**What closes it** is putting the stall *inside the region the rule is about* rather than beside it.
`FilterableRecord.headers` is a `Map[String, String]` — a trait — and `CelEnvironment.activation` is
built **inside** the interruptible block, so a header map whose iteration parks stalls the CEL
evaluation itself. `CelFilterEngineSuite`'s new
*cancelling a browse cancels the evaluation in flight rather than waiting it out* starts
`predicate.test`, waits on a latch the stalling map counts down (not a sleep — the cancel is
guaranteed to arrive mid-evaluation), cancels the fibre and asserts two things: the cancel returned
inside 5 s while the evaluation had 20 s left, and the interrupt actually reached the program.

### 2.2 `libs/kafka-auth` — the second `setPosixPermissions` · **CLOSED, and W11-A1's judgement overturned**

W11-A1 filed this as *"not portably closable"*. The brief said to decide that rather than inherit it.
**It is wrong, and the reason it looked right is arithmetic rather than coverage.**

`createDirectories(directory, Some(DirectoryPermissions))` reaches `mkdir(2)` with mode `0700`, and a
umask can only **clear** bits — so on any ordinary umask the leaf is already `0700` before the second
call runs, and the existing `filesAreOwnerOnly` case cannot tell the two versions apart. Deleting the
line left all **395** cases green, `filesAreOwnerOnly` included. That is what W11-A1 measured.

What it missed is the case where the second call is **the only thing that acts**: a directory that
already exists. `createDirectories` is then a no-op that applies no permissions at all, and whatever
the directory was found at is what a private key gets written into. That is portable, deterministic
and needs no umask control.

It needs a seam, because `createDirectory` mints a random directory name internally and no test can
pre-create the path it will choose. **The declared production edit** — the only one in this packet —
extracts the two calls, unchanged and in the same order, into

```scala
private[auth] def secureDirectory[F[_]: {Async, Files}](directory: Path): F[Unit] =
  Files[F].createDirectories(directory, Some(DirectoryPermissions)) >>
    Files[F].setPosixPermissions(directory, DirectoryPermissions)
```

and `createDirectory` calls it. Behaviour-preserving: same two effects, same order, same arguments.

`KeyStoreMaterializerSuite`'s new *a directory that already exists is narrowed to the owner rather
than left as it was found* pre-creates the directory at `rwxrwxrwx`, asserts it started at nine
permission bits (so a fixture that silently stopped being wide open fails rather than passes), calls
the production helper, and requires `rwx------`.


## 3. The three new ungated rules, all in `services/consumer`

### 3.1 `PlanToken.boundTo` — the cluster binding is a substring search, not an identity · **CLOSED**

**The most serious finding in this report.** ADR-045's token binds a reset plan to the cluster it was
computed against, so that *"a plan for `orders` on staging cannot be applied to `orders` on
production"*. The binding is one line:

```scala
.exists(_.startsWith(s"${cluster.value}/"))
```

Rewritten to `_.contains(cluster.value)` — one method name — **all 1,390 tasks of
`./mill --no-daemon services.consumer.__.test` stay SUCCESS.** The existing case
*a token minted for another cluster does not apply to this one* mints on `staging` and verifies on
`prod`, and `"staging/orders-consumer"` does not contain `"prod"`, so it passes either way.

Under the mutation the binding stops being a cluster identity: the payload field is
`"<cluster>/<group>"`, so **a token minted on `prod` for group `orders-consumer` applies to any
cluster whose id is a substring of that string** — `orders`, `pro`, `d`. The group check does not
save it, because the group parsed out of the payload is still the group being asked for. The offsets
an operator was shown were read from a different cluster's log ends, and they get written.

Closed in `MutationSuite` — *a cluster whose id only appears inside the binding is not the cluster the
token was minted for* — which mints on `prod`/`orders-consumer`, requires `KUI-VALIDATION` when
verified as cluster `orders`, and asserts the other direction (the minting cluster still gets its own
token) so a mutation that refuses everything fails here too.

```
$ # with the new case, unmutated          1390/1390, SUCCESS
$ # .startsWith(s"${cluster.value}/")  →  .contains(cluster.value)
==> X kui.consumer.application.MutationSuite.a cluster whose id only appears inside the binding is
    not the cluster the token was minted for 0.088s MutationSuite.scala:281
1390/1390, 1 FAILED
```

For the record, the *coarse* mutation is gated: replacing the whole predicate with a constant `true`
turns *a token minted for another cluster does not apply to this one* red. What was ungated is the
**strictness** of the binding, which is where this class of defect always lives.

### 3.3 `ResetPlanner.plan` — the canonical partition order · **CLOSED**

`partitions.toList.sorted` with the `.sorted` deleted leaves all **1,390** tasks SUCCESS. Every
existing case reads the plan through the suite's `planned` helper, which folds the list into a
`Map[Int, Long]` and throws the order away; the cases that *do* care about byte-stability read it
through `PlanToken`, which sorts again on its own account. So the planner's own ordering had no reader.

The comment claims the token; the token is safe either way. What is not safe is the other reader:

the same reset.

Closed in `ResetPlannerSuite` — *the planned partitions come out in partition order, whatever order the
scope iterated in* — using an `immutable.ListSet` so the out-of-order input is deterministic rather
than hash-dependent, with a guard assertion that the fixture really does iterate out of order (`List(1,
0)`) so the case cannot silently stop proving anything.

## 5. The two equivalent mutants, with the algebra written out

Both are the **same defect in two files**, and only one of them has a `TECH_DEBT.md` row.

`RegistryCredentials` (schema) and `ConnectCredentials` (connect) both hold, with identical
constants — `RefreshMargin = 30.seconds`, `MinimumLifetime = 1.minute`:

```scala
val lifetime = cursor.get[Long]("expires_in").toOption.map(_.seconds)
  .filter(_ > MinimumLifetime)          // guard A
  .getOrElse(MinimumLifetime)
… now.plusMillis((lifetime - RefreshMargin).max(MinimumLifetime / 2).toMillis)   // guard B
```

**Deleting A alone changes nothing, for every input.** With A, `lifetime ≥ 60 s` always, so
`lifetime − 30 s ≥ 30 s` and B never binds; the answer is `expires_in − 30 s`. Without A,
`lifetime = expires_in`; for `expires_in > 60` the answer is the same, and for `expires_in ≤ 60`
(including `0`, negative, and absent) B clamps to `30 s`, which is exactly what A-then-B produced.
Verified rather than only derived: `./mill --no-daemon services.schema.__.test` → **1186/1186
SUCCESS** and `./mill --no-daemon services.connect.__.test` → **1186/1186 SUCCESS** with A deleted.

**Deleting B alone also changes nothing**, by the same identity read the other way. **Deleting both
does** — `expires_in: 0` then yields a `usableUntil` in the past and KUI asks the issuer once per
call — and that *is* gated: `ConnectCredentialsSuite` *an issuer that omits expires_in gets the
minimum lifetime rather than a cache of zero* goes red, and `RegistryCredentialsSuite` holds the same
floor from both sides (*a token an issuer says expires in one second is still cached for thirty* and
*a token cached under the floor is renewed once the floor has passed*).

So: **the floor is a rule and it is gated; the redundancy is not a rule and no case can close it.**
That is TD-033's own conclusion, re-derived independently here and confirmed empirically in both
directions. **No mutation counts against the rate for either file, and no case is written**, because a
case that went red for either single deletion would have to assert something the product does not do.

**What is new and belongs in `TECH_DEBT.md`: TD-033 names only
`services/schema/.../RegistryCredentials.scala:180`, and the identical dead pair is at
`services/connect/.../ConnectCredentials.scala:241`.** The row's exit — delete one guard, say in the
scaladoc that the other is the floor — has to be done to both files or the puzzle survives in the one
nobody looked at. **Not done here**: it is a hygiene edit in two services with no gate behind it, the
register already carries the decision, and this packet's production budget was spent on the one seam
that closed a rule. **For W12-01: amend TD-033 to name both files.**
