## 3. Row 13 argued down: `App.tsx`'s no-cluster guard is equivalent today

The filed mutation is real and it is green:
`if (chosen !== undefined) navigate(paths.topics(chosen), …)` → `navigate(paths.topics(chosen ?? ""), …)`
leaves `pnpm -C frontend test packages/shell` at **557 passed**, measured in this pass.

It is also **unreachable**, and the algebra is short. `CreateTopicAction` marks the button
`aria-disabled` whenever `props.cluster` is `undefined`; `props.cluster` is
`params.clusterId ?? kui.cluster()`; `kui.cluster()` **is** `clusterForFrame()` (`App.tsx:371`) and
`params.clusterId` is `routeCluster()` by another name. So the button is inert on exactly the
addresses the guard refuses, and `Button`'s `inert()` swallows the press with
`preventDefault`/`stopPropagation` *before* the handler runs. There is one caller, and it cannot
reach the branch. Equivalent by accident of there being one caller, not by construction — W10-A1's
`G10` shape.

So the case written is the one that keeps the accident visible, and it is measured three ways:

| tree | `app.render.test.tsx` case |

| guard removed, disablement kept | **GREEN** — the mutant is equivalent, as argued |
| disablement removed, guard kept | **RED** on `aria-disabled`; the address stayed `/ui` |
| both removed | **RED twice**, the second `expected '/ui/clusters//topics' to be '/ui'` |

It is the only case in the repository that presses that button at `/ui` through the composition

## 6. Two findings of this pass's own

**6.1 — Mill caches these text-reading suites, so a local re-run can measure nothing.**
`BuildWiringSuite` reads `build.mill`, `.github/workflows/ci.yml` and `frontend/package.json` at
runtime; none of them is an input Mill tracks for `build-tests.test`. Measured: with the `typecheck`
script mutated, `./mill --no-daemon build-tests.test` returned **137/137 SUCCESS without running the
suite at all**; `./mill --no-daemon clean build-tests.test` then went red on the expected case. In CI
this is harmless — a fresh checkout has no cache — but anybody reproducing one of these gates
locally must `clean` first, or they will measure the previous run. Worth a `TECH_DEBT.md` row and an
`inputs`/`PathRef` on the three files.

**6.2 — the fixture that reads the live roster reads another fixture's residue.**
`verify_service_fact_roster_independence` seeds `declared_service_state[fixture-routed]` and never
removes it. A fixture driving `audit_service_states` over the roster *as this run left it* therefore
reports the alias-roster disagreement in **both** directions — measured, while row 5's fixture was
being written. Fixed inside row 5's fixture by rebuilding the roster from `service_aliases` before
each direction, which is what section 6 says a fixture does: it builds its own input.
