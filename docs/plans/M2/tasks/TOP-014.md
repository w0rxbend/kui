# TOP-014 — The list pipeline: filter, search, sort, page — in that order

- **ID:** TOP-014
- **Title:** The list pipeline: filter, search, sort, page — in that order
- **Milestone / Feature:** M2 / TP-001, SF-001, CL-010 (server half)
- **Owner role:** Domain Architect (topics)
- **Context / service:** `services/topic/application`
- **Size:** L
- **Dependencies / blocked by:** TOP-013, TOP-001

## Goal (user value)

A topic list that says how many topics matched, and means it — so that "page 3 of 40" is true, and
turning off "show internal topics" changes both the rows and the count.

This is the task the milestone brief singled out: the reference product computes its page count
before applying the internal-topic filter and therefore overstates it. KUI does not, and this task
is where that is made impossible rather than merely intended.

## Scope

1. `ListTopics`: one pure function from a `TopicSnapshot` plus a `TopicListQuery` to a
   `Page[TopicSummary]`.
2. The order, fixed and enforced: **visibility → internal → search → sort → page**.
3. `TopicListQuery`: the validated query — `q`, `mode`, `showInternal`, `sort`, `PageRequest`, and
   a visibility predicate.
4. Sorting by every field of `TopicSortField`, with `None` values always last in both directions
   and a stable tiebreak on name.
5. The visibility predicate parameter, passed but not populated: M6's RBAC filter plugs in here
   and the ordering rule is already enforced by then.

## Non-goals

- No RBAC. The predicate M2 passes admits everything; `services/identity` does not exist.
- No CSV (TP-017, M5), no cursor paging (that is ADR-026's other half and belongs to messages).
- No caching of results. The input is already a snapshot; caching a page of it would be a cache
  keyed by every query.
- No favourites. They are a browser preference and never reach the server (DEVPLAN §10 D9).
- No second `Page` type. `libs/kernel`'s `Page.of` cuts the page and computes the total.

## Design references

- **`libs/kernel/src/kui/kernel/paging.scala`** — read `Page.of`'s doc comment before writing
  anything: "filtering must happen before this call, never after … the implementation this project
  is modelled on counts before filtering, so its page count is wrong whenever a filter removes
  anything, and the only reliable fix is to make the arithmetic impossible to get wrong by doing
  it in one place". M2 is the first caller of that decision.
- `research/kafbat/api-analysis.md` §3.3 — the reference's parameters, defaults, sort enum and the
  bug, cited to `TopicsController.java:213-220`.
- `research/kafbat/feature-matrix.md` TP-1 — "pagination is in-memory over the statistics cache
  **after** RBAC filtering", which is where the visibility predicate goes.
- ADR-026 (defaults, maximum, the response shape), ADR-038 (`q` and `mode`), DEVPLAN §10 D2, D3, D4.

## Public Scala signatures to implement

```scala
package kui.topic.application

import kui.kernel.search.SearchMode
import kui.kernel.{Page, PageRequest, Sort, TopicName}
import kui.topic.domain.{TopicSnapshot, TopicSortField, TopicSummary}

/** Everything a list request asks for, already validated.
  *
  * It is a value and not a bag of parameters because the ordering rule below is a property of the
  * *query*, and a function taking six arguments in the right order is a function somebody will
  * call in the wrong one.
  */
final case class TopicListQuery(
    q: Option[String],
    mode: SearchMode,
    showInternal: Boolean,
    sort: Sort[TopicSortField],
    page: PageRequest,
    /** M6's RBAC filter. M2 passes `_ => true`; it exists now so that the ordering rule — filter
      * before you page — is enforced by a property test before there is anything to get wrong. */
    visible: TopicName => Boolean
)

object TopicListQuery {
  val DefaultSort: Sort[TopicSortField] = Sort(TopicSortField.Name, SortOrder.Asc)
}

/** The one place a topic list is produced.
  *
  * ==The order is the contract==
  *
  *   1. `visible` — RBAC (M6). A user must not learn a topic exists from a page count.
  *   2. internal — the `showInternal` toggle.
  *   3. `q` / `mode` — the name search.
  *   4. `sort`.
  *   5. `Page.of` — which counts what it is handed.
  *
  * Every filter runs before the total is taken, which is the whole difference from the
  * implementation this is modelled on (`research/kafbat/api-analysis.md` §3.3: `pageCount` is
  * computed from the list *before* the `showInternal` filter, so it overstates pages when internal
  * topics are hidden). `ListTopicsSuite` asserts the equivalence as a property over generated
  * snapshots, so a future refactor that reorders these lines fails a test rather than a user.
  */
object ListTopics {
  def apply(snapshot: TopicSnapshot, query: TopicListQuery): Page[TopicSummary]
}
```

```scala
package kui.topic.application

/** The orderings, one per sort field.
  *
  * Two rules apply to all of them and are the reason this is a named object rather than six
  * inline lambdas:
  *
  *   - **Missing values sort last in both directions.** A topic whose message count could not be
  *     computed must not float to the top when the user sorts descending by count; the rows with
  *     data are what the user asked to see.
  *   - **The tiebreak is always the name, ascending.** Without it, two topics with equal size swap
  *     places between requests and the second page of a stable list is not stable.
  */
object TopicOrdering {
  def of(sort: Sort[TopicSortField]): Ordering[TopicSummary]
}
```

## Decisions this task takes (no ADR covers them)

1. **Search runs after the internal filter, not before.** Both orders give the same rows; only this
   one gives the same *count* as the rows, because the count is taken once at the end. Stating it
   removes the temptation to "optimise" by searching the index first — which would also mean
   searching an index that includes hidden topics.
2. **`fts` relevance order is honoured only when `sort` is absent from the request.** The contract
   layer therefore distinguishes "no sort given" from "sorted by name ascending", and
   `TopicListQuery.sort` is an `Option` at the edge and defaulted here. Anything else would make an
   explicit sort silently ignored in `fts` mode, which is the reference's behaviour and is
   confusing.
3. **An out-of-range page is an empty page with the correct total, not a 404.** A bookmark to page
   9 of a list that has shrunk should say "nothing here, 3 pages", not fail. `Page.of` already does
   this and the suite asserts it.

The property that closes the brief's named defect, runnable as a one-liner in the suite:

```scala
property("the total counts what the filters left") {
  forAll { (snapshot: TopicSnapshot, query: TopicListQuery) =>
    val expected = snapshot.topics.filter(query.visible(_.name))
      .filterNot(t => t.isInternal && !query.showInternal)
      .filter(matches(query))
    assertEquals(ListTopics(snapshot, query).totalItems, Some(expected.size.toLong))
  }
}
```

## Tests required

`ListTopicsSuite` (property-first):

- **`theTotalCountsWhatTheFiltersLeft`** (property) — above.
- **`hidingInternalTopicsChangesTheTotal`** — the exact reference bug, as a regression test with
  the citation in its comment.
- `theUnionOfEveryPageIsTheFilteredSetExactlyOnce` (property).
- `noPageIsLargerThanPageSize` (property).
- `anOutOfRangePageIsEmptyWithTheCorrectTotal`.
- `theVisibilityPredicateRunsBeforeEverythingElse` — a predicate that hides a topic removes it from
  the total, not just from the page.
- `searchIsAppliedToTheFilteredSet` — a query matching only internal topics returns zero rows and a
  zero total when `showInternal` is false.
- `plainAndFtsAgreeOnExactSubstrings` (property).
- `relevanceOrderIsUsedOnlyWhenNoSortWasGiven`.

`TopicOrderingSuite`:

- `missingValuesSortLastAscending` and `...Descending` — one test each, because getting one right
  and the other wrong is the likely bug.
- `theTiebreakIsTheName` (property) — shuffle equal rows, assert a deterministic result.
- `everySortFieldHasAnOrdering` — an exhaustive match over `TopicSortField`, so adding a field
  fails to compile rather than sorting by nothing.
- `sortingIsStableAcrossPages` (property) — page 2 of a sorted list equals rows 26…50 of the fully
  sorted list.

## Observability

- `kui.topic.list.duration` histogram with `cluster`, `mode` and whether a sort was given. It is
  pure computation over an in-memory snapshot, so a slow one means the snapshot has grown, and
  that is worth seeing before a user reports it.
- `kui.topic.list.matched` histogram — how many topics a query matched. Search that always returns
  everything or nothing is a search nobody is using well.
- No log line per request: the `api` layer already logs the request.

## Degraded behaviour

- **A stale snapshot**: the pipeline neither knows nor cares; staleness is carried by the
  `SnapshotCell` and rendered as `Section.Stale` at the edge. That separation is deliberate — the
  list must be computable from an old snapshot, or a cluster outage would empty the screen.
- **A snapshot with `incomplete` topics**: the page is computed over what was read, and the edge
  carries the incomplete count so the screen can say "2 topics could not be read".
- **An empty snapshot**: an empty page with a total of zero, which the screen renders as its empty
  state and not as an error.
