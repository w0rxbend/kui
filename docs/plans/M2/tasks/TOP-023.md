# TOP-023 — Gateway: topic routes, `ServiceContracts` entry, capability entry

- **ID:** TOP-023
- **Title:** Gateway: topic routes, `ServiceContracts` entry, capability entry
- **Milestone / Feature:** M2 / TP-001, KU-001
- **Owner role:** Chief Architect
- **Context / service:** `services/gateway`
- **Size:** M
- **Dependencies / blocked by:** TOP-020

## Goal (user value)

The browser can reach the topic service through the one process it talks to, and the sidebar's
Topics entry dims when that service is down and comes back when it returns.

## Scope

1. `ServiceContracts.byService` gains `topic -> TopicEndpoints.all`, which is the **only** line in
   the gateway that names the topic service.
2. The derived proxy routes for all five topic endpoints, under `/api/v1`.
3. `X-Kui-Cluster-Id` handling for the topic routes, reusing `ClusterScope` — not a second
   implementation.
4. The topic service's capability entry: configured, polled for readiness, folded per ADR-039, and
   reported in `GET /api/v1/capabilities` as `topic`.
5. The gateway's own configuration gains `kui.gateway.services.topic.url`.

## Non-goals

- No aggregation. TOP-024 adds the topic overview; this task is proxying only.
- No Kafka anything. Rule A8: the gateway holds no Kafka client, and this task adds no dependency
  that could carry one.
- No knowledge of topic semantics. The gateway does not know what a partition is, and no code here
  may branch on a topic field.
- No RBAC pre-check rules for topics beyond the existing generic mechanism; `TOPIC:VIEW` becomes
  meaningful in M6.

## Design references

- `services/gateway/api/src/kui/gateway/api/routing/ServiceContracts.scala` — its own doc comment
  says it "grows by one line per service across M1 to M8". This is that line.
- `ContractRouting.scala`, `ClusterScope.scala`, `CapabilityRegistry.scala`,
  `ReadinessPoller.scala` — the existing mechanisms, all of which this task uses and none of which
  it changes.
- ADR-004 (the gateway owns no domain), ADR-039 (the capability fold: four inputs, precedence,

- DEVPLAN §10 D11 — a Kafka cluster the topic service cannot reach is a `Section`, and must not dim

## Public Scala signatures to implement

```scala
object ServiceContracts {

  val byService: Map[ServiceId, List[AnyEndpoint]] =
    Map(
      ServiceId.unsafe("cluster") -> ClusterEndpoints.all,
      ServiceId.unsafe("topic") -> TopicEndpoints.all
    )

  /** Endpoints the gateway serves itself and must therefore not derive a proxy route for.
    *
    * Keyed by the endpoint `name` the contract fixes, because the name is stable and the path is a
    * string the derivation is already deriving. Two routes for one path is a collision nobody sees
    * in a route list.
    */
  val aggregated: Set[String] = Set("cluster.list")
}
```

No new type is introduced. That is the point of this task: adding a service to the gateway is one
map entry and one configuration key, or the routing mechanism M0 built has failed.

## Decisions this task takes (no ADR covers them)

1. **The topic list is proxied, not aggregated.** The dashboard's cluster list is aggregated
   because the gateway decorates each row with capability state it alone holds; a topic list has no
   such decoration, and an aggregation with nothing to add is a second copy of a response shape to
   keep in step — which is exactly M1's second integration defect.
2. **The topic service's tier is Degradable**, so its being down never affects the shell, the
   dashboard or the brokers page. That is a statement about the fallback panel and the capability
   fold, both of which already exist; this task only registers it correctly.

## Observability

- Inherited: the gateway's access log, `kui.http.client.duration` per upstream with `service =
  topic`, and the capability registry's own transitions.
- No new instrument. A new metric per proxied service would be a metric per service to maintain,
  and the `service` label already exists for exactly this.

## Degraded behaviour

- **Topic service down**: the capability is `Unavailable` with the reason and a sticky `since`; the
  sidebar entry dims but stays clickable; the feature renders its fallback panel; every other
  feature is untouched. This is the milestone's headline scenario and TOP-037 asserts it in a
  browser.
- **Topic service slow**: the breaker opens per ADR-037, the capability degrades, and the response
  is bounded by the configured timeout rather than by the upstream.
- **Topic service not configured at all**: `NotConfigured`; the sidebar entry is hidden and no
  route is derived. A deployment that has not deployed the topic service is a supported shape and
  must not show a broken menu item.
