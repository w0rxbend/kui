# TOP-029 — The topics list screen

- **ID:** TOP-029
- **Title:** The topics list screen
- **Milestone / Feature:** M2 / TP-001, SF-001, SF-003, CL-010
- **Owner role:** Frontend Architect
- **Context / module:** `frontend/ui-topics`
- **Size:** L
- **Dependencies / blocked by:** TOP-028, TOP-026, TOP-027

## Goal (user value)

The screen the milestone is judged on: ten thousand topics, searchable, sortable, paged, with
internal topics hidden by default, favourites pinned to the top, and a count that is true.

## Scope

1. `TopicListPage` at `/ui/clusters/{clusterId}/topics`.
2. The control bar: search with its mode toggle, the "show internal topics" switch, the refresh
   button, and the row count.
3. The table: `VirtualizedTable` with six columns, server-side sorting, and the em-dash rule for
   every unknowable value.
4. Paging: `Pagination` under the table, with every control's state in the URL.
5. Favourites: a star column, pinning within the page.
6. Whole-table staleness through `StaleDataOverlay`, and the three distinct failure renderings.
7. The row model as one pure function, so every rule below is a test row rather than a rendering to
   eyeball.

## The row model, stated exactly

| Response state | Table | Controls | Overlay |
| --- | --- | --- | --- |
| `Section.Ok(page)` | the rows | enabled | none |
| `Section.Stale(page, fetchedAt, reason)` | the rows, dimmed | **refresh disabled**, search and sort still work | dimmed, badged with `fetchedAt` |
| `Section.Unavailable(reason, message, since)` with previous rows held | previous rows, dimmed | refresh disabled | dimmed, badged, the reason shown |
| `Section.Unavailable` with nothing held | error region with the reason and "Try again" | disabled | none — there is nothing under it |
| `Section.Forbidden` | empty state: "you may not view topics on this cluster" | disabled | none |

Search, sort and paging keep working on stale rows because they are client-side over rows already
in hand — except sort and page, which are server parameters and therefore **do** refetch. That is
the one place this screen's behaviour differs from the dashboard's, and it is deliberate: a refetch
that fails leaves the previous rows under the overlay, so the user loses nothing by trying.

## Columns

| Column | Source | Rendering | Sortable |
| --- | --- | --- | --- |
| ★ | `Favourites` | a star toggle; no header label | no |
| Topic name | `name` | the link to the detail page; a grey `IN` tag when `internal` | yes, default ascending |
| Partitions | `partitionCount` | count | yes |
| Replication factor | `replicationFactor` | count, em dash when absent | yes |
| Out of sync replicas | `outOfSyncReplicas` | `0` in normal colour, above zero in the warning colour | yes |
| Messages | `messageCount` | count with a magnitude bar; **em dash plus an "offline" chip** when absent and `offlinePartitions > 0` | yes |
| Size | `sizeBytes` | formatted bytes with a magnitude bar | yes |

Two rules from the design, applied: quantities show a horizontal magnitude bar beside the figure,
scaled against the largest value among the rows currently displayed; and counts that cross a
threshold switch to the warning colour rather than being coloured constantly.

**The messages column is the one to get right.** An absent count with offline partitions renders as
an em dash and a chip that says why — not `0`, which reads as "this topic is empty" and is the
worst thing this screen can say. DEVPLAN §10 D6.

## Non-goals

- **No Create, no delete, no purge, no clone, no batch actions.** M5. No button is rendered, not
  even disabled: a disabled control for a feature that does not exist promises a date
  (DEVPLAN §10 D8).
- No CSV download (M5). No row actions menu.
- No client-side sorting. The server sorts; `VirtualizedTable`'s sort `Var` writes the URL and the
  query refetches.
- No polling. The snapshot's `scrapedAt` is on screen and the refresh button is the user's control
  (DEVPLAN §10 D5).

## Decisions this task takes (no ADR covers them)

1. **The "show internal topics" switch is persisted in `localStorage` *and* mirrored in the URL.**
   The reference persists it, which is right — an operator who hides internal topics wants them
   hidden tomorrow — but a link must reproduce what the sender sees, so the URL wins when it is
   present and the stored value seeds it when it is not.
2. **The row count is stated as "N topics" from `totalItems`, not "N of M".** After every filter,
   `totalItems` *is* the number of topics the user is looking through, and a second number invites
   the reader to work out the difference — which is the reference product's bug wearing a label.
3. **Sorting by a column whose values are mostly absent is allowed.** The server puts missing
   values last in both directions (TOP-014), so the rows with data are always at the top, which is
   what the user wanted.

## Degraded behaviour

The five rows of the row model above, plus: **a slow response** shows the previous rows with a
loading indicator rather than a full-page loader — the reference product replaces its whole table
with a page loader on every refetch, which `research/kafbat/ui-analysis.md` records as a defect,
and this screen does not copy it.
