# TOP-034 — The profile seam suite: two processes, one contract

- **ID:** TOP-034
- **Title:** The profile seam suite: two processes, one contract
- **Milestone / Feature:** M2 / OT-007, KU-012
- **Owner role:** QA Engineer
- **Context / modules:** `apps/allinone`, `services/cluster/client`, `e2e`
- **Size:** L
- **Dependencies / blocked by:** TOP-033

## Goal (user value)

The one new failure mode this milestone creates — the topic service depending on the cluster
service — is tested across the boundary and not only on each side of it, because that is where the
M0 and M1 reviews found the worst defects.

## Scope

1. A suite that runs the **real** cluster service and the **real** topic service and exercises the
   profile protocol between them: first fetch, conditional refetch, change propagation, removal,
   and the cluster service going away and coming back.
2. Recorded-document parity: the bytes `services/cluster/api` produces are the bytes
   `services/cluster/client` decodes, asserted by a shared golden file rather than by two
   hand-written fixtures.
3. Fault injection scenario 2 of DEVPLAN §7: the cluster service stopped while the topic service
   runs.
4. The identity assertion of risk R-7: the cluster ids the topic service serves are exactly the ids
   the cluster service publishes, with no local resolution of its own.

## Non-goals

- No browser. TOP-037 does the browser.
- No new production code. If the suite cannot be written without one, that is a finding and it goes
  back to TOP-008, TOP-009 or TOP-018 — writing it here would put production behaviour in a test
  module.
- No Kafka-level assertions. This is about the seam between two KUI processes.

## What the golden document is, and why there is only one

`e2e/test/resources/expected/cluster-profile.json` is committed **once** and read by three suites:

- `services/cluster/api`'s suite asserts the running route produces exactly these bytes;
- `services/cluster/client`'s suite asserts its decoder accepts exactly these bytes;
- this suite asserts the two agree over a real socket.

Two hand-written fixtures, one on each side, would both be descriptions of what their author
believed the other side does — and M1's second integration defect was exactly that belief being
wrong, in a way that made every response decode successfully into zero rows. One file that both
sides are held to cannot express a disagreement.

## Tests required

`GoldenParitySuite` (in `services/cluster/client`, no network):

- **`theClientDecodesTheExactBytesTheServiceProduces`** — the shared golden.
- `everyFieldTheServiceSendsIsReadByTheClient` — a field the producer sends and the consumer
  ignores is a field one of them is wrong about; asserted by comparing the decoded value's
  re-encoding to the original document.

`ProfileSeamSuite` (Testcontainers Compose: broker, `kui-cluster`, `kui-topic`, `kui-gateway`):

- **`theTopicServiceResolvesEveryClusterTheClusterServicePublishes`** — the id sets are equal. Risk
  R-7's assertion, and the reason the topic service holds no cluster list of its own.
- **`theTopicServiceBuildsAWorkingAdminClientFromAFetchedProfile`** — it lists topics, which is only
  possible if the credentials crossed the seam intact.
- `aSecondFetchIsConditionalAndAnswers304`.
- **`editingAClusterPropagatesWithoutARestart`** — write a changed profile through the cluster
  service's store-backed write endpoint, assert the topic service reconnects and its next scrape
  uses the new setting, within the poll interval.
- **`stoppingTheClusterServiceLeavesTheTopicServiceServing`** — `docker stop kui-cluster`; the topic
  list still answers from the last known profiles; the topic capability reports `Degraded` with a
  reason and a sticky `since`; the topic service does not restart.
- `startingTheClusterServiceAgainClearsTheDegradedState` — with no restart of the topic service.
- **`aRemovedClusterIsReleasedAndItsSnapshotStops`** — asserted through the topic service's own
  cache metric, so a leaked refresh loop is visible as a number rather than as a hunch.
- `aFailedListFetchDoesNotRemoveAnything` — kill the cluster service mid-poll; no cluster
  disappears from the topic service.
- **`noCredentialAppearsInAnyPublicResponseOrLog`** — a sentinel-valued cluster is configured, the
  suite scrapes every `/api/v1` response and both containers' logs, and finds it nowhere.

## Observability

The suite asserts on observable state rather than on internals wherever it can: the capability
document, the cache metrics on `/metrics`, and the containers' logs. That is deliberate — a seam
test that reaches into a process's memory is a test that only passes in one deployment shape.

## Degraded behaviour

The suite *is* the degraded-behaviour test. What it must not do is tolerate a failure it was
written to detect: every assertion has an explicit timeout, and a scenario that cannot be set up
(a container that will not start) fails loudly rather than skipping. A skipped seam test is worse
than no seam test, because the build stays green.
