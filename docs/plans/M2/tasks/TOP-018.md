# TOP-018 — `ClusterProfiles` adapter over `services/cluster/client`, and client rebuild on version change

- **ID:** TOP-018
- **Title:** `ClusterProfiles` adapter over `services/cluster/client`, and client rebuild on version change
- **Milestone / Feature:** M2 / OT-007, TP-001
- **Owner role:** Domain Architect (topics)
- **Context / service:** `services/topic/infrastructure`
- **Size:** M
- **Dependencies / blocked by:** TOP-017, TOP-009

## Goal (user value)

An operator changes a cluster's bootstrap address or credentials and the topic service picks it up
without a restart — and when the cluster service is down, the topic service keeps working with what
it last knew instead of losing every cluster.

## Scope

1. `ClusterProfilesAdapter`: the topic domain's `ClusterProfiles` port implemented over
   `services/cluster/client`'s `ClusterProfiles`.
2. `TopicAdminClients`: one `AdminClientPool` per cluster, built from the profile's
   `ClusterConnection`, **rebuilt when the profile version moves**, and closed when the cluster is
   removed.
3. The change fan-out: a profile change invalidates that cluster's admin client and asks the
   snapshot registry to refresh it — one code path, so a version bump cannot update the client
   without refreshing the data or vice versa.
4. The cancellation path: releasing the resource closes every pool and deregisters the handler.

## Non-goals

- No profile fetching. TOP-009 owns the protocol; this task consumes it.
- No second definition of "how to build a Kafka client from a connection". `libs/kafka`'s client
  factory (KAFKA-004) does it, and the cluster service uses the same one.
- No configuration reading. The topic service holds no `kui.clusters[]` slice; DEVPLAN §10 D1 and
  risk R-7 are explicit that there is exactly one resolver in the product.

## Design references

- ADR-036's distribution paragraph — "rebuild clients, serde registries and snapshots when the
  version changes; no restart".
- `services/cluster/infrastructure/src/kui/cluster/infrastructure/ClusterAdminClients.scala` and

- ADR-037 (per-upstream resilience), ADR-039 (the health this feeds).

```scala
package kui.topic.infrastructure

import cats.effect.kernel.Resource
import kui.cluster.client.ClusterProfiles as ClientProfiles
import kui.topic.domain.ClusterProfiles as DomainProfiles

/** The domain's view of the profile client: identities only, no connection material.
  *
  * The narrowing is the point. A use case that could reach a password is a use case that could log
  * one, and the domain port was written without one for that reason (TOP-012).
  */
object ClusterProfilesAdapter {
  def apply[F[_]: Async](client: ClientProfiles[F]): DomainProfiles[F]
}
```

```scala
package kui.topic.infrastructure

import kui.kafka.AdminClientPool
import kui.kernel.ClusterId

/** One admin client pool per cluster, kept in step with the profiles.
  *
  * ==Why a rebuild is not just a reconnect==
  *
  * A profile version bump can change the bootstrap addresses, the security mechanism, the
  * credentials or the TLS material. A pool that reconnected with its old properties would
  * authenticate with a password the operator has just rotated away, fail, and report the cluster
  * as unreachable — which is the failure that looks like the operator's mistake and is not.
  */
trait TopicAdminClients[F[_]] {
  def poolFor(cluster: ClusterId): F[Either[TopicError, AdminClientPool[F]]]
}

object TopicAdminClients {

  /** @param onRebuilt called after a pool is replaced, so the snapshot for that cluster can be
    *                  refreshed. One callback rather than two subscriptions to the same event: a
    *                  client updated without its data refreshed shows old topics through a new
    *                  connection, which is indistinguishable from a bug.
    */
  def resource[F[_]: Async](
      client: ClusterProfiles[F],
      onRebuilt: ClusterId => F[Unit],
      logger: StructuredLogger[F]
  ): Resource[F, TopicAdminClients[F]]
}
```

## Behaviour it must have

- A pool is created lazily, on first use for a cluster, and cached.
- `ProfileChange.Updated` closes the old pool **after** the new one is built, so an in-flight
  request is not cancelled by a configuration edit; the old pool is released when its outstanding
  calls finish or after a grace period, whichever is first.
- `ProfileChange.Removed` closes the pool immediately and drops it.
- A pool that cannot be built (an unreachable broker, a bad credential) is **not** cached as a
  failure: the next request tries again, because the fix is usually external and a cached failure
  would need a restart to clear.
- Every path is bounded by `AdminTuning.apiTimeout`; nothing here waits indefinitely.

## Cancellation and shutdown

Releasing the resource deregisters the change handler first, then closes every pool. Reversing
those two would let a change arrive mid-teardown and build a pool nothing will close. Asserted by
`releasingTheClientsClosesEveryPoolAndDeregisters`.

`TopicAdminClientsSuite` (`munit-cats-effect` + `TestControl` + a fake profile client):

- `aPoolIsBuiltOnceAndReused`.
- **`aVersionBumpRebuildsThePoolWithTheNewConnection`** — the fake reports a changed bootstrap
  address and the new pool has it.
- **`aVersionBumpAlsoTriggersOnRebuilt`** — the two are one code path.
- `theOldPoolIsClosedAfterTheNewOneIsBuilt`, and an in-flight call on the old pool completes.
- `aRemovedClusterClosesItsPoolImmediately`.
- `aPoolThatCannotBeBuiltIsNotCachedAsAFailure` — the second call retries.
- `noProfileIsClusterNotFound`.
- **`releasingTheClientsClosesEveryPoolAndDeregisters`** — and no handler runs afterwards.
- `aChangeArrivingDuringTeardownBuildsNothing`.

## Observability

- INFO on every rebuild: cluster, old version, new version, and what changed at the level of
  "bootstrap servers", "security mechanism" or "properties" — never the values. This is the line an
  operator looks for after editing a cluster, and it is the difference between "KUI has not picked
  it up" and "KUI picked it up and the broker still refuses".
- `kui.topic.admin.pools` up-down counter, so a pool leak is visible as a number that only grows.
- WARN when a pool cannot be built, rate-limited per cluster.

## Degraded behaviour

- **Cluster service down**: the client serves last-known profiles; pools keep working; the
  capability is `Degraded` with the reason from `ProfileClientHealth`. This is the scenario TOP-034
  injects and nothing else in the product covers.
- **Cluster service down and this service just started**: no profiles at all; every list answers
  `Section.Unavailable` and the service stays up, retrying.
- **A profile that will not build a client** (bad credentials after a rotation): that cluster's
  calls fail; every other cluster is unaffected; the WARN names the cluster.
