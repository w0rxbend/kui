# TOP-007 — `libs/testkit`: seeded topics, an internal topic, a leaderless partition, a 10k bulk create

- **ID:** TOP-007
- **Title:** `libs/testkit`: seeded topics, an internal topic, a leaderless partition, a 10k bulk create
- **Milestone / Feature:** M2 / TP-001, PA-001
- **Owner role:** QA Engineer
- **Context / module:** `libs/testkit`
- **Size:** M
- **Dependencies / blocked by:** —

## Goal (user value)

Every suite in M2 that needs a broker with topics on it gets the same broker with the same topics
from one file, including the two states that are hard to produce by hand: an internal topic and a
partition with no leader.

## Scope

1. `TopicSeed`: a declarative description of topics to create (name, partitions, replication
   factor, configs) and the helper that applies it to a running broker.
2. `TopicFixtures`: the named seeds M2's suites share — a small realistic set, the internal set,
   and a bulk generator for the 10 000-topic case.
3. **A leaderless partition**, produced deterministically. On a single-broker Testcontainers
   cluster the reliable way is a topic created with a replica assignment naming a broker id that
   does not exist; the helper does that and documents why, because the obvious approach (stopping
   a broker) does not work on a one-broker cluster and is slow on a three-broker one.
4. Domain-free: `libs/testkit` may not depend on a service (A5), so these fixtures speak in Kafka
   and `libs/kernel` terms only.

## Non-goals

- No new container topology. `KafkaFixture` and `KafkaTopology` exist from CFGOP-004 and are the
  single home of the container. This task adds *seeding*, not a second broker.
- No message production. Seeding data into topics is M3's; M2 needs topics, partitions and
  offsets, and an empty topic has offsets (0, 0) which is a case worth testing anyway.
- No generators of `services/topic` domain types. Those live in the topic service's own test
  module, exactly as the cluster domain's fixtures do, and for the same rule.

## Design references

- `libs/testkit`'s existing `KafkaFixture` / `KafkaTopology` (CFGOP-004) — the shape to extend.
- `research/kafka/admin-capabilities.md` §2, "Create topic": `NewTopic(name, replicasAssignments)`
  is the constructor that lets a test place replicas on a broker that is not there.
- M1's gate finding F-11 — one container topology, in one file. A second broker declared in a
  suite is the finding this task exists to prevent from recurring for topics.

## Public Scala signatures to implement

```scala
package kui.testkit.kafka

import kui.kernel.TopicName

/** One topic to create.
  *
  * `replicaAssignment` is how a test produces a partition with no leader: naming a broker id that
  * is not in the cluster creates the partition with a replica that can never be elected, which is
  * indistinguishable, from the AdminClient's point of view, from a broker that has died. The
  * alternative — stopping a broker — is impossible on the single-broker container M2's suites use
  * and takes tens of seconds on a three-broker one.
  */
final case class TopicSeed(
    name: TopicName,
    partitions: Int = 1,
    replicationFactor: Short = 1,
    configs: Map[String, String] = Map.empty,
    replicaAssignment: Option[Map[Int, List[Int]]] = None
)

object TopicSeed {
  /** A topic whose partition `partition` has no electable leader. */
  def leaderless(name: TopicName, partitions: Int, offlinePartition: Int): TopicSeed
}
```

```scala
package kui.testkit.kafka

import cats.effect.kernel.{Async, Resource}

object TopicFixtures {

  /** Eight topics with varied partition counts, replication factors and configs: enough to
    * exercise every sort field with distinct values, so a sort test cannot pass by accident on a
    * set where every row is equal.
    */
  val realistic: List[TopicSeed]

  /** `__consumer_offsets` is created by the broker; these are the ones KUI's own store makes and
    * the ones a prefix rule must catch that Kafka's `isInternal` flag does not (DEVPLAN §10 D3).
    */
  val internal: List[TopicSeed]

  /** One topic, three partitions, the middle one offline. */
  val withOfflinePartition: TopicSeed

  /** `count` topics named `bulk-000000` … , one partition each. Created in batches so a 10 000
    * topic seed does not exceed the broker's request size limit.
    */
  def bulk(count: Int): List[TopicSeed]

  /** Applies seeds to a running broker and deletes them when the resource is released, so a suite
    * that shares a container with another suite does not leave it dirty.
    */
  def seeded[F[_]: Async](bootstrap: String, seeds: List[TopicSeed]): Resource[F, Unit]
}
```

## Decisions this task takes (no ADR covers them)

1. **Bulk topics are created in batches of 500 per `createTopics` call.** One call with 10 000
   `NewTopic`s exceeds the default `max.request.size` on some broker configurations and fails with
   a message that names nothing useful. Five hundred is comfortably inside it and keeps the seed
   under a minute.
2. **`seeded` deletes what it created and nothing else.** A fixture that dropped every topic would
   race with a suite sharing the container, and container sharing is what makes the M2 suites
   affordable.

## Tests required

`TopicSeedSuite` (Testcontainers, one PLAINTEXT broker from `KafkaFixture`):

- `realisticSeedsAppearInAListing` — created, listed, and each with the partition count it asked
  for.
- **`aLeaderlessSeedActuallyHasNoLeader`** — `describeTopics` reports `leader = null` for the
  offline partition and a leader for the others. If this assertion cannot be made to pass, every
  leaderless test in the milestone is testing nothing, so it is the first one to write.
- `internalSeedsAreNotFlaggedInternalByKafka` — the assertion that justifies DEVPLAN §10 D3's
  union rule, taken from a real broker rather than from a document.
- `bulkCreatesTheRequestedCount` at 1 000 (the 10 000 case runs in TOP-035's nightly suite).
- `seededReleasesWhatItCreated` — after the resource closes, the listing is back to what it was.

## Observability

None: test code. The seed helper prints the elapsed creation time for the bulk case, because that
number is the input to TOP-035's benchmark and to the decision in DEVPLAN §6.4 item 3.

## Degraded behaviour

- A broker that refuses a create fails the fixture loudly, naming the topic and the Kafka
  exception. A fixture that silently seeded nothing would make every downstream suite pass
  vacuously, which is worse than a red build.
- `seeded`'s release path never fails a suite: deletion errors are logged and swallowed, because a
  failed cleanup must not mask a passing test or a real failure.
