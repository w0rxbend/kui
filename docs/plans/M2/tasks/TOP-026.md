# TOP-026 — `ui-kernel`: `VirtualizedTable`

- **ID:** TOP-026
- **Title:** `ui-kernel`: `VirtualizedTable`
- **Milestone / Feature:** M2 / SF-003
- **Owner role:** Frontend Architect
- **Context / module:** `frontend/ui-kernel`
- **Size:** L
- **Dependencies / blocked by:** — (start on day one; it needs no backend)

## Goal (user value)

A table of thousands of rows scrolls smoothly, because only the rows on screen are in the document.

## Scope

1. `VirtualizedTable` in `kui.ui.kernel.component`: a windowed table over a `Signal[List[A]]`, with
   a fixed row height, an overscan, sortable headers and a sticky header row.
2. Absolute ARIA indices: `aria-rowcount` is the total and each row's `aria-rowindex` is its
   position in the whole list, not in the window — otherwise a screen reader announces "row 3 of
   12" on a list of ten thousand.
3. Keyboard support: arrow keys, Page Up and Page Down, Home and End move the focused row and
   scroll the window; the focused row is never a row that has been recycled out of the document.
4. Density: the `compact` flag changes row padding from 15 px to 9 px and nothing else, per the
   design.
5. A benchmark hook — a `data-kui-bench` attribute and a deterministic row generator in the test
   tree — that `e2e`'s harness page (TOP-037) drives.

## Non-goals

- **No general grid.** This is the risk the roadmap names itself. No column resizing, no column
  reordering, no grouping, no pinned columns, no cell editing, no row expansion. Dynamic columns
  arrive with MS-004 in M3, and the component takes a fixed `List[Column[A]]`.
- No variable row heights. A single fixed height is what makes the window arithmetic exact; a
  measured-height virtualizer is a different component with a different set of bugs.
- No data fetching, no paging. The component takes the rows it is given. Paging is `Pagination`
  (TOP-027) and it is a sibling, not a parent.
- No replacement of `DataTable`. The M0 table stays and keeps its callers; a list of thirty
  brokers does not need a window.

- `research/kafbat/ui-analysis.md` "NewTable" and "Topics list" — the sortable header behaviour and

## Public Scala signatures to implement

```scala
package kui.ui.kernel.component

import com.raquo.laminar.api.L.*

/** A table that keeps only the visible rows in the document.
  *
  * The row height is fixed and given, not measured. Measuring would allow variable-height rows and
  * would also make every scroll a layout read; a fixed height turns the window into arithmetic,
  * which is what makes the frame budget in `docs/benchmarks/` achievable and, more importantly,
  * *predictable* — a virtualizer whose cost depends on content is one that is fast in a test and
  * slow on the one cluster that matters.
  */
object VirtualizedTable {

  def apply[A](
      rows: Signal[List[A]],
      columns: List[Column[A]],
      rowKey: A => String,
      rowHeight: Int = 40,
      /** Rows rendered above and below the viewport. Three is enough to hide a fast scroll's
        * repaint and small enough that the document stays short. */
      overscan: Int = 3,
      compact: Signal[Boolean] = Val(false),
      sort: Var[Option[TableSort]] = Var(None),
      emptyState: HtmlElement = EmptyState.default,
      testId: Option[String] = None
  ): HtmlElement
}

/** The arithmetic, extracted so it is testable without a DOM.
  *
  * Every off-by-one in a virtualizer is in this function, and every one of them looks like a
  * flickering row rather than like an exception.
  */
object Window {

  final case class Slice(firstIndex: Int, count: Int, offsetPx: Int, totalHeightPx: Int)

  def slice(scrollTop: Int, viewportHeight: Int, rowHeight: Int, overscan: Int, total: Int): Slice
}
```

## Decisions this task takes (no ADR covers them)

1. **The window arithmetic is a pure function in its own object.** It is the part that is wrong,
   and it is the part that cannot be tested by looking at a screen.
2. **Rows are keyed by a caller-supplied `rowKey`, not by index.** A keyed row survives a re-sort
   without being torn down, which is what keeps focus and selection where the user left them.
3. **The component owns its scroll container.** A caller that provided the scroller would have to
   coordinate the height calculation, and two owners of one scroll position is how a table
   jitters.
4. **Sorting is a `Var[Option[TableSort]]` the caller owns.** The topic list sorts on the server
   (TOP-029), and a component that sorted its own rows would silently disagree with the page it is
   on.


## Tests required

`WindowSuite` (pure, property-heavy — this is where the bugs are):

- `theSliceNeverExceedsTheTotal` (property).
- `theSliceCoversTheViewport` (property) — every pixel of the viewport is covered by a rendered
  row, which is the assertion that catches an off-by-one that shows as a blank strip.
- `scrollingToTheEndDoesNotOverrun` (property).
- `aShortListRendersEveryRow` — fewer rows than the viewport holds.
- `anEmptyListIsAZeroSlice`.
- `totalHeightIsRowsTimesHeight` (property) — the scrollbar's length, which is what makes the
  scrollbar honest.
- `theOffsetKeepsRowsAlignedToTheirIndex` (property).

`VirtualizedTableSuite` (jsdom, `domtestutils`):

- **`onlyTheWindowIsInTheDocument`** — 10 000 rows, fewer than 30 `<tr>` elements present.
- **`ariaRowIndexIsAbsolute`** — the first rendered row after scrolling to the middle announces its
  real position, and `aria-rowcount` is 10 000.
- `scrollingReplacesTheRenderedRows`.
- `sortingAColumnUpdatesTheSortVarAndDoesNotResortLocally`.
- `theHeaderStaysWhileTheBodyScrolls`.
- `keyboardNavigationMovesFocusAndScrolls` — arrow, Page Down, End.
- `focusIsNotLostWhenTheFocusedRowScrollsOutAndBackIn`.
- `compactChangesOnlyThePadding` — asserted on the computed class, not the pixel, since jsdom does
  not lay out.
- `anEmptyListRendersTheEmptyStateNotAHeaderWithNothingUnderIt`.
- `rowsAreKeyedSoASortDoesNotRecreateThem`.

## Observability

None. Kernel components send no client-side metric to the server; M0's rule. The benchmark
harness measures from outside, in the browser, which is where a frame time is real.

## Degraded behaviour

- **A row height that does not match the CSS**: the arithmetic is authoritative and the CSS is
  generated from the same constant, so they cannot disagree; the constant is exported for the
  stylesheet's use rather than typed twice — one string typed twice in two files is the M0 finding
  this avoids.
- **A viewport of zero height** (a hidden tab): the slice is empty, nothing renders, and nothing
  divides by zero.
- **A list that changes while scrolled past its new end**: the scroll position is clamped and the
  window recomputed, rather than showing a blank area.
