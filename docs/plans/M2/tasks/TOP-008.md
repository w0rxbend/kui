# TOP-008 — The profile carries credentials on `/internal/v1`, and nothing else does

- **ID:** TOP-008
- **Title:** The profile carries credentials on `/internal/v1`, and nothing else does
- **Milestone / Feature:** M2 / OT-007, TP-001 (enabling)
- **Owner role:** Chief Architect
- **Context / service:** `services/cluster/{contract,api}`
- **Size:** M
- **Dependencies / blocked by:** —

## Goal (user value)

A KUI service other than the cluster service can connect to a Kafka cluster, because the one
place that resolves cluster configuration will now tell it how — over the internal channel only,
and provably nowhere else.

## Scope

1. `ClusterProfileDto` gains the connection material: the security ADT with its `Secret` fields
   populated, the client-property overrides, and the admin tuning — everything
   `kui.kernel.cluster.ClusterConnection` needs to be reconstructed on the other side.
2. The endpoint's `description` is rewritten: it currently says "Every credential is removed: M1
   has no consumer that builds a Kafka client from this", which stops being true in this commit.
3. `services/cluster/api`'s profile route serves the populated profile.
4. **The proof that nothing else does**: a test that walks every endpoint in
   `ClusterEndpoints.all` and `ProfileEndpoints.all`, encodes a profile whose every secret is a
   distinctive token, and asserts the token appears in exactly one response body — the profile's —
   and in no log line and no span attribute produced during those calls.

## Non-goals

- No change to the public `/api/v1` cluster DTOs. `ClusterRowDto` and its friends stay redacted and
  this task must not touch them.
- No change to the metadata store, its encryption, or `libs/config`. The profile is assembled from
  the registry the cluster service already holds.
- No client. `services/cluster/client` is TOP-009.
- No new authentication between services. The signed-principal header and the `/internal/v1`
  boundary are ADR-020 and ADR-043 and already exist; this task adds no mechanism, it uses one.

## Design references

- **ADR-036**, the distribution paragraph: section owners consume the store directly "while every
  other Kafka-facing service keeps receiving the resolved `ClusterProfile` over the internal
  contract", and "keystore bytes travel inside the signed inter-service channel; adapters
  materialize to tmpfs". This task is that sentence, executed.
- DEVPLAN §10 D1 — the decision, its alternative (every service a store client with the decryption
  key) and why it was rejected.
- ADR-020 (signed principal), ADR-040 (edge header policy), ADR-043 (`/internal/v1` direct calls),
  `ARCHITECTURE.md` §5 and §14.
- `services/cluster/contract/src/kui/cluster/contract/ProfileEndpoints.scala` — the existing
  endpoint, its ETag semantics and its `oneOf` 200/304 shape, none of which changes.

## Public Scala signatures to implement

```scala
package kui.cluster.contract.dto

import kui.kernel.cluster.{AdminTuning, BootstrapServers, ClientProperties, ClusterSecurity}
import kui.kernel.{ClusterId, Secret}

/** A cluster's resolved connection settings, for another KUI service.
  *
  * ==Why this document carries credentials==
  *
  * It is served only on `/internal/v1`, only to a caller carrying a signed principal (ADR-020),
  * and it is the mechanism ADR-036 names for exactly this purpose. The alternative considered and
  * rejected in DEVPLAN §10 D1 was for every Kafka-facing service to become a metadata-store client
  * holding `kui.store.encryptionKey`, which would put the key that decrypts every stored secret
  * into four processes instead of one, and give write-capable credentials for `__kui_config` to
  * three services that must never write it.
  *
  * The fields are `Secret[…]`, so `toString`, log interpolation and span attributes render `***`.
  * Only the explicit encoder used by this endpoint writes them out, and `SecretLeakSuite` asserts
  * that no other endpoint's encoder can.
  */
final case class ClusterProfileDto(
    id: ClusterId,
    name: String,
    readOnly: Boolean,
    bootstrapServers: BootstrapServers,
    security: ClusterSecurityDto,
    properties: ClientProperties,
    admin: AdminTuning,
    /** The store version this profile was resolved at; it is also the ETag. A consumer compares
      * it rather than diffing the document, so an unchanged profile costs one 304. */
    version: Long
)
```

## Decisions this task takes (no ADR covers them)

1. **The profile is served whole, not as a delta.** A consumer that has just started has no base to
   apply a delta to, and a version comparison plus a full fetch is one code path instead of two.
   The 304 is what makes the full fetch cheap.
2. **Keystore *bytes* are not in the profile in M2.** ADR-036 says they travel on this channel, and
   they will — but nothing in M2 configures a keystore that lives in `__kui_files`, and shipping a
   field no producer fills is the "permanently-null field" CLAPI-001 already ruled against. The
   field arrives with its first producer, and `docs/operations/metadata-store.md` says so.
3. **`version` is on the body as well as in the ETag.** The ETag is an HTTP concern that an
   in-process client (all-in-one) does not have, and the consumer's rebuild decision must work
   identically in both deployment shapes.

## Tests required

`ProfileRoutesSuite`:

- `theProfileCarriesTheSecurityMaterial` — a SCRAM profile round-trips through the endpoint and the
  password comes back intact.
- `anUnchangedProfileAnswers304WithTheSameETag`.
- `theBodyVersionAndTheETagAgree` (property).
- `aProfileForAnUnknownClusterIs404`.
- `theGoldenDocumentDecodes` — the committed `cluster-profile.json`, decoded by the **contract's**
  decoder, which is the same decoder TOP-009's client will use.

`SecretLeakSuite` — the seam assertion:

- **`onlyTheProfileEndpointEmitsASecret`** — build a profile whose password, keystore password and
  every `properties` value is the literal `SENTINEL-c0ffee`; call every endpoint in
  `ClusterEndpoints.all` and `ProfileEndpoints.all` through the stub interpreter; assert the
  sentinel appears in exactly one response body.
- **`noSecretReachesALogLineOrASpan`** — with a capturing logger and the in-memory OpenTelemetry
  testkit, assert the sentinel appears in neither, including on the profile call itself.
- `theRedactedClusterDtoStillRedacts` — the M1 assertion, re-run here so this change cannot weaken
  it.

## Observability

- The profile route logs at DEBUG: cluster id, version, and whether the answer was 200 or 304.
  **Never the profile.** The suite above is what makes that a fact rather than a convention.
- A counter `kui.cluster.profile.served` with `outcome = current | not_modified`, because "the
  consumer is refetching every second" and "the consumer is polling cheaply" look identical in a
  latency graph and completely different here.

## Degraded behaviour

- **The registry has no such cluster**: 404 with `KUI-CLUSTER-NOT-FOUND`. A consumer treats it as
  "this cluster is gone" and releases its snapshot (TOP-018).
- **The store is unreachable**: the registry still resolves from static configuration and the last
  replay, so the profile is served with the version it has. A consumer that keeps working during a
  store outage is the behaviour M1's exit criteria already demanded of the cluster service, and it
  now extends one hop further.
