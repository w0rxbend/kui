# TOP-037 — Fault-isolation E2E and the virtualized-table benchmark

- **ID:** TOP-037
- **Title:** Fault-isolation E2E and the virtualized-table benchmark
- **Milestone / Feature:** M2 / KU-012, SF-003, TP-001
- **Owner role:** QA Engineer
- **Context / module:** `e2e`
- **Size:** L
- **Dependencies / blocked by:** TOP-033, TOP-030

## Goal (user value)

A browser proves the milestone's two visible claims: stopping the topic service leaves the rest of
KUI working and the topic list readable, and ten thousand rows scroll smoothly.

## Scope

1. `TopicServiceDownSuite`: the milestone's headline fault-isolation scenario, in a real browser
   against the Compose topology.
2. `TopicListSuite`: the list screen's behaviour end to end — search, sort, page, internal toggle,
   favourites, and the em-dash rule — against the seeded broker.
3. `TopicBundleSuite`: the topics module is not fetched on first paint.
4. The benchmark harness page and `VirtualizedTableBenchSuite`, writing
   `docs/benchmarks/m2-virtualized-table.md`.
5. The compose job's image dependency, so this suite runs against images built from the current
   commit.

## Non-goals

- No unit-level assertions. Anything provable without a browser belongs in a module suite; a
  browser test is slow and every one of them must earn its place.
- No fix for TD-016. `ui-clusters` is still statically imported by `main.js`; this suite asserts
  the **topics** module specifically, and its assertion must not be written in a way that passes
  only because the clusters module is fetched anyway.
- No visual regression testing. Screenshots are not asserted.

## What each suite asserts

### `TopicServiceDownSuite` — the milestone's headline scenario

With the Compose stack up and the quickstart's topics seeded:

- `theTopicsEntryIsAvailableToBeginWith`.
- `theListRendersTheSeededTopics`.
- **After `docker stop kui-topic`:**
  - `theSidebarEntryDimsButStaysClickable`;
  - `theFallbackPanelNamesTheReasonAndWhenItStarted`;
  - **`theDashboardAndBrokersPagesKeepWorking`** — the fault-isolation claim, and the reason the
    topic service is Degradable;
  - `theSettingsPageKeepsWorking`;
  - `aTopicListAlreadyOnScreenStaysReadableGreyedAndTimestamped` — through the
    `topics-stale-badge` test id;
  - `theRefreshControlIsDisabled` — DEVPLAN §10 D8: there is no Create button to assert on, and
    this is the control that exists.
- **After `docker start kui-topic`:**
  - `theEntryHealsWithNoPageReload` — asserted by a navigation counter, exactly as M1's suite does.

### `TopicListSuite` — the screen, end to end

- `searchingFiltersAndUpdatesTheCount`.
- `theInternalToggleChangesBothTheRowsAndTheCount` — the brief's named defect, in a browser.
- `sortingBySizeReordersAndSurvivesAReload` — the sort is in the URL.
- `pagingWorksAndTheUrlReproducesThePage`.
- `starringATopicPinsItAndSurvivesAReload`.
- **`aTopicWithAnOfflinePartitionShowsAnEmDashAndNotZero`** — seeded by
  `libs/testkit`'s leaderless fixture; the single most important pixel in the milestone.
- `openingATopicShowsItsPartitionsAndSettings`.
- `theTopicPageShowsNoMessagesOrConsumersTab` — asserted by absence, so M3 and M4 are visible
  additions rather than silent ones.

### `TopicBundleSuite`

- **`theTopicsModuleIsNotFetchedOnFirstPaint`** — the network log after loading `/ui` contains no
  request for the topics module; it appears only after navigating to Topics. Written so that it
  fails if the topics module is eagerly imported **even though** the clusters module still is
  (TD-016).

### `VirtualizedTableBenchSuite`

- Loads `e2e/resources/bench/virtualized-table.html`, which drives the kernel component with 10 000
  generated rows and no backend.
- Scrolls a fixed distance in fixed steps, records frame times from the browser's own performance
  timeline, and computes p50, p95 and the worst frame.
- **Gates on a regression against the committed baseline**, not on an absolute number — a runner's
  load is not the component's fault (DEVPLAN risk R-6).
- Writes `docs/benchmarks/m2-virtualized-table.md` with the machine, the browser build, the date,
  the row count and the three figures.
- The absolute 16 ms claim is asserted **once**, on the reference machine, and recorded in that file
  as an observation with the machine named.

## Decisions this task takes (no ADR covers them)

1. **The benchmark drives the component directly from a harness page, not the product's topic
   list.** ADR-026 caps a page at 500 rows, so the product can never show 10 000 at once; the
   roadmap's number is a claim about the component. DEVPLAN §10 D7 records the reasoning, and this
   is where it becomes two artefacts: a harness page and a product page.
2. **CI gates on regression; the absolute figure is an observation.** Stated above.
3. **The suite asserts the deployed build's version on startup.** M1 ran its headline suite against
   the previous milestone's images for an entire milestone; a version assertion costs one request
   and makes that impossible to repeat quietly.

## Observability

The suites read the capability document and the browser's network and performance logs — observable
surfaces, not internals. Each failure message must name what it saw: "the sidebar entry for topics
had opacity 1.0 and no title attribute" is actionable; "assertion failed" is not.

## Degraded behaviour

- A container that will not start fails the suite. **No skipping**, for the reason TOP-035 states.
- The benchmark is the one suite allowed to *warn* rather than fail: a regression beyond the
  threshold fails, but a missing baseline (a first run, a new machine) records a baseline and
  passes with a printed notice. A benchmark that cannot run on a new machine is a benchmark that
  gets deleted.
