# TOP-003 — `libs/kafka`: `listTopics` and `describeTopics` with chunking and per-key skips

- **ID:** TOP-003
- **Title:** `libs/kafka`: `listTopics` and `describeTopics` with chunking and per-key skips
- **Milestone / Feature:** M2 / TP-001, TP-003, PA-001
- **Owner role:** Principal Scala Engineer
- **Context / module:** `libs/kafka`
- **Size:** L
- **Dependencies / blocked by:** TOP-002

## Goal (user value)

KUI can ask a cluster with ten thousand topics what they are, in bounded chunks, and get an answer
in which every topic either has a description or says why it does not.

## Scope

1. `KafkaTopicAdmin`, the adapter over `AdminClientPool`, implementing `listTopics` and
   `describeTopics`. The other three methods are declared by TOP-002 and implemented by TOP-004
   and TOP-005; this task leaves them returning `ApplicationError.Unsupported("not yet
   implemented")` **only** because both of those tasks land in this milestone. A worker who finds
   a stub after TOP-005 has landed has found a bug.
2. `TopicConversions`: the pure Kafka-object-to-KUI-type functions, in their own object, so the
   `null` cases are testable with a constructor call rather than a broker in a particular state.
3. Chunking at `AdminTuning.describeChunkSize` (default 200) with bounded parallelism, reusing
   `AdminBatch` — not a second batching implementation.
4. Per-key skips: `UnknownTopicOrPartitionException` becomes `SkipReason.NotFound`,
   `TopicAuthorizationException` becomes `SkipReason.NotAuthorized`, and neither fails the batch.

## Non-goals

- No configs (TOP-004), no offsets or sizes (TOP-005), no mutations at all (M5).
- No caching. The snapshot is TOP-013's and lives in `services/topic/application`.
- No second batching helper. `libs/kafka`'s `AdminBatch` exists and its chunk sizes already come
  from `AdminTuning` (KAFKA-006); a topic-shaped copy of it would be the duplication rule A10 was
  written to make visible.
- No `listTopics` re-filtering by prefix. The internal-topic union rule of DEVPLAN §10 D3 is a
  domain rule and lives in `services/topic/application`; this port reports Kafka's flag verbatim.

## Design references

- `research/kafka/admin-capabilities.md` §2, rows "List topics" and "Describe topics": names only
  from `listTopics`, `listings()` for `topicId` and `isInternal`, per-key drops for unknown and
  unauthorized topics, chunk 200, `leader()` is `null` for offline partitions.
- DC-D4 (batching and concurrency in the adapter, configured per cluster).
- ADR-006 Amendment 1 — per-key futures, not `all()`.
- The existing `KafkaClusterAdmin` and `AdminConversions` in `libs/kafka` are the shape to copy;
  KAFKA-007's own deviation 1 records why the conversions live in their own object, and that
  reasoning applies here unchanged.

```scala
package kui.kafka.admin

import org.apache.kafka.clients.admin.{TopicDescription as KTopicDescription, TopicListing as KTopicListing}

/** Pure translation from the Kafka client's objects to KUI's.
  *
  * Every rule this module cares about at the Kafka boundary is a conversion rule — a `null` that
  * means "offline", a `-1` that means "not reported", an id a broker older than 2.8 does not
  * have. Testing those through the adapter needs a live cluster in each of those states; testing
  * them as functions needs a constructor call.
  */
object TopicConversions {
  def listing(raw: KTopicListing): TopicListing
  def description(raw: KTopicDescription): TopicDescription
  /** `null`, and a negative node id, both mean "no leader". */
  def leader(node: org.apache.kafka.common.Node | Null): Option[BrokerId]
}
```

### Behaviour `listTopics` must have

- `listTopics(new ListTopicsOptions().listInternal(includeInternal))`, read through `.listings()`
  and not `.names()`: `isInternal` and `topicId` are on the listing and a second call to get them
  would double the cost of the cheapest part of the scrape.
- Sorted by name before returning. The scrape's downstream chunking is then deterministic, which
  is what makes a failing chunk reproducible.
- `topicId` is `None` on a broker older than 2.8 rather than an error (ADR-030).

### Behaviour `describeTopics` must have

- Chunk the input at `AdminTuning.describeChunkSize`, run chunks with
  `AdminTuning.parallelism`-bounded concurrency through `AdminBatch`, and merge with
  `BatchResult.combine`.
- Use `topicNameValues()` — the per-key futures — never `all()`. One unknown topic must not lose
  the other 199 in its chunk.
- `UnknownTopicOrPartitionException` → `SkipReason.NotFound("deleted since the listing")`.
- `TopicAuthorizationException` → `SkipReason.NotAuthorized("no DESCRIBE on this topic")`.
- `InvalidTopicException` → `SkipReason.Failed(ErrorCode.Validation, …)`.
- Anything else goes through `KafkaErrorMapper`; a reconnect-class error fails the **whole call**
  with a `Left`, because a broker that has gone away will not answer the next chunk either.
- An empty input list is `Right(BatchResult.empty)` and issues no call.

## Tests required

`TopicConversionsSuite` (unit + property):

- **`nullLeaderIsNone`** and `negativeLeaderIdIsNone` — the offline-partition case, the one this
  whole milestone's worst bug grows from.
- `internalFlagIsReportedVerbatim` — no prefix rule is applied here.
- `topicIdIsNoneWhenAbsent`.
- `isrIsAsReportedEvenWhenLargerThanReplicas` — Kafka should not produce it; the conversion must
  not silently "fix" it, because a fixed value hides a broker bug from the operator.
- `partitionsAreSortedByPartitionId` (property).

`KafkaTopicAdminSuite` (unit, fake `AdminClientPool` returning canned Kafka objects):

- `chunksAtTheConfiguredSize` (property over input sizes).
- `parallelismIsBounded` — a recording pool asserts the maximum concurrent chunk count.
- **`oneUnknownTopicDoesNotLoseItsChunk`** — 200 names, one throws
  `UnknownTopicOrPartitionException`, 199 values and one `NotFound` skip come back.
- `anUnauthorizedTopicIsASkipNotAFailure`.
- `aReconnectClassErrorFailsTheWholeCall` — a `Left`, not a `BatchResult` full of skips: half an
  answer from a dead broker would be cached as if it were the truth.
- `anEmptyInputIssuesNoCall`.
- `resultsMergeInADeterministicOrder` (property).
- `listTopicsSortsByName` (property).
- **`cancellingTheCallCancelsTheOutstandingChunks`** — cancel the fiber mid-batch and assert the
  pool observed no further calls.

## Observability

- Inherited from `AdminClientPool.run`: one span per admin call
  (`kafka.admin.describeTopics`, `kafka.admin.listTopics`) and one `kui.kafka.admin.duration`
  sample with `cluster`, `operation` and `outcome`.
- One additional counter, `kui.kafka.admin.skipped`, with `operation` and `reason` labels. It is
  the number that tells an operator "your list is short because 40 topics refused, not because you
  have 40 fewer topics", and no existing metric can say that.
- DEBUG per chunk with the chunk index and size — off in production, and the only way to tell a
  slow cluster from a slow chunk when someone reports a slow scrape.

## Degraded behaviour

- **Topic deleted mid-scrape**: a `NotFound` skip. The list simply does not show it.
- **No `DESCRIBE` on some topics**: `NotAuthorized` skips; the caller renders what it has and the
  skipped count is on the metric above.
- **Broker unreachable or timed out**: `Left(InfrastructureError)`, bounded by
  `AdminTuning.apiTimeout`, the client invalidated by the pool, and the snapshot keeps serving its
  previous value as `Stale` (TOP-013).
