- **Owner role:** QA Engineer

## Goal (user value)

Every claim the milestone makes about topics is demonstrated against a real broker: the internal
filter, the search modes, every sort field, the page boundaries, the offline partition, and the ten
thousand topics the roadmap names.

## Scope

1. `TopicListLiveSuite`: the list pipeline end to end against a seeded broker, through the
   adapter and the application layer.
2. `LeaderlessLiveSuite`: the port invariant against a real offline partition — including the
   timing assertion that is the whole reason the invariant exists.
3. `TopicScaleSuite`: 10 000 topics, in the **nightly** job, with a 500-topic variant in the default
   job so the code path is covered on every commit.
4. The measurements: scrape duration, index build time and admin-call count, written to
   `docs/benchmarks/m2-topic-scrape.md`.

## Non-goals

- No security matrix. M1's three-mode suite covers PLAINTEXT, SASL/SCRAM and SSL for the admin
  path, and re-running it per milestone would triple the CI time for no new information. This suite
  is PLAINTEXT.
- No browser. TOP-037.
- No message production. M3.
- No second container topology. `libs/testkit`'s `KafkaFixture` and `TopicFixtures` are the only
  source (M1 gate finding F-11).

## What each suite asserts

### `TopicListLiveSuite` — the realistic seed

- `theInternalFilterHidesKafkaInternalTopicsAndKuiOwnOnes` — `__consumer_offsets` (Kafka's flag)
  and `__kui_config` (the prefix) are both hidden with `showInternal=false` and both shown with
  `true`. **The union rule of DEVPLAN §10 D3, against a real broker rather than a document.**
- `hidingInternalTopicsChangesTheTotal` — the brief's named defect, at the outermost testable
  layer, with a real broker behind it.
- `everySortFieldOrdersCorrectly` — one case per `TopicSortField`, against a seed whose values are
  deliberately all different so a sort cannot pass by accident.
- `sortingIsStableAcrossPages` — page 2 of a sorted list equals rows 26…50 of the whole.
- `plainSearchMatchesSubstrings` and `ftsSearchFindsATransposition`.
- `pageBoundariesAreExact` — the last page has the remainder, and page `pageCount + 1` is empty
  with the right total.
- `partitionCountsAndReplicationFactorsMatchTheSeed`.
- `messageCountsAreZeroForEmptyTopics` — zero, not absent: an empty topic has offsets and its count
  is a fact.
- `topicConfigsIncludeTheSeededOverrides` and `aSensitiveEntryHasNoValue`.

### `LeaderlessLiveSuite` — the invariant

- **`aTopicWithAnOfflinePartitionHasNoMessageCount`** — `None`, and the other topics are unaffected.
- **`theListRespondsInMillisecondsWithALeaderlessPartitionPresent`** — the assertion the whole
  `PORT-INVARIANTS.md` file exists for: elapsed time is far below `AdminTuning.apiTimeout`. Without
  the port's filtering this test takes sixty seconds and fails; with it, it takes milliseconds. It
  is the only test in the repository whose *speed* is its assertion, and the comment says so.
- `theOfflinePartitionIsReportedAsSkippedWithNoLeader`.
- `theOtherPartitionsOfTheSameTopicStillReportOffsets` — partial data is present; only the aggregate
  refuses.
- `theDetailPageDataDistinguishesOfflineFromEmpty`.

### `TopicScaleSuite` — the roadmap's number

- `tenThousandTopicsAreListedAndPaged` (nightly) — the seed, one scrape, and a page of 25 taken
  from the middle.
- `theScrapeCompletesWithinItsBudget` — against `TopicsConfig.scrapeTimeout`'s default, and the
  measured figure is printed and written to the benchmark file.
- `theAdminCallCountIsBoundedByTheChunkSizes` — asserted arithmetically from the configured chunks,
  so a regression that stops chunking is caught by a number rather than by a timeout.
- `searchOverTenThousandNamesIsUnderTheBudget` — both modes.
- `fiveHundredTopicsRunInTheDefaultJob` — the same assertions at a size CI can afford.

## Decisions this task takes (no ADR covers them)

1. **The scale suite is tagged and runs nightly, with a smaller variant on every commit.** Ten
   thousand topics take minutes to seed; a CI job that takes minutes is a CI job people skip. The
   smaller variant means a regression in the code path is caught immediately and a regression in
   the *scaling* is caught within a day.
2. **The timing assertion in `LeaderlessLiveSuite` is expressed against `AdminTuning.apiTimeout`,
   not against a literal.** A future change to the default timeout must not silently invalidate the
   test, and the assertion "much faster than the timeout" is the claim being made.
3. **The benchmark file is written by the suite, not by hand.** A number typed into a document is a
   number that ages.

## Observability

The suites read the service's own metrics back — `kui.topic.scrape.duration`,
`kui.kafka.admin.skipped`, the cache instruments — rather than measuring with a stopwatch where a
metric exists. That is deliberate: it proves the instruments are wired as well as proving the
behaviour, and a metric nobody has read back is a metric nobody knows works.

## Degraded behaviour

- A container that will not start fails the suite loudly. **No skipping.** A skipped integration
  test leaves the build green and the claim unmade, which is the failure mode `STATUS.md` records
  for M1's E2E job running against the previous milestone's images for a whole milestone.
- The scale suite is the one exception to "no skipping", and it is not a skip: it is a separate
  job. The default job always runs its smaller variant, so the code path is never untested.
