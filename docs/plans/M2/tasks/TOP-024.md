# TOP-024 — Gateway: the topic overview aggregation with placeholder sections

- **ID:** TOP-024
- **Title:** Gateway: the topic overview aggregation with placeholder sections
- **Milestone / Feature:** M2 / KU-011, KU-013, TP-003
- **Owner role:** Chief Architect
- **Context / service:** `services/gateway`
- **Size:** M
- **Dependencies / blocked by:** TOP-023

## Goal (user value)

One request returns everything a topic page shows, with each part able to be missing on its own —
so the page renders the topic even when four other services do not exist, and gains the consumer
groups tab in M4 by registration rather than by redesign.

## Scope

1. `GET /api/v1/clusters/{clusterId}/topics/{topicName}/overview` on the gateway's contract.
2. `TopicOverviewDto`: five sections — `topic`, `consumerGroups`, `connectors`, `acls`, `schemas`.
3. `TopicOverviewUseCase`: fetch the `topic` section from the topic service; every other section is
   answered from the capability registry without a call, because there is nothing to call.
4. The placeholder rule, decided in DEVPLAN §10 D10 and implemented here: a section whose service
   is absent from the deployment is `NotConfigured`, one whose service is configured and
   unreachable is `Unavailable`.
5. The extension point: adding a section in M4 is one entry in a map plus a client, and this task's
   suite asserts the shape by adding a fake sixth section in a test.

## Non-goals

- No consumer-group, connector, ACL or schema data. Those services do not exist.
- No fan-out concurrency framework. Four of the five sections are constants in M2; the fifth is one
  call. When M4 adds a real second call, the aggregation becomes a `parTraverse` and that is a
  three-line change the suite already covers.
- No caching. The topic section's freshness is the topic service's business.

## Public Scala signatures to implement

```scala
package kui.gateway.contract.dto

import kui.contracts.Section
import kui.contracts.topic.TopicDetailDto

/** Everything the topic page shows, in one document, with five independent failure levels.
  *
  * ==Why absent services are `NotConfigured` and not `Unavailable`==
  *
  * `Unavailable` means "this deployment has this thing and cannot reach it", and a screen shows it
  * with its reason so somebody can go and fix it. `NotConfigured` means "this deployment has no
  * such thing", and a screen hides it (ADR-032). In M2 the consumer, connect, security and schema
  * services do not exist in any build, so four red panels reading "unavailable" would appear on
  * every topic page of every installation — and an operator who is shown four permanent errors
  * stops reading errors. The roadmap's wording said `Unavailable`; DEVPLAN §10 D10 corrects it and
  * this is where the correction lives.
  */
final case class TopicOverviewDto(
    topic: Section[TopicDetailDto],
    consumerGroups: Section[List[Json]],
    connectors: Section[List[Json]],
    acls: Section[List[Json]],
    schemas: Section[Json],
    generatedAt: Instant
)
```

```scala
package kui.gateway.application.topic

/** The topic page's aggregation.
  *
  * Like the dashboard's, **it never fails**: every path returns a document. A section whose service
  * answered is `Ok`; one whose service is configured and did not answer is `Unavailable` with the
  * reason; one whose service this build has no client for is `NotConfigured`.
  */
trait TopicOverviewUseCase[F[_]] {
  def overview(cluster: ClusterId, topic: TopicName, principal: Principal, correlationId: CorrelationId)
      : F[TopicOverviewDto]
}

object TopicOverviewUseCase {

  /** The sections this build can actually fill. Adding one in M4 is an entry here plus its client;
    * nothing else in the aggregation changes, and `TopicOverviewSuite` proves that by adding a
    * fake section in a test.
    */
  val fillable: Set[String] = Set("topic")
}
```

## Decisions this task takes (no ADR covers them)

1. **The four future sections are typed as `Json`, not as `Unit` or as invented case classes.**
   Their shape is the owning service's contract and does not exist yet; a placeholder type invented
   here would be a type M4 has to delete from a shared module. `Json` is honest, and the sections
   are `NotConfigured` in M2 so nothing ever decodes one.
2. **The endpoint exists in M2 even though it has one real section.** It is the page's request, the
   browser is written against it now, and adding it later would mean changing the topic page's data
   flow in the milestone that adds the consumers tab — which is the milestone that should be adding
   a tab, not rewriting a page.
3. **`topic` is fetched through the same proxy client as the direct route**, not by calling the
   topic service twice with different codecs. One client, one decoder, one recorded golden.

## Tests required

`TopicOverviewSuite` (stub upstream):

- **`everySectionWhoseServiceIsAbsentIsNotConfigured`** — the four of them, by name.
- **`theTopicSectionIsOkWhenTheTopicServiceAnswers`**, from the recorded golden document.
- **`aFailingTopicServiceGivesAnUnavailableSectionAndStillA200`** — the aggregation never fails.
- `aStaleTopicSectionSurvivesAsStale`.
- `anUnknownTopicIsA404FromTheAggregationNotAnEmptySection` — a topic that does not exist is a
  different fact from a service that could not answer, and collapsing them would make the page show
  an empty topic instead of "no such topic".
- **`addingASectionIsAMapEntry`** — the test registers a fake sixth section with a stub client and
  asserts it is filled with no other change to the use case. This is KU-013's extension point,
  proven rather than promised, and it is what makes M4 a registration.
- `theResponseIsBoundedByThePerUpstreamTimeout` (`TestControl`).
- `theGoldenDocumentDecodesOnBothPlatforms` — the browser decodes this document, and M1's second
  integration defect was exactly a browser and a server disagreeing about an aggregation's shape.

## Observability

- Span `gateway.topic.overview` with `cluster`, `topic`, and one attribute per section's status —
  so a trace answers "which part of the page was missing" without opening the response.
- `kui.gateway.aggregation.section` counter with `aggregation = topic.overview`, `section` and
  `status`. It is the number that says how often operators see a degraded topic page and which part
  degrades.
- No log line on a `NotConfigured` section: it is the normal state in M2 and would be noise on
  every request.

## Degraded behaviour

- **Topic service down**: `topic` is `Unavailable`; the page renders its header from the URL and an
  error region in place of the body; the four placeholder sections are unchanged.
- **Topic service stale**: `topic` is `Stale`; the page renders greyed and timestamped.
- **Everything down except the gateway**: a 200 with five non-`Ok` sections. The page still tells
  the user which cluster and which topic they are looking at, which is more than a 503 does.
