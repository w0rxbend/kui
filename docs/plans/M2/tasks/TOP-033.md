# TOP-033 — All-in-one, Compose and the `kui-topic` image

- **ID:** TOP-033
- **Title:** All-in-one, Compose and the `kui-topic` image
- **Milestone / Feature:** M2 / KU-005, OT-003
- **Owner role:** Infrastructure Lead
- **Context / modules:** `apps/allinone`, `deployment/{docker,compose}`, `deployment/quickstart`
- **Size:** M
- **Dependencies / blocked by:** TOP-022

## Goal (user value)

Both ways of running KUI include topics: the single JVM a developer starts with one command, and
the container topology CI and production use — and the quickstart's eight seeded topics are visible
in a browser.

## Scope

1. `apps/allinone` wires the topic service into the composition root, with an **in-process**
   `ClusterProfiles` that reads the cluster service's registry directly instead of an HTTP client.
2. The `kui-topic` container image.
3. `deployment/compose/docker-compose.yml` gains the container, its configuration and its
   dependency ordering.
4. The quickstart already seeds eight topics; this task makes them visible and updates the script's
   final message to name the topics URL.
5. The all-in-one's configuration gains the `kui.topics.*` section — and it is **passed on**, which
   is the specific failure M1 shipped and integration caught.

## Non-goals

- No new seed data. The quickstart's eight topics, 111 messages and three consumer groups are M1's
  and are enough.
- No Helm chart. M8.
- No changes to the cluster service or the gateway beyond the compose wiring TOP-023 declares.

## Public Scala signatures to implement

```scala
package kui.allinone

/** The all-in-one's `ClusterProfiles`.
  *
  * In one JVM there is no HTTP hop to make: the cluster service's registry is in the same process
  * and already holds resolved profiles. Going through `services/cluster/client` here would mean
  * serialising a profile, signing a principal and parsing it back to reach an object that is
  * already on the heap — and it would make the all-in-one's behaviour depend on an HTTP stack that
  * the distributed shape tests anyway.
  *
  * What must stay identical is the **interface**, so the topic service cannot tell the two apart.
  * That is why this implements `kui.cluster.client.ClusterProfiles` rather than being wired in as
  * a special case: `TopicServiceWiringSuite` runs the same assertions against both implementations
  * and a divergence fails a test rather than a deployment.
  */
object InProcessClusterProfiles {
  def resource(registry: kui.cluster.application.ClusterRegistry[IO])
      : Resource[IO, kui.cluster.client.ClusterProfiles[IO]]
}
```

## Decisions this task takes (no ADR covers them)

1. **The all-in-one does not make an HTTP call to itself for profiles.** Above, in the doc comment.
   The interface is shared, and both implementations run the same contract assertions.
2. **The compose topology gives `kui-topic` its own container**, not a sidecar of the cluster
   service. The milestone's fault-isolation criterion is `docker stop kui-topic`, and a criterion
   that cannot be executed is not a criterion.
3. **The topic service's readiness is not a compose `depends_on: service_healthy` for the
   gateway.** The gateway must start with the topic service absent — that is the capability model —
   and a hard dependency would hide a regression in it behind a startup ordering.

## ADRs this task must obey

ADR-005 (both shapes, same modules), ADR-004, ADR-010, ADR-039 (the capability model the compose
topology must not paper over).

## Tests required

`TopicServiceWiringSuite` (`munit-cats-effect` + Testcontainers, one broker that is both the store
cluster and the managed cluster):

- **`everySectionReachesItsService`** — a configuration with distinctive values in `kui.topics.*`,
  `kui.clusters[]` and `kui.clusterProfiles.*` is loaded, and each is asserted to have arrived. M1's
  first integration defect, as a test.
- **`theInProcessProfilesSatisfyTheSameContractAsTheHttpOne`** — the shared assertions from
  TOP-009's suite, run against `InProcessClusterProfiles`.
- `theWholeGraphBootsAndServesTopics` — `GET /api/v1/clusters/{id}/topics` returns the seeded
  topics through the whole chain in one process.
- `aProfileChangeInProcessRebuildsTheTopicServicesClient` — edit a cluster through the store, assert
  the topic service reconnects without a restart.

`AllInOneWiringSuite` gains `theTopicServiceIsInTheGraph`.

`FaultIsolationSuite` gains `stoppingTheTopicUseCasesLeavesTheClusterOnesWorking` — the in-process
analogue of the compose scenario, which cannot literally stop a container.

## Observability

- The all-in-one's startup log gains a line naming the topic service and its resolved cluster
  count, for the same reason the cluster service's exists: it is what made M1's discarded-section
  defect visible the moment somebody read the log.
- The compose file sets the same OTLP exporter configuration the other services use; a service
  without telemetry in the topology is a service nobody can trace through.

## Degraded behaviour

- **`kui-topic` stopped**: the gateway reports the capability unavailable, every other feature
  works, and the browser renders the fallback panel. TOP-037 asserts it in a browser.
- **`kui-cluster` stopped, `kui-topic` running**: the topic service keeps serving from the profiles
  it holds and reports `Degraded`. TOP-034 asserts it.
- **The all-in-one with no cluster configured**: starts, serves an empty dashboard and a 404 for any
  topic list. A legitimate first-run state.
