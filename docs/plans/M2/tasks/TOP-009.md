# TOP-009 — `services/cluster/client`: the shared profile consumer, with its cancellation path

- **ID:** TOP-009
- **Title:** `services/cluster/client`: the shared profile consumer, with its cancellation path
- **Milestone / Feature:** M2 / OT-007
- **Owner role:** Chief Architect
- **Context / module:** `services/cluster/client` (new)
- **Size:** L
- **Dependencies / blocked by:** TOP-008

## Goal (user value)

Every Kafka-facing KUI service learns how to connect to every cluster the same way, from one
implementation: fetch the profile, subscribe to changes, keep the last one seen, poll as a
fallback, and rebuild when the version moves — with no restart, and with nothing left running when
the service stops.

## Scope

1. The new Mill module `services.cluster.client`, JVM only.
2. `ClusterProfiles[F]`: the interface a consuming service programs against — the current set of
   profiles, one profile by id, and a change callback.
3. `HttpClusterProfiles`: the implementation. Conditional GET with `If-None-Match`, an SSE
   subscription to `GET /internal/v1/clusters/stream`, a fallback poll every
   `kui.clusterProfiles.pollInterval` (default 60 s), a last-known cache that survives the cluster
   service being down, and a `Resource` whose release cancels the subscription and the poll.
4. The mapping from `ClusterProfileDto` to `kui.kernel.cluster.ClusterConnection`, which is what a
   Kafka client is built from.
5. Failure reporting: transport failures are reported to the caller's health reporter so the
   consuming service's capability can degrade (ADR-039), rather than being logged and forgotten.

## Non-goals

- No Kafka client. This module holds no `libs/kafka` dependency and rule A10 forbids it one.
- No domain. It maps a DTO to a `libs/kernel` value and stops.
- No caching of anything but profiles, and no persistence: a restart refetches.
- No use of it. `services/topic/infrastructure` adopts it in TOP-018.
- No in-process variant here. The all-in-one build supplies its own `ClusterProfiles` from the
  cluster service's registry directly (TOP-033); this module is the HTTP one.

## Design references

- ADR-036's distribution paragraph — "subscribe, keep the last known profile, poll as a fallback
  (60 s), and rebuild clients, serde registries and snapshots when the version changes; no
  restart". Those five behaviours are this task's checklist.
- ADR-035 (the SSE envelope and named events), ADR-037 (per-upstream timeout, bulkhead, breaker),
  ADR-043 (internal calls, one hop, cached last-known fallback, reported to the registry).
- `services/gateway/api/src/kui/gateway/api/client/SttpServiceClient.scala` and `SseWire.scala` —
  the gateway's existing typed client over a contract, which is the shape to follow rather than
  invent. What must **not** be copied is the gateway's `ServiceClient` abstraction itself: it lives
  in the gateway's application layer and rule A4 keeps it there.
- DEVPLAN §5.1 for why this is a module, and §5.3 for the rule that admits it.

## Public Scala signatures to implement

```scala
package kui.cluster.client

import cats.effect.kernel.Resource
import kui.kernel.cluster.ClusterConnection
import kui.kernel.{ClusterId, CorrelationId}

/** How a Kafka-facing service learns what it may connect to.
  *
  * The whole interface is `F`-shaped and returns values rather than throwing, because every one of
  * these can be answered from a cache while the cluster service is down — which is the point.
  */
trait ClusterProfiles[F[_]] {

  /** Every cluster this KUI knows about, as connections. Served from the last known set when the
    * cluster service is unreachable; empty only before the first successful fetch.
    */
  def all: F[Map[ClusterId, ClusterProfile]]

  def get(id: ClusterId): F[Option[ClusterProfile]]

  /** Registers a handler for profile changes and returns its deregistration.
    *
    * A callback rather than an `fs2.Stream`, for the reason ADR-041 Amendment 3 gives about the
    * domain: a stream is a concrete runtime type in a signature, and this interface is
    * implemented twice — over HTTP and in process — by callers who should not have to agree about
    * a streaming library to do it.
    */
  def onChange(handler: ProfileChange => F[Unit]): F[F[Unit]]

  /** Whether the last attempt to reach the cluster service succeeded, and when. The consuming
    * service folds this into its own capability report (ADR-039).
    */
  def health: F[ProfileClientHealth]
}

/** One cluster's connection settings plus the identity a screen shows. */
final case class ClusterProfile(
    id: ClusterId,
    name: String,
    readOnly: Boolean,
    connection: ClusterConnection,
    version: Long
)

enum ProfileChange {
  case Updated(id: ClusterId, from: Option[Long], to: Long)
  case Removed(id: ClusterId)
}

final case class ProfileClientHealth(
    lastSuccessAt: Option[java.time.Instant],
    lastError: Option[kui.kernel.error.KuiError],
    /** Sticky: the instant the current failure began, not the instant of the latest attempt. */
    failingSince: Option[java.time.Instant],
    subscribed: Boolean
)
```

    maxReconnectBackoff: FiniteDuration = 30.seconds

## Behaviour it must have

1. **On start**: fetch the cluster list, then each profile, with no `If-None-Match`. The resource
   becomes available with whatever it got; a total failure is not fatal — the service starts
   `Degraded` rather than not at all, because a consuming service that refuses to start when the
   cluster service is briefly down turns one outage into two.
2. **Steady state**: hold the SSE subscription. On a change event, refetch only the named cluster,
   with `If-None-Match`; a 304 is a no-op and does **not** fire `onChange`.
3. **Fallback**: every `pollInterval`, refetch the cluster list and any profile whose version the
   list says has moved. This is what covers a dropped SSE connection that has not yet been
   noticed.
4. **Reconnect**: exponential backoff from `reconnectBackoff` to `maxReconnectBackoff`, with jitter,
   and a single WARN when the connection is first lost — not one per attempt.
5. **Removal**: a cluster in the last known set and absent from a successful list fetch fires
   `Removed`. A *failed* fetch never fires `Removed`, because "I cannot see the list" is not "the
   cluster is gone", and treating them the same would tear down every Kafka client during a blip.

## Cancellation and shutdown

The resource's release must, in order: stop the poll fiber, close the SSE connection, and drain
outstanding change handlers. After release, no fiber remains and no HTTP request is in flight. This
is asserted by a named test (`releasingTheClientLeavesNothingRunning`), not assumed.

## Tests required

`ProfileDecodingSuite` — the seam half, with no network:

- **`theRecordedResponseDecodes`** — `recorded/cluster-profile-200.json` is a byte-for-byte capture
  of what `services/cluster/api` produces (TOP-008 commits the same bytes as its golden file), and
  it is decoded here by the client's own decoder. This is the assertion M1's second integration
  defect would have failed.
- `theRecordedStreamParses` — `recorded/clusters-stream.sse` through the SSE parser, yielding the
  named events ADR-035 defines.
- `everySecurityMechanismRoundTrips` (property) — a profile carrying each `ClusterSecurity` case
  survives encode and decode with its secrets intact.

`HttpClusterProfilesSuite` (`munit-cats-effect` + `TestControl` + an sttp stub backend):

- `startFetchesTheListAndEachProfile`.
- `aStartupFailureLeavesTheClientAvailableAndDegraded` — not a failed `Resource`.
- `anUnchangedProfileAnswers304AndFiresNoChange`.
- `aVersionBumpOnTheStreamRefetchesExactlyThatCluster` — and exactly once.
- `theFallbackPollCatchesAChangeTheStreamMissed` — with the stream stubbed silent, advance
  `pollInterval` and assert the refetch.
- `aFailedListFetchNeverFiresRemoved` — the assertion that stops a blip from tearing down clients.
- `aSuccessfulListWithoutAClusterFiresRemoved`.
- `reconnectBackoffIsExponentialAndCapped` (property, virtual time).
- `oneWarningPerDisconnectNotOnePerAttempt`.
- `healthFailingSinceIsSticky` — it is the instant the failure began, and repeated failures do not
  move it.
- **`releasingTheClientLeavesNothingRunning`** — release, advance an hour of virtual time, assert
  the backend saw no request and no handler ran.
- `handlersThatThrowDoNotKillTheSubscription` — a consumer's bad callback degrades that consumer,
  not the client.

## Observability

- Span `cluster.profile.fetch` per request, with `cluster` and `outcome`.
- `kui.cluster.profile.fetch` counter with `outcome = current | not_modified | failed`, and
  `kui.cluster.profile.subscribed` as an up-down counter — the two together answer "is this
  service getting changes, or is it polling because the stream is broken", which is the question
  an operator asks when a cluster edit does not take effect.
- INFO on a version change actually applied, naming the cluster and both versions. That line is
  the audit trail of "why did the topic service reconnect at 03:14".
- **Never the profile.** The `Secret` fields render as `***` by construction; the suite in TOP-008
  asserts the same thing on the producing side and `ProfileDecodingSuite` asserts it here.

## Degraded behaviour

- **Cluster service down at startup**: no profiles, `health.lastError` set, the consuming service
  reports `Degraded` and its list endpoints answer `Section.Unavailable`. It does not crash-loop.
- **Cluster service down after a successful fetch**: every profile is served from the last known
  set; existing Kafka clients keep working; the consuming service reports `Degraded` with the
  reason and `failingSince`. This is TOP-034's fault-injection scenario 2.
- **SSE dropped, HTTP fine**: changes arrive up to `pollInterval` late, `subscribed` is false, and
  the metric says so.
- **A profile that no longer decodes** (a newer cluster service): the cluster is left at its
  previous profile, one ERROR names the cluster and the decoding failure, and the rest of the set
  is unaffected. One malformed cluster must not blind a service to the other thirty-nine.
