# TOP-022 — Topic `app`: wiring, bootstrap ordering, readiness, teardown

- **ID:** TOP-022
- **Title:** Topic `app`: wiring, bootstrap ordering, readiness, teardown
- **Milestone / Feature:** M2 / TP-001, OT-003
- **Owner role:** Chief Architect
- **Context / service:** `services/topic/app`
- **Size:** L
- **Dependencies / blocked by:** TOP-021, TOP-018

## Goal (user value)

`kui-topic` is a process an operator can run: it starts, says what it is doing, reports itself
ready only when it can actually answer, and stops without leaving anything behind.

## Scope

1. The Mill module `services.topic.app` with its `BuildInfo`, its `Main`, and its runtime
   dependencies (logging backend, JSON encoder, telemetry exporters — none named in code).
2. `TopicWiring`: the composition root, macwire, `Resource`-shaped.
3. The bootstrap order, made explicit and tested.
4. Readiness: the process is ready when the profile client has completed its first fetch attempt
   and the HTTP server is bound — **not** when every cluster has been scraped, and §"Decisions"
   says why.
5. Teardown: the reverse order, with every resource released.
6. Configuration failure: every problem reported together, at startup, before anything binds.

## Non-goals

- No new configuration keys. TOP-032 owns the `kui.topics.*` slice; this task consumes it.
- No all-in-one wiring. TOP-033.
- No container image. TOP-033.
- No business logic of any kind. `app` names `IO` and wires; that is all it may do (ADR-010).

## Design references

- `services/cluster/app/` — `Main`, `ClusterWiring`, `ClusterBootstrap`, `ClusterConfig` and their

```scala
package kui.topic.app

import cats.effect.{IO, Resource}

/** The composition root. The only module in the topic tree allowed to name `IO` (ADR-010), and the
  * only one allowed to see `infrastructure` (rule A9), because the composition root is the one
  * place that is supposed to know which adapter implements which port.
  */

  def resource(config: TopicServiceConfig, telemetry: Telemetry[IO]): Resource[IO, TopicApp]
}

final case class TopicApp(
    routes: List[ServerEndpoint[Any, IO]],
    readiness: IO[Readiness],
    /** Exposed so the all-in-one build can drive the same graph without an HTTP server. */
    snapshots: TopicSnapshots[IO]

```

```scala
package kui.topic.app

/** The order in which this process comes up, stated once because getting it wrong makes the
  * service *hang* rather than fail — the worst startup failure shape, and the one M1's risk R-2
  * named for the metadata store.
  *
  *   1. Configuration is loaded and validated. Every error is accumulated and reported together
  *      (ADR-013); nothing else has started, so a bad configuration costs no connections.
  *   2. Telemetry, then logging: the next steps' failures must be visible.
  *   3. The profile client (`services/cluster/client`) starts and makes **one** fetch attempt with
  *      a bounded timeout. Failure is logged and the client comes up empty — it does not block
  *      startup, because a topic service that refuses to start while the cluster service restarts
  *      turns one outage into two.
  *   4. The admin client pools, lazily; nothing connects to Kafka yet.
  *   5. The snapshot registry, with no cells: the first scrape of a cluster happens when somebody
  *      asks for it, not at boot, so starting with forty clusters configured does not open forty
  *      Kafka connections in the first second.
  *   6. The HTTP server binds. Readiness flips true here.
  *
  * Teardown is exactly the reverse, and every step is a `Resource` finalizer rather than a
  * shutdown hook.
  */
object TopicBootstrap
```

## Decisions this task takes (no ADR covers them)

1. **Readiness does not wait for a scrape.** A cluster with ten thousand topics takes seconds to
   scrape and a dead cluster takes the admin timeout; gating readiness on that would make the
   process fail its Kubernetes probe because a *third-party* cluster is down. Readiness means "this
   process can answer requests", and its answer for an unscraped cluster is a well-formed
   `Section.Unavailable`.
2. **The first profile fetch is attempted, awaited with a timeout, and allowed to fail.** Awaiting
   it means the common case — everything healthy — has profiles before the first request, so the
   first user does not see an empty list. Allowing it to fail means the uncommon case does not
   deadlock. The timeout is `kui.clusterProfiles.startupTimeout`, default 10 s.
3. **Snapshots are created on demand, not at boot.** Stated in the bootstrap comment; it is the
   difference between a process that starts in a second and one that starts in a minute on a large
   installation.

## Cancellation and shutdown

`Main` runs the resource and releases it on SIGTERM. The release must: stop accepting requests,
release the snapshot registry (cancelling every refresh and in-flight scrape), release the admin
pools, release the profile client (cancelling its SSE subscription and poll), then flush telemetry.
`TopicBootstrapSuite.shutdownReleasesEverythingInReverseOrder` asserts the order by recording
finalizers, and `nothingIsRunningAfterShutdown` advances virtual time and asserts silence.

## Tests required

`TopicWiringSuite`:

- **`wiringUsesEveryConfiguredSection`** — a configuration with distinctive values in every section
  is loaded and each is asserted to have reached the component that needs it. This is M1's first
  integration defect — a section parsed and silently discarded — turned into a test before it can
  happen a second time.
- `theGraphBuildsWithNoClustersConfigured`.
- `theGraphBuildsWhenTheClusterServiceIsUnreachable` — and readiness is still true.

`TopicBootstrapSuite` (`munit-cats-effect` + `TestControl`):

- `theStartupOrderIsTheDocumentedOne` — recorded acquisitions compared to the list above.
- `readinessDoesNotWaitForAScrape` — a scrape that never completes; the server is ready.
- `theFirstProfileFetchIsAwaitedWithinItsTimeout`.
- `aFailedFirstProfileFetchDoesNotFailStartup`.
- `noSnapshotIsCreatedAtBoot` — zero admin calls before the first request.
- **`shutdownReleasesEverythingInReverseOrder`**.
- **`nothingIsRunningAfterShutdown`** — an hour of virtual time, no loader, no HTTP call, no
  subscription.

`MainConfigFailureSuite`:

- `everyConfigurationProblemIsReportedTogether` — an unknown key, a missing secret and an invalid
  URL produce one message naming all three, and the process exits non-zero without binding a port.

## Observability

- The standard startup lines: build info, the configuration summary (redacted), the resolved
  cluster count, and the bind address. The cluster count line is specifically the one M1 got wrong
  in the all-in-one — "resolved 0 configured cluster(s)" against a file that named one — and it is
  worth keeping precisely because it is what made that defect visible.
- Readiness and liveness endpoints from `libs/http`.
- A single INFO on shutdown naming what was released, so an operator can tell a clean stop from a
  kill.

## Degraded behaviour

- **No clusters configured**: the service starts, the list endpoints answer 404 for any cluster id,
  and the capability report is empty. Not an error: a KUI with the topic service deployed before
  any cluster is registered is a legitimate state.
- **Cluster service unreachable at startup**: starts, ready, `Degraded`, retrying.
- **Kafka unreachable**: irrelevant at startup — nothing connects until a request arrives.
- **A bad configuration**: does not start, and says everything that is wrong at once.
