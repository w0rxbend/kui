# E2E-002 — Fault-isolation scenario: stop the sample service

- **ID:** E2E-002
- **Title:** Fault-isolation scenario: stop the sample service
- **Milestone / Feature:** M0 / KU-001, KU-002, KU-003
- **Owner role:** QA Engineer
- **Size:** L
- **Dependencies / blocked by:** E2E-001, INFRA-002

## Goal (user value)

The milestone's central claim, proven in a browser against real separate processes: **killing
a service dims its entry, explains why, offers a retry, and leaves everything else working —
and bringing it back heals the UI with no reload.**

Every later milestone copies this test for its own service (PLAN §46: "fault-isolation tests
pass for every service introduced"), so this task also defines the reusable shape.

## Scope

1. A Testcontainers-driven Compose fixture starting `deployment/compose/docker-compose.yml`,
   with handles to stop and start individual containers.
2. The scenario, asserted step by step:

   | Step | Assertion |
   | --- | --- |
   | stack up, browser open at `/ui/` | Clusters entry is normal; `/api/v1/capabilities` says `available` |
   | `docker stop kui-cluster` | within the readiness interval + 5 s grace: the entry is **dimmed** and still clickable; exactly **one** toast appears |
   | — | the capability API reports `unavailable` with a `reason` and a `since` timestamp |
   | click the dimmed entry | the fallback panel renders with the reason, the `since` time, a Retry button and a "what still works" list |
   | navigate to Settings | Settings works normally — the rest of the app is unaffected |
   | click Retry while still down | the probe is called, the panel shows it retried and stayed unavailable; no crash, no toast storm |
   | `docker start kui-cluster` | within the readiness interval: the entry returns to normal, a success toast appears, **the page was never reloaded** (asserted by a sentinel value written into `window` at load time) |
   | ping again | it succeeds |

3. A second scenario — **slow, not dead**: `docker pause kui-cluster` (or a latency injection
   via the stub) drives the circuit breaker open; the entry shows `Unavailable(CircuitOpen)`
   rather than hanging the UI, and the gateway's response time stays bounded by the configured
   timeout. This proves HTTP-003 end to end.
4. A reusable `FaultIsolationScenario` helper so M1's cluster test, M2's topic test and every
   later one is roughly twenty lines.

## Non-goals

No Kafka failure modes (M1+). No network partition simulation beyond stop/pause. No chaos
testing framework.

## Acceptance criteria

```
$ ./mill e2e.test.testOnly kui.e2e.ClusterServiceDownSuite
kui.e2e.ClusterServiceDownSuite:
  + entry is normal while the service is up
  + stopping the service dims the entry within the readiness interval
  + exactly one toast is raised for the transition
  + the fallback panel shows reason, since, retry and what-still-works
  + settings and the shell keep working while the service is down
  + retry while down probes and reports still-unavailable
  + starting the service restores the entry with no page reload
  + ping works again after recovery
```

This output **is** the milestone exit criterion "Fault-isolation E2E" and is the single most
important artifact of M0. Attach the run log to `STATUS.md`.

## Tests required

The two suites above. Timing rules, because this is where flakiness would live:

- Every wait is `waitForCondition(timeout = readinessInterval * 3, message = "...")`, never a
  fixed sleep; the message names the expected state so a CI failure is self-explanatory.
- The readiness interval is lowered to 3 seconds in the E2E compose configuration so the suite
  is fast, and the production default of 10 seconds is asserted separately in CFG-001's
  defaults test — the test must not silently depend on a non-default configuration.
- The "no reload" assertion uses a sentinel (`window.__kuiLoadedAt`) captured at first load and
  re-read after recovery; equality proves the SPA survived.

## Observability

On failure the suite attaches the screenshot, the browser console, **both** containers' logs
and the last `/api/v1/capabilities` response — the four things needed to tell a UI bug from a
gateway bug from a service bug without re-running.

## Degraded behavior

This suite *is* the degraded-behavior verification. Its own degraded case: if Docker is
unavailable the suite skips loudly (E2E-001's rule), and CI marks the milestone criterion as
unverified rather than green.
