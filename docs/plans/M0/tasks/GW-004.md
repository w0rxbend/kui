# GW-004 — Readiness poller and circuit-state feed

- **ID:** GW-004
- **Title:** Readiness poller and circuit-state feed
- **Milestone / Feature:** M0 / KU-001
- **Owner role:** Chief Architect
- **Size:** M
- **Dependencies / blocked by:** GW-003

## Goal (user value)

The registry learns the truth by itself: it polls every configured service, watches every
circuit breaker, and notices within one interval when something dies or recovers — no manual
refresh, no user report.

## Scope

1. `ReadinessPoller` — a `Supervisor`-managed fiber per configured service that every
   `readinessInterval` (default 10 s) calls the service's `GET /health/ready` and
   `GET /capabilities` through its `ServiceClient`, and calls `registry.report`.
2. `CircuitFeed` — subscribes to `ServiceClients.circuitStates` and reports transitions.
3. Latency tracking: a bounded sliding window of the last 50 readiness call durations per
   service, from which the p95 the fold consumes is computed.
4. Jitter: each service's poll is offset by a random fraction of the interval so eleven
   services do not stampede on the same tick.
5. `probeNow` support: the poller exposes a trigger so GW-003's `probeNow` runs a poll
   immediately without waiting for the tick.

## Non-goals

No HTTP endpoints (GW-005). No polling of Kafka clusters (M1: a service reports its own
per-cluster capability; the gateway never talks to Kafka, ADR-004 §3).

## Public Scala signatures to implement

```scala
package kui.gateway.application.capability

object ReadinessPoller:
  /** Starts one fiber per service under the supervisor. The returned `Trigger` forces an
    * immediate poll for one service (used by probeNow). */
  def resource[F[_]: Async](
      clients: ServiceClients[F],
      registry: CapabilityRegistry[F],
      interval: FiniteDuration,
      telemetry: Telemetry[F],
      logger: StructuredLogger[F]
  ): Resource[F, Trigger[F]]

trait Trigger[F[_]]:
  def probe(service: ServiceId): F[Unit]

object CircuitFeed:
  def resource[F[_]: Async](
      clients: ServiceClients[F],
      registry: CapabilityRegistry[F]
  ): Resource[F, Unit]

final class LatencyWindow private (size: Int):
  def record(d: FiniteDuration): LatencyWindow
  def p95: Option[FiniteDuration]
object LatencyWindow:
  def empty(size: Int = 50): LatencyWindow
```

**Polling rules**, decided here:

- A poll has its own timeout equal to `min(interval, 5s)`; a poll that times out is a failure,
  not a hang, and never overlaps with the next tick (the fiber skips a tick rather than
  running two polls concurrently).
- A poll failure is reported with the mapped `KuiError`'s reason code; the poller never
  crashes on an exception — it logs at WARN with a per-service rate limit of one line per
  minute and keeps polling.
- Polls stop when the resource is released; a released poller leaves no running fiber
  (asserted).

## Tests required

- `ReadinessPollerSuite` (concurrency, `TestControl` — deterministic virtual time, no sleeps):
  - `pollsEachServiceOncePerInterval`.
  - `aFailingPollReportsUnavailableWithinOneInterval` — the exit criterion's timing promise.
  - `recoveryIsReportedOnTheNextSuccessfulPoll`.
  - `aHangingServiceDoesNotBlockOtherServicesPolls` — the fault-isolation property at the
    poller level.
  - `pollsDoNotOverlap` — a service whose response takes longer than the interval is polled
    once, not twice.
  - `pollsAreJittered` — the first poll times of N services are not all identical.
  - `releasingTheResourceStopsEveryFiber` — assert no further calls reach the stub after
    release.
  - `pollFailuresAreRateLimitedInTheLog` — 60 consecutive failures produce one log line, not
    sixty.
  - `probeForcesAnImmediatePoll`.
- `LatencyWindowSuite` (unit + property): `p95` of a known distribution; the window never
  exceeds its size; `p95` is `None` before any sample.

## Observability

`kui.upstream.duration {upstream, outcome}` for each readiness call (reusing OBS-002's metric
rather than inventing a poller-specific one); one INFO log per state transition (the registry
emits it, not the poller — no duplicate logging).

## Degraded behavior

If a service's `/capabilities` succeeds but `/health/ready` fails, the service is
`Unavailable` — readiness wins, because a service that says it is not ready must not receive
traffic. If `/health/ready` succeeds but `/capabilities` fails, the state is
`Degraded(Unknown)` with the previous capability payload retained.
