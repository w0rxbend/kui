# GW-001 — Gateway skeleton, correlation id and error envelope

- **ID:** GW-001
- **Title:** Gateway skeleton, correlation id and error envelope
- **Milestone / Feature:** M0 / OT-005, KU-006
- **Owner role:** Chief Architect
- **Context / service:** `services/gateway`
- **Size:** M
- **Dependencies / blocked by:** HTTP-001, KERN-005

## Goal (user value)

The one process a browser ever talks to exists, answers `/api/v1`, stamps every request with a
correlation id an operator can grep for, and returns the same error envelope as every service.

## Scope

1. The four gateway modules (`application`, `contract`, `api`, `app`) with the minimum content
   that compiles and serves: `GET /api/v1/health/live`, `/health/ready`, and a 404 for
   everything else with the proper envelope.
2. Correlation id and edge header policy (ADR-040): the gateway **generates** the id and does
   **not** trust an inbound `X-Kui-Correlation-Id`, which is stripped along with every other
   header whose name begins `X-Kui-` — matched by prefix, not by an enumerated list, and
   removed before routing, authentication or logging. The generated id is echoed in the
   response header, the error envelope, every log line and every span, and is forwarded to
   upstreams.
3. Gateway configuration slice: `server`, `gateway`, `telemetry`.
4. `GatewayWiring.make` following ADR-010's shape, so AIO-001 reuses it.

## Non-goals

No routing to services (GW-006). No capability registry (GW-003). No static assets (GW-008).
No sessions (GW-009). No aggregations (M1+). **No domain logic, ever** (ADR-004 §3) — the
architecture test's rule A4 guards this.

## Observability

`service.name = gateway` on every entry. The gateway's own span is the parent of every
upstream span, so a single trace shows the browser request and every service call it caused.

## Degraded behavior

The gateway is Core tier (PLAN §15): if it is down, nothing works, and the browser shows the
single full-screen "cannot reach gateway" state (UI-011). Therefore the gateway must have no
mandatory upstream: it starts and serves the shell even when every service is unreachable.
Assert this in `GatewayWiringSuite` (AIO-001 extends it).

## Deviations

Recorded while implementing, as `docs/development/` asks. Each is a place where the
specification above could not be followed literally, with what was built instead.

### `EdgeHeaders.strip` is pure and takes the correlation id as a parameter

The specification gives `def strip(request: ServerRequest): (ServerRequest, CorrelationId)`.
That signature cannot be honest: generating a correlation id needs a source of randomness,
which is a side effect, so the function would have to reach for `SecureRandom` in the middle
of what looks like a pure transformation — and a function that invents its own answer cannot
be tested by writing down what it should return.

What was built instead splits the two jobs:

- `strip(request, correlationId)` is pure and total. It removes the headers and puts the given
  id in their place, so the rule can be property-tested over generated header casings.
- `stripInterceptor[F]` is the effectful half: it mints the id with
  `Correlation.newRandom[F]` and calls `strip`. It is what a server actually installs.

The security property is unchanged, and `GatewayApiSuite.neverReusesAnInboundOne` asserts it
end to end through a real server.

### A second interceptor puts the correlation id on the response

The specification does not say how the id reaches the response header. It cannot be an output
on each endpoint, because the responses that most need it — a 404 from the router, a 400 from
a decoder, a 500 from an exception — are produced before or instead of any endpoint's outputs.
`EdgeHeaders.echoInterceptor` reads the id back off the request and stamps it on whatever
response came out, so `EdgeHeaders.interceptors` is a list of two rather than one.

### `GatewayApi.routes` takes readiness checks and a capability document, not a logger

The specification gives `routes(logger, config)`. Neither parameter is used by anything the
route list actually builds: the health endpoints need the readiness checks and the capability
document, and the logger is used by `ErrorInterceptor`, which is an interceptor rather than a
route. Passing values a function does not use makes it impossible to tell, at a call site,
what the function depends on. The signature is `routes(readiness, capabilities)`, and the
logger is given to `ErrorInterceptor` in `GatewayWiring` where it is genuinely needed.

### `GatewayServer` also carries the interceptor chain

The specification's `GatewayServer` holds `routes` and `readiness`. The interceptor chain is
part of "the gateway, assembled but not listening" in exactly the same sense the routes are —
the edge header policy is not optional decoration — and AIO-001 needs it in order to serve the
gateway's routes inside another process. It is a third field rather than something the caller
reassembles.

### The gateway's identity lives in the application layer

`Gateway.Id` and `Gateway.ServiceName` are in `services/gateway/application` rather than in
`api`, and `GatewayApi` re-exports them. The service id is a capability key, a metric label and
a log field before it is anything to do with HTTP, so the layer that owns capability state owns
it. This also gives the `application` module a definition to hold in M0: Scala 3 deprecates
`package object`, so the specification's `package.scala` — a file with a doc comment and
nothing in it — does not compile under `-Werror`. The layer's rules are documented on
`Gateway` instead.

### `/api/v1/capabilities` is served now with a placeholder document

`HealthEndpoints.make` in `libs/http` returns liveness, readiness and capabilities as a triple,
and its three endpoints are private, so serving only two of them would mean editing `libs/http`
— which another lane is working in. All three are served; the capability document is
`ServiceCapabilities(gateway, Map.empty)` until GW-003 replaces it with the fold over every
upstream's readiness (ADR-039).

### CORS is wired here rather than being left to a later task

`Cors.interceptor` already exists in `libs/http` and `CorsConfig` is already part of
`GatewayConfig`, and the gateway is the only process a browser talks to, so it is the only
process where CORS means anything. Wiring it in the composition root now costs one line and
one test; leaving it out would have left a configured-but-ignored setting, which is worse than
an unimplemented one because it looks like it works.
