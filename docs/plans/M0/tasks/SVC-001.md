# SVC-001 — `services/cluster`: domain and application skeleton

- **ID:** SVC-001
- **Title:** `services/cluster`: domain and application skeleton
- **Milestone / Feature:** M0 / KU-006 (sample service)
- **Owner role:** Domain Architect (Cluster Registry context)
- **Size:** S
- **Dependencies / blocked by:** KERN-002

## Goal (user value)

The six-layer hexagonal skeleton every one of the eleven services will copy, built once, with
the dependency rules already enforced — so M1 adds Kafka behaviour into a structure that is
already correct rather than inventing one under time pressure.

## Scope

Two modules with the smallest possible content that still exercises the layering:

- `services/cluster/domain`: a `Ping` value object with an invariant (`message` non-empty,
  ≤ 128 chars) and one port, `ClockPort[F]`. Depends on `libs.kernel.jvm` and cats-core only.
- `services/cluster/application`: `PingUseCase[F]` returning `F[Either[KuiError, Ping]]`, and
  `CapabilityReportUseCase[F]` returning the `ServiceCapabilities` this service reports.

## Non-goals

**Everything M1 owns.** No `ClusterProfile`, `ClusterDescription`, `Broker`, `LogDir`,
`ClusterFeature`, `ClusterAdmin`, `ClusterConfigStore`, `ConnectivityProbe`. In particular no
metadata store: `ClusterConfigStore[F]` and its Kafka adapter over `__kui_config` (ADR-042,
feature-matrix row OT-004) arrive in M1 together with the rest of the cluster registry, and
M0's cluster service reads nothing but the static Ciris configuration. No
`infrastructure` module at all in M0 — there is no adapter to write, and creating an empty one
invites someone to fill it. No Kafka dependency of any kind.

If this task feels too small, that is the point: the value is the structure, not the code.

## Design references

PLAN §18 (module layout and the dependency rules), `ARCHITECTURE.md` §3, ADR-002 (`F[_]` with
the weakest bound, `IO` only in `app`), ADR-004 §4, `docs/domain/context-map.md` (Cluster
Registry context, so the package is `kui.cluster`).

## Public Scala signatures to implement

```scala
package kui.cluster.domain

final case class Ping private (message: String, at: Instant)
object Ping:
  def from(message: String, at: Instant): Either[DomainError, Ping]

trait ClockPort[F[_]]:
  def now: F[Instant]
```

```scala
package kui.cluster.application

trait PingUseCase[F[_]]:
  def ping(message: String): F[Either[KuiError, Ping]]

object PingUseCase:
  def make[F[_]: Monad](clock: ClockPort[F], logger: StructuredLogger[F]): PingUseCase[F]

trait CapabilityReportUseCase[F[_]]:
  /** In M0 this is a constant: the service is configured, has no cluster-scoped features and
    * reports `available`. M1 replaces the body with real capability probing. */
  def report: F[ServiceCapabilities]
```

## Library coordinates

`domain`: `org.typelevel::cats-core::2.13.0` only.
`application`: cats-core, `org.typelevel::cats-effect::3.7.1`, `co.fs2::fs2-core::3.13.0`,
`org.typelevel::log4cats-core::2.8.0`, `org.typelevel::otel4s-core::1.1.0`,
`libs/contracts-core` **is not** a dependency of `application` — the `ServiceCapabilities` DTO
crosses in `api`. **Correction to note in review:** because `CapabilityReportUseCase` returns a
DTO, either the DTO moves behind an application-owned type or the use case moves to `api`.
**Decision for this task:** `CapabilityReportUseCase` returns an application-owned
`CapabilityReport` case class, and `api` maps it to `ServiceCapabilities`. `application` never
depends on `contracts-core`.

```scala
final case class CapabilityReport(clusters: Map[ClusterId, ClusterCapabilityReport])
final case class ClusterCapabilityReport(configured: Boolean, features: Set[String], available: Boolean)
```

## Tests required

- `PingSuite` (unit + property): `from` rejects empty and over-long messages with a
  `DomainError`; accepts everything in between (property).
- `PingUseCaseSuite` (unit, `munit-cats-effect`): returns the message and the clock's instant;
  logs one structured entry with `operation = "kui.cluster.ping"`; a domain rejection surfaces
  as `Left` and is logged at WARN, not ERROR (a client mistake is not a server incident).

## Observability

Span `kui.cluster.ping`; log fields `service.name`, `correlation.id`, `operation`. No metrics
of its own — `kui.http.server.duration` from OBS-002 covers the endpoint.

## Degraded behavior

None — the use case has no upstream. This is deliberate: the sample service's *unavailability*
is produced by stopping the process (E2E-002), not by an internal failure mode.

## Deviations

1. **`checkArchitecture` rejected every possible test module, so the rules were corrected.**
   Rules A1, A2 and A3 are written against the module id, and Mill names a test module after the
   module it tests: `services.cluster.domain.test`. A domain test module necessarily depends on
   `services.cluster.domain`, on `libs.testkit.jvm` and on MUnit — none of which rule A1 allows a
   domain module — so `./mill checkArchitecture` failed with three violations the moment
   `services/cluster/domain/test` existed, and no domain module anywhere could ever have been
   tested. `ArchitectureRules.check` now skips A1, A2 and A3 for a module whose id ends in `.test`,
   with two new cases in `ArchitectureSuite` pinning both halves of that: a domain test module is
   legal, and a *test* module is still held to A4, A5 and A8, because those are about reaching
   somewhere nothing may reach and a suite that reaches there is telling you about the production
   code it tests.

2. **`CapabilityReportUseCase` carries no `ServiceId`.** The spec's `CapabilityReport` has only a
   `clusters` map, while the `ServiceCapabilities` DTO it maps to also names the service. The
   signature was left exactly as specified: `services/cluster/api` supplies the id from
   `ClusterService.Id` when it maps the report (SVC-003). The alternative — adding the field —
   would have made the use case restate a fact about the deployment that `app` already knows.

3. **`PingUseCase` logs `service.name` and `operation`, not `correlation.id`.** A use case has no
   request context and cannot invent a correlation id; the id is put on the line by the MDC bridge
   in `libs/observability` (OBS-001), which sees the request. The suite asserts the two fields the
   use case can honestly produce.

4. **`CapabilityReportUseCase.constant` takes the configured cluster ids.** The spec says only "in
   M0 this is a constant". A constant with no input could only ever answer with an empty map, which
   would report nothing rather than reporting the truth; taking the ids keeps the answer a function
   of this deployment's configuration, which is the one thing about it that is real in M0.
