# UI-013 — Reconcile the implemented style surface with the "Kafka UI v2" design import

- **ID:** UI-013
- **Title:** Reconcile the implemented style surface with the "Kafka UI v2" design import
- **Milestone / Feature:** post-M0 improvement (NX-007 is already `DONE` via UI-002)
- **Owner role:** Frontend Architect
- **Size:** M
- **Dependencies / blocked by:** UI-002, UI-003, UI-004, UI-009 (the gallery this task diffs
  against). **Blocked on an action only the project owner can take:** the Claude Design MCP
  authorization step (`/design-login` in Claude Code, PLAN §21 "Visual design reference"). Until
  that has been done the design's contents are unreadable and this task cannot start.
  **Nothing waits on this task and no milestone is gated by it.**

## Goal (user value)

KUI looks like the design the project owner actually drew, instead of like the reference product its
values were seeded from — and it costs one file to get there, because UI-002 was built so that
adopting a palette is a value edit rather than a component rewrite.

## Status and the decision this task does *not* reopen

UI-002 took the token decision on KUI's own authority after analysing Kafbat and Kouncil. The token
set is authoritative, `NX-007` is `DONE`, and B-001 is closed as decided-around. This task changes
**values**, not the vocabulary and not the architecture.

The rule the whole task hangs on, stated once so nobody has to infer it:

> **The design decides how it looks. The research decides what it does.**
> Styling and user-interface design come from the design project. All functionality —
> which screens exist, what data they show, which actions they offer, what happens when a
> call fails — continues to come from PLAN, `docs/FEATURE_MATRIX.md`, and the analysed
> behaviour of the two reference products in `research/`. Where the design implies a
> behaviour that contradicts the research, **the research wins and the difference is
> recorded**, never silently implemented and never silently dropped.

## Scope — the method, in order

Each step produces an artefact. Do not start a step before the previous one's artefact exists.

### 1. Import, and record what was imported

Pull **every** file the project exposes (`DesignSync list_files`, then `get_file` for each), not
only the artboard named in PLAN §21. Write `research/design/REFERENCE.md` containing:

- the project id and title exactly as the tool reports them;
- the project's revision marker — `updatedAt`, a version id, or whatever the tool gives — and the
  UTC timestamp of the import;
- the complete file list with each file's role (artboard, support script, asset);
- the reader's warning: **no design HTML, CSS or JS is copied into this repository** (PLAN §21).
  `support.js` is read to understand intended interaction; it is never bundled.

This file is what makes the next import a *delta* instead of a re-derivation.

### 2. Extract the design's tokens; map them onto KUI's names

Write `research/design/tokens.md`: the design's own values, under the design's own names, verbatim —
a transcript, not a proposal. Then produce the mapping table in the same file, one row per design
value:

| Design name | Design value | KUI token | Verdict |

**KUI's token names are the stable interface; the design supplies values.** Three verdicts and no
fourth:

- **maps** — an existing semantic token means the same thing. Take the value.
- **grows the set** — the design expresses something no existing name can carry. The set grows by
  exactly one token, with a written reason naming the component that needs it. Adding a token is a
  decision, so it is recorded like one; the ban on component-scoped tokens (UI-002, `docs/frontend/tokens.md`)
  still holds absolutely — a new token is semantic or it is not added.
- **dropped** — the design defines a value nothing in KUI uses. Record it and move on. A design
  defining more colours than KUI needs is not a reason to add tokens no component reads.

A KUI token the design does **not** define keeps its current KUI value and its `/* kui */`
provenance. A gap in the import is not a reason to lose a token components depend on.

### 3. Apply values, not structure

`frontend/ui-kernel/resources/css/10-tokens.css` is the **only** file where a colour, spacing or
type value changes. Update each adopted value's provenance comment to `/* design */`, keeping
`/* kui */` on everything the design did not define and on every value adjusted in step 4.

If a design value cannot be applied as a token change, that is **a finding about KUI's code, not
about the design**: some component holds a hard-coded value it should have read from a token. Fix
the hard-coded value — replace the literal with the token — and record the finding in the
Implementation Report, because it means UI-002 modelled that part of the set wrongly and the same
gap probably exists elsewhere.

### 4. Run the contrast test, and adjust rather than adopt

`ContrastSuite` reads the pair table in `docs/frontend/tokens.md` and checks every pair in both
themes (WCAG 2.2 AA: 4.5 for body text, 3.0 for large text, icons and control boundaries).

**An imported pair that fails is adjusted until it passes.** Accessibility outranks fidelity to a
mockup; this is a decision already taken, not a question to send back to the design owner.

Every adjustment is recorded in `docs/frontend/tokens.md` in a table that keeps the **original
design value beside the shipped one**:

| Token | Theme | Design value | Shipped value | Pair that failed | Ratio before → after |

The original value is not decoration. Without it, the next importer sees a mismatch between the
design and the stylesheet, assumes a transcription error, and "fixes" the accessibility adjustment
back out.

### 5. Component-by-component diff, sorted into three buckets

Walk the gallery at `/ui/gallery` (UI-009) against the design's artboards, one component at a time,
in both themes. Every difference lands in exactly one bucket:

- **A — a token can express it.** In scope. Fix it here.
- **B — the component needs a structural change** (different markup, a slot that does not exist, a
  different interaction shape). **Out of scope.** Becomes a new task against `ui-kernel`.
- **C — the design shows something that does not exist yet** (a component, a screen, a state KUI has
  not built). **Out of scope.** Becomes a new task, and if it implies a feature, a
  `docs/FEATURE_MATRIX.md` row is proposed — proposed, not added, since matrix rows come from
  research and product scope, not from a mockup.

The bucket list ships in `research/design/gaps.md` with every item assigned, including the ones that
became tasks and the task ids they became. An unassigned item is an unfinished task.

### 6. Never take behaviour from the design

If an artboard implies an action, a data field, an error state, an empty state, a default sort, a
refresh interval, or any other behaviour, check it against `research/kafbat/ui-analysis.md`,
`research/provectus/`, and `docs/FEATURE_MATRIX.md` **before** it influences anything. Then:

- design and research agree → nothing to do, it was already specified;
- design shows behaviour research does not cover → record it in `research/design/gaps.md` as a
  bucket C candidate; it is an input to a future scoping decision, not an implementation licence;
- design **contradicts** research → **research wins.** Record the contradiction in
  `research/design/gaps.md` with both positions written out, so the decision is visible and can be
  revisited deliberately by the product owner.

## Non-goals

Explicitly out of scope, so that a large import does not turn into a large rewrite:

- **No component redesign.** Bucket B and C items become tasks; they are not done here.
- **No new primitives**, no new screens, no new routes, no new pages.
- **No new tokens beyond the ones step 2 justifies individually**, however many the design defines.
- **No component-scoped tokens, ever** (UI-002's core constraint; there is no
  `--kui-button-primary-hover-background` and there never will be).
- **No behaviour change of any kind**, including copy that states a behaviour, default values,
  sort orders, polling intervals, and error text.
- **No feature-matrix rows added** from the design. Rows come from research and product scope.
- **No design HTML/CSS/JS copied into the repository**, and `support.js` is never bundled (PLAN §21).
- **No reopening of the Shoelace question.** ADR-024 decided against a third-party widget library;
  an import of colour values is not new evidence about component ownership. Reopening it needs a
  superseding ADR (PLAN §39).
- **No `.scala` change** except (a) `Tokens.scala` if step 2 justified a new token, and (b) a
  component whose hard-coded literal step 3 replaced with a token — both of which are reportable
  findings, not routine edits.

## Tests required

No new tests. The existing suites must stay green, which is the entire argument for having built
UI-002 as tokens-only:

- `ContrastSuite` — every documented pair, both themes, WCAG AA. Green **after** step 4's
  adjustments, never by relaxing a minimum or deleting a row.
- `ThemeSuite` — the three-state switch is untouched by a value import.
- `A11ySuite` and the per-component DOM suites — a value change cannot alter a role, an
  attribute or a keyboard behaviour. If one of these goes red, the change was structural and
  belongs in bucket B.
