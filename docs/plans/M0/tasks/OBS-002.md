# OBS-002 — `libs/observability`: Tapir interceptors and metric names

- **ID:** OBS-002
- **Title:** `libs/observability`: Tapir interceptors and metric names
- **Milestone / Feature:** M0 / MT-007
- **Owner role:** Infrastructure Lead
- **Context / service:** `libs/observability`
- **Size:** M
- **Dependencies / blocked by:** OBS-001, KERN-004

## Goal (user value)

Every endpoint in every service is traced and measured identically without a single line of
per-endpoint instrumentation, so no feature can ship unobservable.

## Scope

1. `KuiInterceptors.serverInterceptors(telemetry, logger)` returning the ordered Tapir
   interceptor list: correlation-id extraction/generation → tracing
   (`tapir-otel4s-tracing`) → metrics (`tapir-opentelemetry-metrics`) → request logging.
2. `MetricNames` — the constant list of PLAN §30 plus the `ARCHITECTURE.md` §13 additions, as
   typed constants so no metric is ever emitted with an ad-hoc name.
3. Span naming: `kui.<context>.<operation>` (PLAN §30), derived from the endpoint's declared
   operation id, with a documented fallback for endpoints that do not set one — and a test
   that fails when an endpoint has no operation id, so the fallback is never used silently.
4. The client-side counterpart used by `libs/http`'s `UpstreamClient`: a span per upstream
   call, `traceparent` injection, and the `kui.upstream.*` metrics.

## Non-goals

No custom exporters. No sampling policy beyond the SDK default (revisit in M8). No business
metrics (`kui.kafka.*` names are declared here but emitted by `libs/kafka` in M1).

## Design references

ADR-009, PLAN §30 (the metric name list), `ARCHITECTURE.md` §13 (the additions:
`kui.stream.events`, `kui.stream.active`, `kui.cursor.rejected`, `kui.principal.rejected`,
`kui.config.version`), ADR-003 (interceptors come from `libs/http` consumers).

## Tests required

- `MetricNamesSuite` (unit): names are unique, all start with `kui.`, and the list matches
  PLAN §30 + `ARCHITECTURE.md` §13 exactly (a literal expected list — this test is the
  contract between the plan and the code).
- `KuiInterceptorsSuite` (unit, otel4s testkit + Tapir stub server):
  - `everyRequestProducesOneServerSpanNamedByOperationId`.
  - `correlationIdIsGeneratedWhenAbsentAndEchoedWhenPresent`.
  - `correlationIdAppearsInTheSpanTheLogAndTheResponseHeader` — the three-way correlation
    that makes an incident traceable.
  - `httpServerDurationIsRecordedWithRouteAndStatus`, including for a 500.
  - `interceptorOrderIsStable` — asserts the exact order, because tracing must wrap metrics
    so failed requests still record duration.
  - `endpointWithoutAnOperationIdFailsTheSuite` — the guard described in the scope.

## Observability

Self-referential: this task defines it. One rule for reviewers — a metric or span attribute
whose value could be user data (a topic name is fine; a message payload is not) must be
justified in the task spec that introduces it.

## Degraded behavior

If the meter or tracer cannot be created, interceptors degrade to no-ops and log one WARN.
A telemetry failure never fails a request.

## Deviations

1. **`serverInterceptors` does not include the error handling, and takes no logger.** The error
   interceptor lives in `libs/http`, which depends on `libs/observability`, so this module cannot
   reach back for it without a dependency cycle. `serverInterceptors` returns the three
   instrumentation interceptors (correlation, tracing, metrics) and a composition root appends
   `ErrorInterceptor.interceptors(logger)`. That is also where request-error logging happens — one
   component logging each failure rather than two logging it twice.

2. **The correlation id is added to the request, not carried beside it.** The interceptor rewrites
   the incoming request to carry a valid `X-Kui-Correlation-Id`, so everything downstream — the
   tracer, the endpoint, and `libs/http`'s error interceptor, which knows nothing about this module
   — reads the same value from the same place. A caller's own id is kept when it passes validation
   and replaced otherwise, because the value goes back out in a response header.

3. **`tapir-opentelemetry-metrics` is not used.** It requires a *Java* `io.opentelemetry` `Meter`,
   which the otel4s abstraction deliberately hides, and its built-in metrics are named
   `http.server.request.duration` rather than `kui.http.server.duration`. Since PLAN §30's names had
   to be produced either way, the histogram is built directly from the otel4s `Meter` and installed
   through Tapir's own `MetricsRequestInterceptor`. `tapir-otel4s-tracing` *is* used, unchanged,
   because it takes an otel4s `Tracer` and only the span name needed overriding.

4. **`UpstreamInstrumentation.wrap` takes a `serviceName` as well as an `upstream`.** `service` is
   one of the three labels PLAN §30 puts on `kui.upstream.duration`, and there is nowhere else for
   it to come from.

5. **`traceparent` is written from the span context directly** rather than through a
   `TextMapPropagator`. The W3C format is four fixed fields; a two-line encoding is easier to read
   and to be sure of than plumbing a propagator through an sttp request builder.

6. **`UpstreamOutcome` is an enum, and `MetricNames.Attr.all` exists.** The outcome label is what an
   operator groups by when an upstream misbehaves, and "timeout" appearing as `timeout`, `Timeout`
   and `timed_out` in three modules would make that grouping useless. `Attr.all` lets
   `MetricNamesSuite` assert the label keys are unique too.

7. **The suites use Tapir's stub interpreter, not a bound port.** What is under test is the
   interceptor chain, and the stub runs exactly that chain; a real socket would add seconds per case
   and prove nothing extra. `libs/http`'s own suites cover the bound-port half.

8. **`endpointWithoutAnOperationIdFailsTheSuite` is `KuiInterceptors.missingOperationIds`,** a
   function each service calls in its own suite. The endpoints it has to check belong to the
   services, so a test in this module could only check this module's fixtures — which it does, plus
   the fallback's shape.
