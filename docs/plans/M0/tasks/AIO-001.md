# AIO-001 — `apps/allinone` composition root and in-process client

- **ID:** AIO-001
- **Title:** `apps/allinone` composition root and in-process service client
- **Milestone / Feature:** M0 / KU-005
- **Owner role:** Infrastructure Lead
- **Size:** L
- **Dependencies / blocked by:** SVC-004, GW-006, GW-009

## Goal (user value)

`./mill apps.allinone.run` and one container give a developer or a small installation the
entire product on one port — running the *same* gateway code path as the distributed
deployment, so what works locally works in production.

## Scope

1. `apps/allinone` depending on every service's `application`, `infrastructure` (none in M0)
   and `api` modules plus the gateway's, with one MacWire root, one `IO` runtime, one Netty
   listener and one otel4s provider (ADR-005).
2. `InProcessServiceClient` — the second `ServiceClient[F]` implementation: it interprets the
   **same** Tapir endpoints against the service's server logic in memory
   (`TapirInProcessClient(endpoints, serverLogic)` in `ARCHITECTURE.md` §11), so routing, the
   capability registry and aggregation are shared code and only the transport differs.
3. `PrincipalCodec.inProcess`: no signing; `kui.gateway.principalKeys` is ignored **with a
   warning** (ADR-005's exact requirement).
4. Services bind no listeners; only the gateway port is exposed.
5. Capability state for an in-process service is derived from its use-case results — an
   `InfrastructureError` becomes `Unavailable` exactly as a remote 5xx would — so the degraded
   UX is exercised locally without Docker.
6. One in-memory instance each of the session store and the capability registry. There is no
   config store in M0 at all: configuration is the static Ciris load (CFG-001), and the
   `ConfigStore[F]` port with its file and Kafka adapters is M1 (ADR-036, ADR-042, OT-004).
   When it arrives, all-in-one keeps working unchanged with the file adapter and with a single
   dev broker as the store cluster.

## Non-goals

No optional-dependency classpath profiles (they matter when Confluent and cloud SASL jars
exist — M3/M7). No clustering. No hot reload.

## Design references

ADR-005 (the entire decision), ADR-010 (`<Name>Wiring.make` reuse), `ARCHITECTURE.md` §11,
PLAN §14, feature matrix KU-005.

## Public Scala signatures to implement

```scala
package kui.allinone

object InProcessServiceClient:
  /** Interprets `endpoints` against `serverLogic` in memory. Same inputs, same outputs, same
    * error envelope as the HTTP path — it must be impossible for a response to differ. */
  def make[F[_]: Async](
      service: ServiceId,
      serverEndpoints: List[ServerEndpoint[Fs2Streams[F], F]],
      principals: PrincipalCodec[F]
  ): ServiceClient[F]

object AllInOneWiring:
  def resource[F[_]: Async](
      config: AllInOneConfig,
      telemetry: Telemetry[F]
  ): Resource[F, GatewayServer[F]]

object AllInOne extends IOApp
```

Wiring order (documented because it is easy to get wrong): telemetry → logger → config →
`PrincipalCodec.inProcess` → each service's `<Name>Wiring.make` → `ServiceClients` built from
`InProcessServiceClient`s → capability registry → readiness poller (which now polls in-process
health endpoints) → gateway routes → one Netty listener.

    endpoints keep answering.

## Observability

One otel4s provider, so a trace covers the gateway span and the in-process service span in one
tree — a developer can see the same trace shape they will see in production.
`service.name` remains distinct per service in logs (`gateway`, `cluster`), so log filtering
works the same in both shapes.

## Degraded behavior

The all-in-one process is a single failure domain by construction; fault isolation still holds
at the **code** level (a failing use case is a `KuiError`, the registry records it, the UI
degrades). Say this plainly in the docs so nobody claims all-in-one gives process isolation.

## Deviations

### 1. The in-process client is a transport, not a second client

The spec asks for `InProcessServiceClient` to "interpret the same Tapir endpoints against the
service's server logic". It does something slightly stronger, and the difference is worth stating
because it is what makes ADR-005's central claim checkable rather than merely intended.

`InProcessServiceClient` writes no request-building, no response-decoding and no error-mapping code
at all. It builds a *backend* — Tapir's stub interpreter over the service's own routes and
interceptors — and hands that to `SttpServiceClient.over`, which is the identical client the
distributed deployment runs. There is therefore literally one client implementation in the codebase
and two backends under it, so a response cannot differ between the two deployment shapes for any
reason other than the transport itself.

This required one small refactor in `services/gateway/api`: `SttpServiceClient`'s private `Impl`
now takes a base URL, a call backend, a stream backend and a circuit-event stream, instead of an
`UpstreamServiceConfig` and an `UpstreamClient`. `SttpServiceClient.resource` (the resilient HTTP
path) is unchanged in behaviour and signature; `SttpServiceClient.over` is the new, unwrapped
constructor. The in-process client deliberately gets no bulkhead, circuit breaker, retry policy or
call timeout, because there is no connection for any of them to protect — see the scaladoc on
`over` for the argument.

### 2. Service routes are not mounted on the gateway's listener

The spec says "services bind no listeners; only the gateway port is exposed", and one reading of
that is "mount every service's routes on the one Netty listener". They are not mounted at all: they
live only behind the in-process client and are reachable only through the gateway's proxied routes.

Two problems disappear as a result, and this is the answer to the "health path prefix strategy"
question the task raised:

- **No prefix strategy is needed.** All eleven eventual services serve the same unprefixed
  `/health/live`, `/health/ready` and `/capabilities`. Mounting them together would need a
  disambiguating prefix per service, invented here and applied forever; not mounting them means the
  paths never share a router and nothing has to be invented.
- **No interceptor merge is needed.** Each service keeps its own chain, running inside its own stub
  backend, exactly as it does behind its own socket. The question of what to do with several
  `KuiInterceptors` and `ErrorInterceptor` chains under one listener does not arise.

It is also the more faithful shape. `ARCHITECTURE.md` §14 says services must not be exposed outside
the cluster network; in this deployment they are not exposed at all, so a habit learned locally
(`curl :8081/health/live` is refused) stays correct in production.

**Consequence for the hoisting suggestion:** `PrincipalInterceptor` was *not* hoisted from
`services/cluster/api` into `libs/http`. The reason to hoist it was to install one copy under a
shared listener, and there is no shared listener. It should still be hoisted when the second
service arrives in M1 and genuinely needs the same code — that is the note SVC-003 already carries,
and this task did not make it more urgent.

### 3. Signature changes

- `InProcessServiceClient.make` takes a fourth parameter, `interceptors`. Without the service's own
  interceptor chain the in-process path would produce a different 401 for a missing principal and a
  different error envelope for an unhandled failure, which is precisely the divergence ADR-005
  forbids. The spec's three-parameter signature could not have satisfied its own acceptance
  criteria.
- `AllInOneWiring.resource` takes a `logger`, matching `GatewayWiring.make` and `ClusterWiring.make`.
  The warnings ADR-005 requires have to go somewhere, and standard error is not it.
- `GatewayWiring.make` grew a sibling, `GatewayWiring.over`, which takes the `ServiceClients` as a
  parameter. This is the seam that lets the all-in-one process reuse the gateway's composition root
  whole instead of copying it — ADR-010's requirement that "every service's `app` module must expose
  a `wire` function returning its server logic without starting a server" applies to the gateway
  too. `make` now delegates to `over` with the HTTP clients, so the distributed path is unchanged.
- Inside `GatewayWiring`, the service list handed to `CapabilitySignals` and to the merged OpenAPI
  document now comes from `clients.all.map(_.service)` rather than from `config.gateway.services`.
  Those two agree in the distributed shape and do not in the all-in-one shape, which configures no
  upstream URLs and still reaches every service.

### 4. `bindsExactlyOnePort` is asserted differently

Enumerating the process's listening sockets tests the operating system. What actually has to hold is
that the one listener serves the gateway's public API and nothing a service publishes for the
gateway's private use, so `AllInOneWiringSuite.bindsExactlyOnePortAndMountsNoServiceRouteOnIt`
asserts that no `/internal/**` route and no unprefixed `/health/live` appears in the served list.
The single-socket property itself was verified by hand against the running process, and the
transcript is in the implementation report.

### 5. An extra suite, and an invented endpoint

`cancellationPropagatesForStreamingEndpoints` lives in its own suite
(`InProcessStreamingSuite`) over a synthetic SSE endpoint declared in the test module
(`StreamingEndpoint.scala`), because no M0 contract publishes a streaming endpoint for it to use.
The property is worth checking now anyway: from M3 a browser tailing a topic holds one of these
open per tab, and an in-process transport that ignored cancellation would leak a fiber — and a
Kafka consumer — per closed tab, with no socket closing to make the leak visible. It passes: Tapir's
stub interpreter propagates cancellation to the producer.
