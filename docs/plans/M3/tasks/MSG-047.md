# MSG-047 — `checkArchitecture` rules A12 and A13, with their build tests

- **ID:** MSG-047
- **Title:** `checkArchitecture` rules A12 and A13
- **Milestone / Feature:** M3 / OT-005
- **Owner role:** Infrastructure Lead
- **Context / service:** `build.mill`, `build-tests`
- **Size:** S
- **Dependencies / blocked by:** MSG-012, MSG-015

## Goal (user value)

The two classpath rules this milestone introduces are enforced by the build rather than by review, so
that "the Confluent stack is optional" and "CEL runs in one module" stay true after the people who
wrote them have moved on.

## Scope

1. Rule **A12**: `libs.serdeConfluent`, `io.confluent.*`, Jackson and Guava are allowed only on
   `libs/serde-confluent`, a service's `infrastructure`, `libs/testkit` and an `app`.
2. Rule **A13**: `libs.filter`, `dev.cel.*` and re2j are allowed only on `libs/filter`, a service's
   `application`, `libs/testkit` and an `app`.
3. The extra assertion of DEVPLAN §6.7: no `services.message.*` module has an edge to
   `services.topic.*` (DEVPLAN §10 D2).
4. Build tests for each: a rule that has never been seen to fail is a rule nobody can trust, so each
   is proved to reject a deliberately violating edge, and the message is recorded.

## Non-goals

- No changes to A1–A10. If an existing rule is wrong, that is its own commit.
- No new module.

## Design references

ADR-041 (machine-enforced layering, and its argument: nobody sets out to break layering, they add one
edge for one type), M1's `CFGOP-003` (the shape of a rule and its build test), ADR-014 (why A12
exists), ADR-017 (why A13 exists), DEVPLAN §5.3 and §6.7; **ADR-041 Amendment 4**, which allocates the rule numbers and is the only place that may.

## Acceptance criteria

```
$ ./mill checkArchitecture
checkArchitecture: 12 rules, 0 violations
$ ./mill build-tests.test
```

The deliberate-violation check, run while writing the task and pasted into the Implementation Report
(M1's G6 condition 4, which applies to every new rule):

```
$ # add `libs.serdeConfluent` to services.message.application's moduleDeps
$ ./mill checkArchitecture
A12 violation: services.message.application depends on libs.serdeConfluent.
  The Confluent stack is an optional runtime dependency (ADR-014). Allowed on:
  libs.serdeConfluent, any service's infrastructure module, libs.testkit, any app module.
```

## Tests required

- `ArchitectureRulesM3Suite`
  - `a11RejectsAViolatingModuleEdge` and `a11RejectsAViolatingLibraryOnTheClasspath` — the second
    matters more: an edge is visible in a diff, a transitive library is not.
  - `a12RejectsAViolatingModuleEdge` and `a12RejectsATransitiveCelDependency`.
  - `theAllowListsAreExactlyTheOnesInTheArchitectureDocument` — parsed from `ARCHITECTURE.md`'s rule
    table, so a rule changed in the build without the document, or the reverse, fails here. This is
    DEVPLAN §6.7's own rule applied to itself.
  - `noMessageModuleDependsOnATopicModule`.
  - `everyRuleHasAMessageNamingTheAllowListAndTheAdr` — a violation message that says only "A12
    violation" makes the next person read the build file to find out what to do.

## Degraded behaviour

Not applicable. One design note: the rules fail the **build**, not a test, so they cannot be ignored
by a developer running one module's suite.
