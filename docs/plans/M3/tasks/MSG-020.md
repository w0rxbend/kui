# MSG-020 — `TailUseCase` with the 20 events/second throttle and no `done`

- **ID:** MSG-020
- **Title:** `TailUseCase`
- **Milestone / Feature:** M3 / MS-005, MS-013, KU-014
- **Owner role:** Domain Architect (message)
- **Context / service:** `services/message/application`
- **Size:** M
- **Dependencies / blocked by:** MSG-019

## Goal (user value)

Live mode: new records appear as they are written, a loud topic does not freeze the browser, and
pressing pause stops the consumer rather than just hiding the rows.

## Scope

1. `TailUseCase.run(request): Stream[F, BrowseEvent]` over `MessageBrowsePort.tail`, reusing
   `RecordMapping` and every pipeline stage of MSG-019.
2. The **event-rate** throttle: 20 events/second to the client by default, applied by dropping the
   oldest undelivered records rather than by slowing the consumer — a tail that applied
   backpressure to Kafka would lag further and further behind and stop being live.
3. `Consumed` events during quiet periods so the UI can show progress, and `Idle` from the port
   turned into nothing at all (the SSE layer's heartbeat covers silence — ADR-035).
4. No `Done`, ever.

## Non-goals

- No cursor. A tail has no page boundary.
- No byte throttle: that is `PollBudget.throttleBytesPerSecond` in the port (MSG-004).
- No client-side buffering policy (MSG-036 decides what the browser keeps on screen).

## Design references

ADR-035 ("tailing has no `done`; UI-facing tailing is rate-limited (default 20 events/s) in the
service"), `research/kafbat/api-analysis.md` Finding 5.1 (`TailingEmitter`: infinite loop, no `DONE`,
UI emission rate-limited to 20 msg/s), `research/kafka/admin-capabilities.md` §4 "Tailing".

## Public Scala signatures to implement

```scala
package kui.message.application.browse

trait TailUseCase[F[_]]:
  /** Endless. No `Done`. A failure is `Failed` and terminates; cancellation ends it silently. */
  def run(request: BrowseRequest): Stream[F, BrowseEvent]

/** Rate limiting that drops rather than blocks.
  *
  * The distinction matters and is the reason this is its own type: `Stream.metered` slows the
  * *upstream*, so a topic producing 5 000 records a second would make the consumer fall further
  * behind every second and the user would be watching a live view of ten minutes ago. Dropping
  * keeps the view live and honest, and the number dropped is reported.
  */
object EventThrottle:
  def dropping[F[_]: Temporal, A](rate: Int, per: FiniteDuration)
    : Pipe[F, A, (A, Long)]      // the Long is the cumulative count dropped before this element
```

## Tests required

- `TailUseCaseSuite` (`TestControl`, fake port)
  - `neverEmitsDone` (property over runs of arbitrary length).
  - `throttlesToTheConfiguredRate` — the snippet above, at 20/s and at a configured 5/s.
  - `dropsOldestRatherThanBlockingTheConsumer` — asserted by checking that the *newest* record is
    always delivered: a throttle that blocked would deliver the oldest and lag.
  - `reportsDroppedCountInConsumed` — the number reaches the UI, so "live view is dropping records"
    is visible rather than being a mystery gap in offsets.
  - `emitsConsumedDuringSilence` (`TestControl`, 60 seconds of nothing).
  - `aFailureIsFailedAndTerminal`.
  - `cancellationStopsThePortAndReleasesTheConsumer` — the application-level half of exit criterion 3.

## Observability

- `kui.message.tail.dropped` — counter, attributes `cluster`, `topic`. A steadily climbing value on a
  topic is the signal that a user is watching something too fast to watch, and it is the number
  MSG-036 shows them.
- `kui.message.tail.active` — from MSG-006, unchanged.

## Degraded behaviour

- A topic faster than the throttle: records are dropped, the count is shown, and offsets in the view
  are visibly non-contiguous. This is deliberate and stated in the UI; a live view that silently
  omitted records would be worse than one that says it is omitting them.
- The port failing mid-tail: `Failed`, the UI shows a toast and keeps the rows (DEVPLAN §10 D13).

## Cancellation and shutdown

The whole feature. `cancellationStopsThePortAndReleasesTheConsumer` cancels the fiber and asserts the
fake port's release flag within one poll interval, which is the assertion the roadmap's criterion
names.
