# MSG-045 — Benchmarks

- **ID:** MSG-045
- **Title:** Benchmarks
- **Milestone / Feature:** M3 / (exit criterion 7)
- **Owner role:** QA Engineer
- **Context / service:** `e2e`, `docs/benchmarks`
- **Size:** M
- **Dependencies / blocked by:** MSG-030, MSG-042

## Goal (user value)

Numbers an operator can plan with, and a baseline a later change can be compared against: how long a
page takes on small and large records, on a hundred partitions, under a tailing load, and against a
slow broker.

## Scope

1. Four benchmark shapes, run against the assembled stack with the fixtures of MSG-042:
   - small records (about 200 B), `limit = 100`, forward and backward;
   - large records (about 1 MiB), `limit = 20`;
   - 100 partitions, `limit = 500`, backward — the shape where the window walker's arithmetic shows;
   - tailing while a producer writes 5 000 records/second, measuring delivered, dropped and lag.
2. A fifth: a broker delayed past the per-call timeout (Toxiproxy), measuring **time to the `error`
   event** rather than throughput. That number is the one that decides whether the UI feels broken.
3. `docs/benchmarks/M3-messages.md`: the numbers, the machine, the commit, the command, and — for
   each — one sentence on what it means for an operator.

## Non-goals

- No CI gate. A benchmark that fails a build on a loaded runner is a benchmark that gets deleted.
  These run on demand and nightly, and the file records the result.
- No comparison against the reference products. Interesting, and not this milestone's job.
- No JMH. The measurements are end-to-end through HTTP; a microbenchmark of the walker would measure
  the wrong thing.

## Tests required

The benchmarks are the tests, and three of them carry an assertion so that a catastrophic regression
still fails something:

- `smallRecordPageCompletesUnderFiveSeconds` — a bound so loose that only a real regression trips it.
- `tailingDeliversAtTheConfiguredRateUnderLoad` — the delivered rate is within 20% of the configured
  20/s.
- `slowBrokerProducesAnErrorEventRatherThanHanging` — bounded by the per-call timeout plus five
  seconds. This one is the important assertion in the whole file: it is the difference between a UI
  that reports a problem and a UI that appears to have frozen.

## Observability

The benchmark run collects `kui.message.*` metrics and reports the cache hit rates and the stop
reasons alongside the timings, so a number can be explained rather than only recorded.

## Degraded behaviour

If a benchmark cannot run (no Docker, insufficient memory for the 1 M fixture), it is skipped with a
message naming what is missing, and the markdown file records the skip rather than silently keeping
last month's number.

## Cancellation and shutdown

The benchmark harness closes every stream it opens and mixes in MSG-044's `LeakDetector` — a
benchmark that leaks consumers would produce numbers that degrade run over run and blame the code.
