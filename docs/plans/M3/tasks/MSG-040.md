# MSG-040 — The Track page

- **ID:** MSG-040
- **Title:** The Track page
- **Milestone / Feature:** M3 / ET-001, ET-002, ET-003
- **Owner role:** Frontend Architect
- **Context / service:** `frontend/ui-messages`
- **Size:** L
- **Dependencies / blocked by:** MSG-036

## Goal (user value)

The second Kouncil differentiator: pick some topics, a time window and one condition, press Track,
and watch matching records arrive from all of them, sorted by time, in the same grid the messages
screen uses.

## Scope

1. The Track page at `/ui/clusters/:c/events/track`: a topic multi-select, a mandatory time range, a
   match builder (source, operator, value), an optional correlation key, and a limit.
2. Results in the message grid (MSG-036's rows), with a topic column added and the `group` value
   shown when a correlation key is set.
3. The streaming variant by default (ET-002), with `phase` progress naming the topic being scanned
   and `consumed` counts; the synchronous variant is not offered in the UI — one path, so there is
   one behaviour to test.
4. One-click entry from a message row: "track this header value" prefills source, operator, value,
   the topic list (the current topic plus recently visited ones) and the window (the record's
   timestamp plus or minus an hour).

## Non-goals

- No correlation *graph*, no join, no trace waterfall (M9).
- No saved track queries.
- No cross-cluster tracking.

## The topic multi-select

The topic list comes from the **topic service, through the gateway, from the browser**
(`GET /api/v1/clusters/{c}/topics`). That is not a service-to-service call and does not violate
DEVPLAN §10 D2: the message service still never calls the topic service. When the topic capability is
unavailable the select degrades to a free-text field with a comma-separated list, so tracking works
on a cluster whose topic screen is down.

## ADRs this task must obey

ADR-029, ADR-032 (the query is URL state, so a track result is a link), ADR-035 (the same envelope
and the same `error` handling), ADR-024, ADR-039 (the page's own capability is `message`, not
`topic` — a degraded topic service must not disable tracking).

  - `progressNamesTheTopicBeingScanned`.

## Observability

None in the browser.

## Degraded behaviour

- `done{reason:"budget"}` or `"limit"`: the result strip says **explicitly** that the scan was cut
  short, which topics were finished, and offers "narrow the window". This is the one screen where a
  partial answer is easy to misread as a complete one.
- Topic capability unavailable: free-text topic entry, everything else unchanged.
- Message capability unavailable: the fallback panel, like every other message screen.

## Cancellation and shutdown

`stop()` and unmount both close the `SseStream`, which aborts the fetch, which cancels the scan and
releases the consumer — the same chain as a browse, asserted here for this screen because a track
scan is the longest-running stream in the product and the most expensive one to leak.
