# GRP-028 — Consumer `app`: wiring, the profile-source bootstrap, readiness

- **ID:** GRP-028
- **Title:** Consumer `app`: wiring, the profile-source bootstrap, readiness
- **Milestone / Feature:** M4 / CG-001 … CG-006
- **Owner role:** Chief Architect
- **Context / module:** `services/consumer/app`
- **Size:** M
- **Dependencies / blocked by:** GRP-027, GRP-022, GRP-023

## Goal (user value)

`kui-consumer` starts, says when it is ready, and stops cleanly. And it starts in an order that
makes a failure visible as a failure rather than as a hang: M1's own risk register named a startup
that hangs as the worst shape a startup path can have, and this service's bootstrap has the same
hazard — it waits on another service before it can do anything.

## Scope

1. The Mill module `services.consumer.app`, its Docker image and its main class.
2. The composition root: macwire (ADR-010), one `Resource` chain, in the documented order.
3. Readiness: the service is ready when it is serving, and it reports `Degraded` — not "not ready" —
   while the cluster service is unreachable but profiles are cached.
4. The **config-to-composition assertion**: every field of `kui.consumer.*` that is parsed reaches a
   component that reads it, asserted field by field. M1's integration defect 1 was exactly this —
   `AllInOneConfig` parsed the cluster list and handed the service a default, so the configuration
   was validated and then discarded, and the log said "resolved 0 configured cluster(s)" against a
   file naming one.

## Non-goals

- **No new configuration keys.** GRP-036 owns the `kui.consumer.*` slice; this task consumes it.
- **No all-in-one changes.** GRP-039.
- **No business logic of any kind.** A composition root with a branch in it is a use case in
  disguise.

## The bootstrap order

```
1. Load and validate `kui.consumer.*` and the shared sections. All errors accumulated, one message.
2. Build observability (meter, tracer, logger) — so that step 3's failures are visible.
3. Build the HTTP client and the ClusterProfileSource (GRP-022). **Do not block on it.**
4. Build the GroupAdminRegistry, the snapshots, the use cases, the routes.
5. Start the HTTP server. **Readiness flips here**, not after the first snapshot.
6. In the background: the profile source's first fetch, then the snapshot loops.
```

Step 5 is the decision worth stating: **the service is ready before it has any data.** A service
that waits for the cluster service to answer before reporting ready is a service that never starts
when the cluster service is down, which turns one outage into two — the precise failure the whole
architecture exists to prevent. Instead it starts, serves, and reports its capability as
`Unavailable` with a reason until the first profile arrives. ADR-032's "Starting is not Unavailable"
applies to the first few seconds; after the configured `startupGrace` (default 30 s) with no profile,
the capability becomes `Unavailable` with the profile source's reason, which is a state an operator
can see and act on.

## Tests required

`ConsumerModuleSuite` (MUnit + `munit-cats-effect`):

1. `theGraphBuilds` — the `Resource` acquires and releases with no error.
2. `readinessFlipsBeforeTheFirstProfile` — **the decision above, asserted**: with a profile source
   that never answers, the server is serving and `/health/ready` is 200 within a second.
3. `theCapabilityIsUnavailableAfterTheGrace` — under `TestControl`, 31 s later, with the profile
   source's reason.
4. `theCapabilityIsAvailableOnceAProfileArrives`.
5. `theCapabilityIsDegradedWhenTheProfileIsStale`.
6. `releaseStopsTheServerThenTheLoopsThenTheClients` — asserted on an ordered log of release
   actions. **The named shutdown test**: a release order that closed the admin clients while a
   snapshot pass was running would log a stream of connection errors on every deploy.
7. `releaseCompletesWithinTwoSeconds` — a `Resource` that hangs on release is a pod that gets
   SIGKILLed, and the next start finds a group still holding its assignment.
8. `aStartupConfigurationErrorNamesEveryProblem` — three bad values, one message.

`ConfigReachesComponentsSuite`, one test, the field sweep:

`everyParsedConfigFieldReachesAComponent` — reflectively enumerate the fields of
`ConsumerServiceConfig`, and for each one assert it is read by the graph, by building the module
with a distinctive value per field and asserting that value is observable in the built components.
The test lists any field it could not account for **by name**, and fails. This is M1's defect 1 made
impossible; the same test shape lands in `apps.allinone.test` (GRP-037) for the composed graph.

## Observability

| Signal | Name | Attributes |
| --- | --- | --- |
| Gauge | `kui.service.ready` | `service.name = "kui-consumer"` |
| Counter | `kui.service.starts` | with the build info from `KuiBuildInfoModule` |

Startup logs, in order and at INFO: configuration resolved (with counts, never values); the cluster
service base URL; readiness; the first profile or the reason there is none. An operator reading the
first ten lines of the log must be able to tell whether the service is healthy.

## Degraded behavior

| Condition | Behaviour |
| --- | --- |
| Cluster service unreachable at start | Serving, ready, capability `Unavailable` after the grace with the reason; every screen shows the fallback panel with "the cluster service could not be reached" |
| Cluster service unreachable later | Cached profiles keep reads working; capability `Degraded`; mutations refused |
| Configuration invalid | Fails at startup with every error in one message; the process exits non-zero and the container restarts, which is the correct behaviour for a config error |
| No clusters configured | Serving, ready, an empty group list; not an error |

## Cancellation and shutdown

The release order is asserted by test 6 and the deadline by test 7. SIGTERM triggers the `Resource`
release; in-flight requests are drained by the Netty server's own shutdown, and the snapshot
supervisor is cancelled before the admin clients are closed. The Implementation Report states the
observed shutdown time.
