# GRP-004 — `GroupAdmin.describeGroups`: chunked, members, classic and KIP-848 assignments

- **ID:** GRP-004
- **Title:** `GroupAdmin.describeGroups`: chunked, members, classic and KIP-848 assignments
- **Milestone / Feature:** M4 / CG-001, CG-002
- **Owner role:** Principal Scala Engineer
- **Context / module:** `libs/kafka`
- **Size:** L
- **Dependencies / blocked by:** GRP-003

## Goal (user value)

Who is in a group, on which host, holding which partitions — for one group on a detail page, and
for four thousand groups on a list page without knocking the coordinators over. And the same answer
whether the group speaks the classic protocol or KIP-848's, which is the difference between a
member list that renders and one that is silently empty on a modern cluster.

## Scope

1. `describeGroups` over the raw `Admin`, chunked **50 ids per request, 4 requests in flight**,
   both read from `AdminTuning` rather than hard-coded.
2. Member mapping: `memberId`, `groupInstanceId`, `clientId`, `host`, `assignment()`, and — when the
   group's protocol is `Consumer` — `targetAssignment()`.
3. The **fabricated dead group**: `GroupIdNotFoundException` for an id is caught inside this method
   and replaced with `GroupDescription(id, isSimple = false, state = Dead, members = Nil, …)`.
   `KafkaErrorMapper` never sees it. This is the invariant GRP-002 documented; this is the task that
   makes it true.
4. Per-id partial results: `GroupAuthorizationException` for one id becomes
   `SkipReason.Forbidden(id)` and does not fail the batch.
5. `authorizedOperations` requested only when the caller asks, because it costs the broker an extra
   ACL evaluation per group and the list page does not use it.

## Non-goals

- **No committed offsets.** GRP-005. A describe that also fetched offsets would make the list page
  pay for the detail page's data.
- **No lag.** The domain's (GRP-011).
- **No retry loop of its own.** `AdminClientPool` owns timeouts and invalidation (M1, KAFKA-004).

## Public Scala signatures to implement

```scala
override def describeGroups(
    conn: ClusterConnection,
    ids: List[GroupId]
): F[Either[KuiError, PartialResult[GroupId, GroupDescription]]]

/** Requested separately because it costs the broker an ACL evaluation per group. The list page
  * calls the method above; the detail page calls this one. */
def describeGroupsWithOperations(
    conn: ClusterConnection,
    ids: List[GroupId]
): F[Either[KuiError, PartialResult[GroupId, GroupDescription]]]
```

Behaviour, precisely:

- `ids.isEmpty` returns `Right(PartialResult.empty)` and makes **no** Kafka call.
- Chunking: `AdminTuning.describeChunkSize` (default 50) and `AdminTuning.describeParallelism`
  (default 4). A failed chunk does not fail the batch: its ids become `skipped` with the mapped
  reason.
- `GroupIdNotFoundException` for a whole chunk is not possible (the exception is per id in the
  result map); per id it becomes the fabricated dead description and increments
  `kui.kafka.group.fabricated_dead`.
- The member's `targetAssignment` is `Some` only when the group's protocol is `Consumer` **and** the
  target differs from the current assignment. Equal targets collapse to `None` so that
  "mid-rebalance" is one comparison rather than a set difference at every call site.
- Results are merged in **id order as given**, not in completion order, so two runs produce the same
  list and a golden document is stable.

## Tests required

`DescribeGroupsSuite` (MUnit + Testcontainers + a stubbed `Admin` where the case cannot be produced
on a real broker):

1. `describesTheSeededStableGroup` — one member, its host, its client id, its partitions.
2. `anUnknownGroupIsDeadWithNoMembers` — **the invariant**, against a real broker. Asserted on the
   value, not on the absence of an exception.
3. `theFabricatedDeadGroupIsCounted`.
4. `aClassicGroupReportsItsAssignment`.
5. `aConsumerProtocolGroupReportsItsAssignment` — the KIP-848 half of R-10, on a 4.x broker.
6. `targetAssignmentIsNoneWhenItEqualsTheAssignment`.
7. `targetAssignmentIsPresentDuringARebalance` — forced by adding a second consumer.
8. `emptyIdsMakesNoCall` — asserted on a stub's call log, because "cheap" is a property worth a
   test.
9. `chunkingUsesTheTunedSizeAndParallelism` — 120 ids against a stub: three chunks, at most four in
   flight.
10. `aFailedChunkDoesNotFailTheBatch`.
11. `aForbiddenGroupIsSkippedNotFatal` — the managed-cluster case: KUI has `DESCRIBE` on some groups
    and not others, and the list still renders.

## Degraded behavior

| Condition | Behaviour |
| --- | --- |
| The group does not exist | `Dead`, no members. Read paths render an empty group page; write paths refuse, because they checked existence with `listGroups` first (GRP-019) |
| No `DESCRIBE` on the group | The id is `skipped` with `SkipReason.Forbidden`; the list row renders with `Section.Forbidden` for its member and lag cells |
| Coordinator moving | `coordinator = None`; the detail page shows `—` for the coordinator, not an error |
| Broker without KIP-848 | `targetAssignment = None` everywhere; no capability is claimed and no call is made |

## Cancellation and shutdown

The chunked batch runs under the caller's fiber. Cancelling it must cancel the in-flight chunks and
release the `Admin` back to the pool. `DescribeGroupsSuite` includes a cancellation assertion:
cancel a describe of 500 ids mid-flight, assert the pool reports no leased client afterwards.
