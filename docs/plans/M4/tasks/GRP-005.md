# GRP-005 — `GroupAdmin.committedOffsets`: multi-group, `requireStable`, absent commits

- **ID:** GRP-005
- **Title:** `GroupAdmin.committedOffsets`: multi-group, `requireStable`, absent commits
- **Milestone / Feature:** M4 / CG-002, CG-004, CG-005
- **Owner role:** Principal Scala Engineer
- **Context / module:** `libs/kafka`
- **Size:** M
- **Dependencies / blocked by:** GRP-004

## Goal (user value)

Where each group actually is. Half of the lag calculation, and the whole of "what will this reset
change" — and the half where a `null` quietly becoming a `0` turns "this group has never consumed
this partition" into "this group is fully caught up".

## Scope

1. `committedOffsets` over `listConsumerGroupOffsets`, with the multi-group form (KIP-709, Kafka
   3.3) when `GroupFeature.MultiGroupOffsets` is present and one call per group when it is not.
2. Chunking at 50 groups per request, from `AdminTuning`.
3. `requireStable` passed through (Kafka 2.6+); silently dropped with a counted, logged note on
   older brokers, because the alternative is refusing a call the operator can still get a useful
   answer from.
4. **A `null` `OffsetAndMetadata` is an absence, not a zero.** The partition is omitted from the
   result list entirely; the domain turns that absence into `LagAnomaly.NoCommit` (GRP-011).
5. `committedAt` read from `OffsetAndMetadata` where the broker supplies it, `None` otherwise.

## Non-goals

- **No end offsets.** GRP-006. Fetching both here would couple the two and make the "same snapshot
  pass" rule of DEVPLAN §10 D7 impossible to state.
- **No lag.** GRP-011.
- **No filtering by topic.** The caller passes the partition set it wants; `None` means all. The
  "offsets for this topic" query of CG-005 is the caller building that set.

## Design references

- `research/kafka/admin-capabilities.md` §3, row "Committed offsets": the call shape, the minimum
  versions (0.10.1, multi-group 3.3, `requireStable` 2.6), **`null` for partitions without a commit
  (`:562-571`)**, `null` partition list meaning all, and the 50-group chunk (`:541-572`).
- DEVPLAN §10 D6 — the absence rule and why it matters.
- ADR-030 — both version-gated behaviours are capability-probed (GRP-008), never version-checked.

## Public Scala signatures to implement

```scala
override def committedOffsets(
    conn: ClusterConnection,
    groups: List[GroupId],
    partitions: Option[Set[TopicPartition]],
    requireStable: Boolean
): F[Either[KuiError, PartialResult[GroupId, List[CommittedOffset]]]]

// in AdminConversions
/** `null` is an absence and returns `None`. There is no default and no `orElse(0)`. */
private[kafka] def toCommittedOffset(
    tp: org.apache.kafka.common.TopicPartition,
    raw: org.apache.kafka.clients.consumer.OffsetAndMetadata | Null
): Option[CommittedOffset]
```

Behaviour, precisely:

- `groups.isEmpty` returns `Right(PartialResult.empty)` with no Kafka call.
- With `MultiGroupOffsets` present: one request per chunk of 50 groups, each group carrying its own
  `ListConsumerGroupOffsetsSpec`. Without it: one request per group, at
  `AdminTuning.describeParallelism` in flight, and the caller cannot tell the difference.
- A group that errors becomes a `skipped` entry; the rest of the chunk is returned.
- Results per group are sorted by `(topic, partition)` before returning, so a golden document is
  stable and a diff between two runs means something changed.

## Tests required

`CommittedOffsetsSuite` (MUnit + Testcontainers):

1. `readsTheSeededGroupsCommits`.
2. `aPartitionWithNoCommitIsAbsentNotZero` — **the headline assertion**. The fixture's
   partial-commit group has committed on partition 0 and never on partition 1; the result has one
   entry, and the test asserts `result.exists(_.partition.partition == 1) == false` rather than
   asserting a zero is absent, so a future `getOrElse` cannot pass it.
3. `aGroupThatNeverCommittedReturnsAnEmptyList` — empty, and `Right`.
4. `partitionsNoneMeansEveryCommittedPartition`.
5. `partitionsSomeNarrowsTheResult`.
6. `requireStableIsPassedThrough` — asserted against a stub's captured options.
7. `multiGroupAndSingleGroupPathsAgree` — the same three groups fetched both ways produce equal
   results. The two-code-paths-one-answer test, as in GRP-003.
8. `chunkingAtFiftyGroups` — 130 groups against a stub: three requests.
9. `aFailedGroupIsSkippedNotFatal`.

## Degraded behavior

| Condition | Behaviour |
| --- | --- |
| Broker below 3.3 | One request per group; slower, identical answer |
| Broker below 2.6 | `requireStable` dropped, counted, logged once per cluster per process |
| No `DESCRIBE` on a group | Skipped with `SkipReason.Forbidden`; the row renders `Section.Forbidden` |
| Group does not exist | An empty offset list. Existence is not this method's question (GRP-002's invariant) |
