# GRP-023 — `AuditSink` log adapter, and the consumer service's observability surface

- **ID:** GRP-023
- **Title:** `AuditSink` log adapter, and the consumer service's observability surface
- **Milestone / Feature:** M4 / CG-003, CG-004, CG-005 (safety); forward to AD-001 (M5)
- **Owner role:** Infrastructure Lead with the Domain Architect (consumer)
- **Context / module:** `services/consumer/infrastructure`
- **Size:** M
- **Dependencies / blocked by:** GRP-021, GRP-018

## Goal (user value)

Every offset reset, every deleted group and every deleted offset leaves a line an operator can find
six weeks later, in the same structured JSON the rest of KUI logs, on a milestone that has no audit
topic and no identity service yet. When M5 adds the `__kui_audit` sink, it plugs into the port this
task fills and nothing above it changes.

## Scope

1. `LoggingAuditSink`: the M4 sink. One structured line per `MutationRecord`, at INFO, on a
   dedicated logger name so it can be routed to its own file or index.
2. The record's JSON rendering, with an explicit codec (ADR-007) and a **committed golden file**, so
   that M5's Kafka sink writes the same document and a change to the shape is a visible diff.
3. The consumer service's observability wiring: the meter and tracer names, the `service.name`
   resource attribute, and the log MDC keys every line in this service carries.
4. `docs/operations/consumer-groups.md`, created: what the audit line looks like, how to route it,
   what the describe-all cost is on a large cluster, and what an operator does about each degraded
   state.

## Non-goals

- **No `__kui_audit` topic.** M5. This task must not create a topic, and must not add a Kafka
  producer to the service.
- **No principal.** M6. `principal` is the literal `"anonymous"`, and the operations document says so
  in the paragraph where an operator would otherwise assume it means something.
- **No retention policy, no rotation.** That is logback's, configured in `deployment/`.
- **No audit viewer.** M6.

## Design references

- ADR-023 (audit and masking) — the record's field set and the sink abstraction.
- ADR-008 — log4cats and the logstash JSON encoder already in `services/*/app`.
- ADR-007 — explicit Circe codecs, no automatic derivation, with a golden file.
- DEVPLAN §10 D2 — this is substitute (c), and it ships with the operation.
- `docs/ROADMAP.md` M5 — "Every mutation produces an audit record (console sink and Kafka topic sink
  tested)". M4 ships and tests the console sink; M5 adds the topic one.

## Public Scala signatures to implement

```scala
package kui.consumer.infrastructure

import io.circe.{Encoder, Json}
import kui.consumer.domain.{AuditSink, MutationRecord}

object MutationRecordCodec:
  /** Explicit, field by field. The golden file is the contract M5's Kafka sink must also satisfy,
    * and a diff on it is the review that catches a field being renamed. */
  given Encoder[MutationRecord]

object LoggingAuditSink:
  /** Logger name `kui.audit`, deliberately distinct from the service's own logger so that an
    * operator can route the audit trail to its own file, index or retention policy without
    * separating it from the rest of the service's logging by grepping. */
  val LoggerName: String = "kui.audit"

  def make[F[_]: Sync](logger: StructuredLogger[F]): AuditSink[F]
```

The line's shape, which the golden file fixes:

```json
{
  "at": "2026-09-04T11:02:31.447Z",
  "cluster": "quickstart-local",
  "operation": "consumer.group.offsets.reset",
  "resource": "orders-consumer",
  "principal": "anonymous",
  "before": { "orders-0": 1200, "orders-1": 1198 },
  "after":  { "orders-0": 0,    "orders-1": 0    },
  "outcome": { "kind": "SUCCEEDED" },
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736"
}
```

`outcome` is an object with a `kind` discriminator rather than a bare string, because `Refused` and
`Failed` carry a code and a reason and a shape that changes between variants is a shape nobody can
parse. `before` and `after` are keyed `"<topic>-<partition>"`, the same rendering `TopicPartition`
already uses in log MDC keys.

## Acceptance criteria

```
$ ./mill services.consumer.infrastructure.test
Test run kui.consumer.infrastructure.LoggingAuditSinkSuite finished: 0 failed, 0 ignored, 9 total
SUCCESS
```

And, from a running quickstart with a reset performed (GRP-039 provides the environment):

```
$ docker logs kui-consumer 2>&1 | grep '"logger":"kui.audit"' | tail -1 | jq -r .operation
consumer.group.offsets.reset
```

That command belongs in `docs/operations/consumer-groups.md`, because it is the answer to "how do I
see what KUI changed" and an operator should not have to derive it.

## Tests required

`LoggingAuditSinkSuite` (MUnit + a capturing logger):

1. `encodesToTheGoldenFile` — a fixed record, byte-for-byte against
   `test/resources/golden/mutation-record.json`. **The seam with M5's sink**, recorded now.
2. `everyOutcomeVariantEncodes` — four variants, each with its discriminator.
3. `theLoggerNameIsKuiAudit`.
4. `aRecordIsOneLine` — no multi-line JSON; a log aggregator splits on newlines.
5. `noSecretAppearsInTheEncodedRecord` — a record built from a profile carrying a distinctive token
   does not contain it. Asserted on the string, not on the case class.
6. `aFailingLoggerDoesNotThrow` — the sink's contract is that it never fails its caller.
7. `beforeAndAfterAreKeyedByTopicDashPartition`.
8. `anEmptyBeforeIsRenderedAsAnEmptyObjectNotOmitted` — an absent field and an empty one mean
   different things to whoever reads the trail, and the delete case has an empty one.
9. `theTraceIdIsPresentWhenOneIsInScope` — and absent, not null, when none is.

## Observability

This task is where the service's signal names are fixed. Every metric in M4 carries
`service.name = "kui-consumer"` and, where it is about one cluster, `cluster.id`.

| Signal | Name | Notes |
| --- | --- | --- |
| Counter | `kui.audit.records` | `operation`, `outcome` — the count that must equal `kui.consumer.mutations` |
| Counter | `kui.audit.write_failures` | `sink = "log"` |

The equality between `kui.audit.records` and `kui.consumer.mutations` is asserted in
`MutationGuardSuite` (GRP-018 test 7) rather than merely hoped for: a mutation without a record is
the failure the whole substitute exists to prevent.

## Degraded behavior

| Condition | Behaviour |
| --- | --- |
| The log sink fails | Counted, logged at ERROR through the *service* logger (not the audit one, which is what failed), and the mutation proceeds |
| Log volume | One line per mutation. There is no rate limit and none is needed: a human performs these |
| M5 arrives | `AuditSink[F]` gains a second implementation and a `combineAll`; nothing above the port changes, and this task's golden file becomes the Kafka sink's too |
