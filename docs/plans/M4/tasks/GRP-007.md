# GRP-007 — `GroupAdmin` mutations: alter offsets, delete offsets, delete groups

- **ID:** GRP-007
- **Title:** `GroupAdmin` mutations: alter offsets, delete offsets, delete groups
- **Milestone / Feature:** M4 / CG-003, CG-004, CG-005
- **Owner role:** Principal Scala Engineer
- **Context / module:** `libs/kafka`
- **Size:** L
- **Dependencies / blocked by:** GRP-005, GRP-006

## Goal (user value)

The three calls that change something. They are deliberately dumb: they do not decide whether the
operation is allowed, they do not clamp, they do not plan. They perform exactly what they are given
and they translate every documented refusal into a typed error an operator can read. Everything that
decides lives in the domain (GRP-012) and the use case (GRP-019), where it can be tested without a
broker.

## Scope

1. `alterOffsets` over `alterConsumerGroupOffsets(groupId, Map(tp -> OffsetAndMetadata))`.
2. `deleteOffsets` over `deleteConsumerGroupOffsets(groupId, Set[tp])`.
3. `deleteGroups` over `deleteConsumerGroups(ids)`, per-id partial results.
4. **The refusal mapping**, which is the substance of this task. Every exception
   `research/kafka/admin-capabilities.md` §3 names for these three rows is mapped to a `KuiError`
   with a message that says what to do, and the mapping is proved total by a property test.
5. `KafkaErrorMapper` extended with the group-specific cases, in the existing file, so there is one
   mapper and not a second one beside it.

## Non-goals

- **No precondition check.** The state and member check of DEVPLAN §10 D4 is the use case's, checked
  twice, and the broker's rejection mapped here is the third line of defence — not the first.
- **No clamping, no timestamp resolution, no shift arithmetic.** All pure, all in GRP-012.
- **No audit record.** GRP-018. This module has no idea who is calling.
- **No `removeMembersFromConsumerGroup`.**

## Public Scala signatures to implement

The three `GroupAdmin` methods declared in GRP-002, plus:

```scala
// in KafkaErrorMapper
/** The group-operation refusals, each mapped to a code an operator can act on.
  *
  * `GroupNotEmpty` is separate from `InvalidState` because it is the one refusal with an obvious
  * remedy — stop the consumers — and a UI that can switch on it can say so.
  */
private[kafka] def mapGroupError(t: Throwable): Option[KuiError]
```

| Kafka exception | `ErrorCode` | Message an operator reads |
| --- | --- | --- |
| `GroupNotEmptyException`, `UnknownMemberIdException`, `IllegalGenerationException` | `GroupNotEmpty` | "The group still has active members. Stop its consumers, wait for the group to become empty, and try again." |
| `GroupIdNotFoundException` | `GroupNotFound` | "No consumer group with this id exists on this cluster." — reachable here and **only** here; on the describe path it is normalised away (GRP-002) |
| `GroupSubscribedToTopicException` | `InvalidState` | "A member of this group is still subscribed to that topic, so its committed offsets cannot be deleted." |
| `GroupAuthorizationException` | `Forbidden` | "KUI is not permitted to change this consumer group." |
| `TopicAuthorizationException` | `Forbidden` | "KUI is not permitted to read one of the topics this group consumes." |
| `UnknownTopicOrPartitionException` | `TopicNotFound` | "The topic or partition no longer exists." |
| `InvalidOffsetException`, `OffsetOutOfRangeException` | `Validation` | "The offset is outside the range this partition holds." |
| everything else | the existing `KafkaErrorMapper` behaviour, unchanged | |

Behaviour, precisely:

- `alterOffsets` with an empty map returns `Right(())` and makes no call.
- `deleteGroups` returns a `PartialResult`: deleting three groups where one is not empty succeeds for
  two and skips one. It does **not** fail the batch, because a bulk delete that rolls back nothing
  and reports nothing is worse than one that reports what it did.
- Each method logs at INFO **before** the call, with `cluster.id`, `group.id`, the operation and the
  partition count — never the offsets themselves at INFO, which are the audit record's job — and at
  INFO again after, with the outcome. A mutation that is attempted and then times out must leave a
  trace that it was attempted.

## Tests required

`GroupMutationSuite` (MUnit + Testcontainers against the GRP-036 fixture):

1. `altersOffsetsOnAnEmptyGroup` — write, then read back with `committedOffsets` and compare.
2. `alteringAnActiveGroupIsGroupNotEmpty` — the fixture's stable group: `ErrorCode.GroupNotEmpty`,
   and the offsets are unchanged when read back. **The third line of defence, proved to exist.**
3. `alterWithAnEmptyMapMakesNoCall`.
4. `deletesOffsetsForOneTopic` — the other topic's offsets survive.
5. `deletingOffsetsForASubscribedTopicIsInvalidState`.
6. `deletesAnEmptyGroup` — and `listGroups` no longer shows it.
7. `deletingANonEmptyGroupIsGroupNotEmpty`.
8. `deleteGroupsIsPartial` — three ids, one active: two deleted, one skipped, `Right`.
9. `deletingAnUnknownGroupIsGroupNotFound` — the one path where the exception is not normalised.
10. `mapGroupErrorIsTotalOverTheDocumentedClasses` — a property over the exception list in
    `admin-capabilities.md` §3, in the mapper's own suite.
11. `noGroupErrorMapsToFiveHundred` — every mapped code has a 4xx status. A refusal the operator
    caused is not a server error, and a 500 in the browser console reads as a KUI bug.
12. `theAttemptIsLoggedBeforeTheCall` — asserted on a fake logger. A mutation that hangs must still
    have left a record that it started.

## Degraded behavior

| Condition | Behaviour |
| --- | --- |
| The group became active between the caller's check and this call | `GroupNotEmpty`; nothing was written. This is why the mapping exists rather than the caller's check being trusted |
| Partial delete | Per-id `PartialResult`; the API reports which succeeded and which did not, and the UI lists both |
| Broker below 2.5 / 2.4 / 1.1 | `Unsupported`, gated by `GroupFeature` (GRP-008) so the button is disabled rather than the call failing |

## Cancellation and shutdown

A mutation cancelled mid-flight may or may not have been applied by the broker — Kafka gives no
guarantee. The method therefore **must not** swallow cancellation: it releases the client and
rethrows, and the caller (GRP-019) logs an `outcome = Unknown` audit record. That is the honest
shape, and `GroupMutationSuite` asserts the audit-visible consequence in GRP-019's suite rather than
pretending the write is atomic.
