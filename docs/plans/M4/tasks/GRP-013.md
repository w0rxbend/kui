# GRP-013 — `GroupSnapshots`: the per-cluster 30 s snapshot under a supervisor

- **ID:** GRP-013
- **Title:** `GroupSnapshots`: the per-cluster 30 s snapshot under a supervisor
- **Milestone / Feature:** M4 / CG-001, CG-002, CG-006
- **Owner role:** Domain Architect (Consumer Group Management context)
- **Context / module:** `services/consumer/application`
- **Size:** L
- **Dependencies / blocked by:** GRP-012

## Goal (user value)

The group list is instant and a slow coordinator never appears on the request path. One background
loop per cluster lists the groups, describes them in bounded chunks, fetches their committed offsets
and the end offsets those need — **in one pass, so lag is never a fresh commit against a stale end
offset** — and every read is a memory read with an honest "updated 12 s ago" beside it.

## Scope

1. The Mill module `services.consumer.application` and its test module.
2. `GroupSnapshot`: the per-cluster value — summaries, the raw pieces the detail page reuses, the
   pace samples, `GroupCompleteness`, the coordinator skips, and a monotonically increasing
   `version` the lag delta is cut from (GRP-016).
3. `GroupSnapshots[F]`: one `SnapshotCell` per cluster plus one longer-interval capability cell,
   created and destroyed as the cluster set changes, all under one `Supervisor`.
4. The refresh function: the ordered call sequence and its partial-failure policy.
5. `ARCHITECTURE.md` §9's `consumer` row confirmed or corrected.

## Non-goals

- **No paging, sorting or searching.** GRP-014 reads this.
- **No per-partition detail for every group.** The snapshot holds committed offsets and end offsets
  for the partitions each group has commits or assignments on — the union DEVPLAN §10 D7 names —
  and nothing else. It does not describe topics and it does not hold messages.
- **No second cache.** `SnapshotCell` from `libs/cache`, as `ClusterSnapshots` uses it.
- **No cross-service call.** Nothing here talks to `services/topic`.

## Design references

- ADR-027, ADR-016, and `ARCHITECTURE.md` §9's `consumer` row: *"per-cluster group snapshot:
  listings, descriptions, committed offsets; end offsets for committed partitions via its own
  `listOffsets` (no cross-service call); every 30 s (50 groups × 4 parallel); invalidated after
  reset/delete of a group; lag on the list page ≤ 30 s old; group detail page computes live"*. That
  row is this task's contract, and it also settles two things a worker would otherwise ask: the
  cadence, and the fact that the detail page does **not** read this cell for its offsets.
- `services/cluster/application/src/kui/cluster/application/ClusterSnapshots.scala` — M1's
  implementation of exactly this shape, including its deviations (the cell owns its supervisor, a
  failed load raises `SnapshotLoadFailure`, `requestRefresh` is on the component that owns the
  fibers). **Read it before writing this one**; the differences must be deliberate.
- DEVPLAN §10 D7 (one pass), D12 (pace), risk R-4 (describe-all cost), risk R-8 (cancellation).
- `research/kafka/admin-capabilities.md` §3 rows "Describe groups" and "Lag".

## Public Scala signatures to implement

```scala
package kui.consumer.application

import java.time.Instant
import scala.concurrent.duration.FiniteDuration

import cats.effect.kernel.{Resource, Temporal}
import kui.cache.{Snapshot, SnapshotCell}
import kui.consumer.domain.*
import kui.kernel.{ClusterId, GroupId, TopicPartition, Offset}

/** One cluster's consumer groups, as of one pass.
  *
  * `version` increases by one per successful pass and is what the lag delta's token carries
  * (GRP-016). It is a counter and not a timestamp for the reason DEVPLAN §10 D9 gives: a clock is
  * not a version.
  */
final case class GroupSnapshot(
    version: Long,
    summaries: Vector[GroupSummary],
    /** Kept so the detail page can render immediately and then refine, and so the topic tab can be
      * answered without describing again. */
    groups: Map[GroupId, ConsumerGroup],
    committed: Map[GroupId, Map[TopicPartition, Offset]],
    endOffsets: Map[TopicPartition, Offset],
    paceSamples: Map[GroupId, LagMath.PaceSample],
    /** Coordinators that did not answer this pass; the list page says the listing is incomplete. */
    incompleteCoordinators: Set[kui.kernel.BrokerId],
    features: kui.kafka.admin.GroupFeatures | Unit,   // see "Deviations" below
    takenAt: Instant
):
  def index: kui.kernel.NameIndex[GroupId]   // built once per pass, used by search (GRP-014)

trait GroupSnapshots[F[_]]:
  def of(cluster: ClusterId): F[Option[SnapshotCell[F, GroupSnapshot]]]
  def all: F[List[(ClusterId, SnapshotCell[F, GroupSnapshot])]]
  /** Fire-and-forget on the component's own supervisor: returns once the refresh has been
    * *requested*. A forced refresh that awaited completion would block for the admin timeout
    * against a dead cluster, and the button would hang. */
  def requestRefresh(cluster: ClusterId): F[Unit]
  /** Called by the mutation use cases: after a reset or a delete the snapshot is wrong, and the
    * next read must not serve it. Invalidates and requests a refresh in one step. */
  def invalidate(cluster: ClusterId, reason: String): F[Unit]

object GroupSnapshots:
  def resource[F[_]: Temporal](
      profiles: ClusterProfileSource[F],
      admin: ClusterId => GroupAdminPort[F],
      refreshInterval: FiniteDuration,       // default 30 s
      metrics: kui.cache.CacheMetrics[F],
      logger: org.typelevel.log4cats.StructuredLogger[F]
  ): Resource[F, GroupSnapshots[F]]

  /** The refresh function, exposed so it is testable without a cell around it. */
  def refreshOne[F[_]: Temporal](
      port: GroupAdminPort[F],
      previous: Option[GroupSnapshot],
      logger: org.typelevel.log4cats.StructuredLogger[F]
  ): F[Either[KuiError, GroupSnapshot]]
```

### The refresh pass — the exact call sequence

```
1. list(states = all)                      — REQUIRED. Left ⇒ the whole pass fails.
                                             A partial listing (one coordinator down) is a Right
                                             whose skipped brokers land in incompleteCoordinators.
2. describe(ids)                            — chunked 50 × 4. Per-id failures are skips, not a
                                             failure: a group KUI may not describe still appears
                                             as a row with a Forbidden section.
3. committedOffsets(ids, partitions = None) — chunked 50. Absent commits stay absent (GRP-005).
4. endOffsets(union of committed and assigned partitions)
                                            — leaderless partitions filtered at the port; each one
                                              lands in the group's GroupCompleteness.excluded.
5. LagMath over 3 and 4, then LagMath.pace against `previous`.
```

**Only step 1 is required.** A cluster that lists its groups has something to render; a list with
member counts and no lag is far more useful than an unavailable panel, and it is exactly what a
cluster where KUI lacks `DESCRIBE` on groups looks like. Steps 2–4 each degrade to absent data
recorded in `GroupCompleteness`, and each failure logs **once at DEBUG** with its error code — not
WARN, because on a partly-authorized cluster these fire every thirty seconds forever and a warning
that always fires trains an operator to filter the log.

Steps 3 and 4 cannot run in parallel with each other: step 4's partition set is derived from step
3's result. Steps 2 and 3 can and do.

## Tests required

`GroupSnapshotsSuite` (MUnit + `munit-cats-effect` + `TestControl` + `FakeGroupAdminPort`):

1. `refreshNeedsOnlyTheListing` — a port that lists and fails everything else yields a `Right`
   snapshot with rows, no lag and `completeness.membersKnown = false`.
2. `refreshFailsWhenTheListingFails` — the error passes through unchanged.
3. `endOffsetsAreFetchedForTheUnionOfCommittedAndAssigned` — asserted on the fake's captured
   partition set. A union that missed assigned-but-uncommitted partitions would make a brand-new
   consumer show no lag.
4. `lagUsesOffsetsFromOneAndTheSamePass` — **the D7 assertion**: the fake returns a different end
   offset on every call; the computed lag matches the value from the same pass, not a later one.
5. `theLoopRefreshesOnTheInterval` — 90 s of virtual time, exactly three passes. The count, not "at
   least one", so a duplicated loop fails.
6. `aFailedRefreshServesThePreviousSnapshot` — `Stale`, value intact.
7. `takenAtDoesNotMoveOnAFailedRefresh`.
8. `versionIncreasesOnlyOnSuccess`.
9. `optionalFailuresLogAtDebugNotWarn` — asserted on a fake logger, for the reason the scope section
   gives.
10. `aFailureTransitionLogsWarnOnce` — two consecutive failures, one WARN.
11. `aClusterRemovedFromTheProfileSourceHasItsLoopCancelled` — remove it, advance 120 s, assert the
    fake's call log stopped growing. **The leak test**: a cell whose cluster was deleted but whose
    fiber survives keeps authenticating to a cluster the operator removed.
12. `aChangedProfileReplacesTheCell` — rotate the password; the next pass used the new profile.
13. `invalidateForcesTheNextReadToBeFresh` — after a simulated reset, a read does not serve the
    pre-mutation snapshot.
14. `paceIsNoneOnTheFirstPassAndComputedOnTheSecond`.

`ConsumerRig` and `ConsumerRig.eventually` live in this test module: the profile source publishes on
a background fiber, so a fixed sleep is a race that passes on a quiet machine. Every suite in lanes
B and D polls for the condition it cares about. (M1 learned this as three flaky suites; see
`STATUS.md`.)

## Degraded behavior

| Condition | Behaviour |
| --- | --- |
| Cluster unreachable, was reachable | Previous snapshot served as `Stale` with `takenAt` and the reason; rows grey with a timestamp |
| Cluster unreachable, never was | No value; the read yields `Unavailable(reason, since)` and the page shows the fallback with the reason |
| One coordinator down | `incompleteCoordinators` non-empty; the list renders and says "one coordinator did not answer; some groups may be missing" |
| KUI cannot describe groups | Rows with ids and states only; member and lag cells are `Section.Forbidden` |
| 4 000 groups | One pass takes as long as 80 chunks at 4 in flight; the gauge says so and `docs/operations/consumer-groups.md` states the cost |

## Cancellation and shutdown

The `Resource` releases in this order: stop accepting refresh requests, cancel the supervisor
(cancelling every in-flight pass), then release the cells. Test 11 is the named cancellation test
required by DEVPLAN §11.10, and the suite additionally asserts that releasing the whole `Resource`
while a pass is mid-flight completes within one second and leaves no fiber running.
