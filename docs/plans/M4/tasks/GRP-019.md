# GRP-019 — `OffsetResetUseCase`: plan, confirm, precondition, apply

- **ID:** GRP-019
- **Title:** `OffsetResetUseCase`: plan, confirm, precondition, apply
- **Milestone / Feature:** M4 / CG-004
- **Owner role:** Domain Architect (Consumer Group Management context)
- **Context / module:** `services/consumer/application`
- **Size:** L
- **Dependencies / blocked by:** GRP-018, GRP-015

## Goal (user value)

The operation the milestone exists for, performed safely. An operator picks a mode; the server
resolves it against the cluster's live offsets and shows exactly what will be written, per partition,
with every clamp and every surprise spelled out; the operator confirms *that*, not a form; and the
server re-checks that the group is still stopped before it writes a single offset.

## Scope

1. `OffsetResetUseCase[F]`: `plan(...)` and `apply(...)`.
2. **The existence check**: `GroupAdminPort.exists`, which lists, because describing a missing group
   returns a fabricated dead one (GRP-002's invariant, DEVPLAN §10 D5). A group that does not exist
   is `KUI-GROUP-NOT-FOUND`, not an empty plan.
3. **The precondition**, checked twice (DEVPLAN §10 D4): at plan time and again immediately before
   the write, both halves — state and member list.
4. **The plan token**: HMAC-SHA256 over the canonical plan using the existing cursor key (ADR-026),
   five-minute expiry, bound to cluster, group and the exact resolved offsets.
5. The apply path, entirely inside `MutationGuard`.

## Non-goals

- **No planning arithmetic.** `ResetPlanner` (GRP-012) is pure and already tested; this task
  gathers its inputs and mints its token.
- **No raw-spec apply endpoint.** DEVPLAN §10 D3: `apply` takes a token and nothing else. There is
  deliberately no "skip the plan" path, not even for tests — the tests plan first, like a user.
- **No delete.** GRP-020.
- **No RBAC check.** M6.

## Design references

- DEVPLAN §10 D3 (the two-phase model and the token), D4 (both halves, twice), D5 (existence by
  listing, and the new error code), D8 (leaderless refuses), D10 (six modes).
- DC-D6 and `research/kafka/admin-capabilities.md` §3, row "Reset offsets" —
  `OffsetsResetService.java:66-92` confirming existence by listing, and `:93-122` for clamping and
  `failOnUnknownLeader`.
- ADR-026 — the cursor key and the `base64url(payload).base64url(HMAC)` shape the token reuses, so
  no new secret and no new configuration is introduced.
- GRP-018's `MutationGuard`, which this use case may not bypass.

## Public Scala signatures to implement

```scala
package kui.consumer.application

import java.time.Instant
import kui.consumer.domain.{ResetPlan, ResetScope, ResetSpec}
import kui.kernel.{ClusterId, GroupId}

/** A plan plus the token that authorises applying exactly it.
  *
  * The token is an HMAC over the canonical rendering of `(cluster, group, scope, sorted proposed
  * offsets, expiry)`. It authorises nothing an operator could not do anyway; what it prevents is
  * applying a *different* set of offsets from the ones that were shown — whether because the client
  * edited them, because the cluster moved, or because a second tab planned something else.
  */
final case class PlannedReset(plan: ResetPlan, token: String, expiresAt: Instant)

trait OffsetResetUseCase[F[_]]:

  /** Resolve the spec against live offsets and return what would be written.
    *
    * Order: existence (by listing) → profile and read-only → precondition → offset window →
    * `ResetPlanner.plan` → token. A read-only cluster is refused **here** as well as at apply, so
    * the wizard never renders a plan the operator cannot apply. */
  def plan(
      cluster: ClusterId,
      group: GroupId,
      scope: ResetScope,
      spec: ResetSpec
  ): F[Either[KuiError, PlannedReset]]

  /** Apply exactly the plan the token names.
    *
    * Order: verify the token (signature, expiry, cluster, group) → **re-check the precondition** →
    * `MutationGuard.guard(ResetOffsets)` → `applyOffsets` → invalidate the snapshot. Nothing between
    * the re-check and the write but the write. */
  def apply(cluster: ClusterId, group: GroupId, token: String): F[Either[KuiError, ResetPlan]]

object OffsetResetUseCase:
  val Operation: String = "kui.consumer.reset"
  val TokenTtl: FiniteDuration = 5.minutes

  def make[F[_]: Temporal](
      admin: ClusterId => GroupAdminPort[F],
      guard: MutationGuard[F],
      tokens: PlanToken[F],
      logger: StructuredLogger[F]
  ): OffsetResetUseCase[F]

trait PlanToken[F[_]]:
  def mint(plan: ResetPlan, expiresAt: Instant): F[String]
  /** `Left(Validation)` for a bad signature, an expired token, or one minted for another cluster or
    * group. The three are **not** distinguished in the message: telling a caller which part of a
    * forged token was wrong is an oracle. The log line distinguishes them; the response does not. */
  def verify(cluster: ClusterId, group: GroupId, token: String): F[Either[KuiError, ResetPlan]]
```

The refusal table, which is the substance of the task:

| Condition | Code | Checked in |
| --- | --- | --- |
| Cluster not configured | `KUI-CLUSTER-NOT-FOUND` | both |
| Group does not exist (by listing) | `KUI-GROUP-NOT-FOUND` | both |
| Cluster is read-only | `KUI-READ-ONLY` | plan, and again in the guard |
| Group state not `Empty`/`Dead`, or members present | `KUI-INVALID-STATE` | plan **and** immediately before the write |
| Any partition in scope is leaderless | `KUI-INVALID-STATE`, naming the partitions | plan |
| Token invalid, expired, or for another group | `KUI-VALIDATION` | apply |
| The broker refuses anyway | `KUI-GROUP-NOT-EMPTY` from the mapper | the port |

## Tests required

`OffsetResetUseCaseSuite`:

1. `planResolvesEarliest` … 4. `planResolvesShiftByAndDuration` — one per mode pair, asserting the
   proposed offsets and the warnings.
2. `planChecksExistenceByListingNotByDescribing` — **the invariant's consequence**: asserted on the
   fake's call log, `describe` was not used to decide existence.
3. `anUnknownGroupIsGroupNotFound` — not an empty plan, not a fabricated dead group.
4. `anActiveGroupIsRefusedAtPlanTime` — both halves: a `Stable` group, and an `Empty` group with a
   member.
5. `aReadOnlyClusterIsRefusedAtPlanTime`.
6. `aLeaderlessPartitionIsRefusedNamingIt`.
7. `applyRequiresAToken` — there is no other entry point; asserted by the type, and by a test that
   the trait has no `apply(spec)` overload.
8. `applyRejectsATamperedToken` — flip one byte of the payload: `KUI-VALIDATION`, and nothing was
   written.
9. `applyRejectsAnExpiredToken` — under `TestControl`, six minutes later.
10. `applyRejectsATokenForAnotherGroup`.
11. `applyRechecksThePrecondition` — **the R-3 assertion**: the group is empty at plan time and the
    fake makes it `Stable` before apply; `KUI-INVALID-STATE`, and `applyOffsets` was never called.
12. `applyWritesExactlyThePlannedOffsets` — asserted on the fake's captured map, compared to the
    plan, key for key.
13. `applyGoesThroughTheGuard` — the recording sink has exactly one record.
14. `applyInvalidatesTheSnapshot`.
15. `applyOfANoOpPlanSucceeds`.
16. `aBrokerRefusalIsMappedNotWrapped` — `KUI-GROUP-NOT-EMPTY` reaches the caller intact.
17. `cancellationDuringApplyIsAuditedAsUnknown`.
18. `theSameSpecPlannedTwiceGivesTheSameToken` — determinism, which `ResetPlanner` test 18 already
    requires and this asserts end to end.

`PlanTokenSuite`: round-trip; a wrong key fails; an expired token fails; a token for another cluster
fails; the failure message is identical for all three (the oracle rule); the token is URL-safe; the
token does not contain the group id in plaintext — it is an HMAC, not an encoding; a property that
`verify(mint(p)) == Right(p)` for arbitrary plans.

Logging: the plan at INFO with the partition count and the mode; the apply at INFO **before** the
write with the full offset map, because a reset that hangs must have left a record of what it was
about to do, and offsets are not secrets.

## Degraded behavior

| Condition | Behaviour |
| --- | --- |
| Cluster unreachable at plan time | `KUI-UPSTREAM-UNAVAILABLE`; the wizard says the cluster cannot be reached and offers retry |
| Cluster becomes unreachable between plan and apply | The apply fails, is audited as `Failed`, and the wizard keeps the plan so the operator can retry it — the token has five minutes |
| The group starts consuming between plan and apply | Refused at the re-check; the wizard says so in the group's own words ("the group has members again") |
| Partial write | Not possible: `alterConsumerGroupOffsets` is one request. A failure leaves the group where it was |
| Cancelled mid-write | Audited as `Unknown`; the response is a 499-shaped cancellation and the log says the outcome is not known |
