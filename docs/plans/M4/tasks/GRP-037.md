# GRP-037 — The seam suites: recorded documents on all three boundaries

- **ID:** GRP-037
- **Title:** The seam suites: recorded documents on all three boundaries
- **Milestone / Feature:** M4 / all rows
- **Owner role:** QA Engineer
- **Context / modules:** `services/consumer/api`, `services/gateway/api`, `apps/allinone`, `frontend/ui-consumers`
- **Size:** L
- **Dependencies / blocked by:** GRP-029, GRP-031

## Goal (user value)

The defects that reach users are not in components; they are between them. The M0 review found that
nothing tested the seams and that is where the worst defects lived. M1's integration then found two
more of exactly that kind — a config section parsed and silently discarded, and a browser decoding a
document nobody sends — **both of which passed every unit test on both sides**. This task builds the
suites that make those two classes impossible in M4, on all three boundaries at once.

## Scope

M4 has three process boundaries and one in-process boundary that behaves like one. Each gets a suite
built on the same principle: **the producing side records the artefact, and the consuming side is
tested against the recording** — never against a hand-written sample that agrees with nobody.

| Seam | Producer | Consumer | Suite |
| --- | --- | --- | --- |
| S1 | consumer service | gateway | `ConsumerServiceGatewaySeamSuite` (`services.gateway.api.test`) |
| S2 | gateway | browser | `GatewayBrowserSeamSuite` (`services.consumer.api.test` + `frontend.uiConsumers.test`) |
| S3 | consumer service | cluster service (profile) | `ProfileSeamSuite` (`services.consumer.infrastructure.test`) |
| S4 | configuration | composition root | `ConfigReachesComponentsSuite` (`apps.allinone.test`) |

## Scope, concretely

1. **Recorded documents.** A `record` mode on each producer suite writes the exact response bytes to
   `test/resources/recorded/<seam>/<name>.json`, committed. A `verify` mode — the default in CI —
   regenerates and diffs. A change to a response is a visible diff in a review.
2. **Consumer-side decoding of those exact files**, in the consuming module's own suite, including
   the browser's, which runs under Node against the same committed bytes.
3. **The field sweep** for S4, over the whole all-in-one graph rather than one service's.
4. A `docs/development/seams.md` page explaining the pattern, because the next milestone should copy
   it rather than reinvent it.

## Non-goals

- **No new production code.** This task adds tests and recordings, and may add a test-only recording
  helper to `libs/testkit`.
- **No end-to-end browser test.** GRP-038. A seam suite is fast and runs on every commit; an E2E is
  not and does not.
- **No golden files for things that are not documents.** A recorded metric or a recorded log line
  would be a brittle assertion on an implementation detail.

## Tests required

**S1 — `ConsumerServiceGatewaySeamSuite`** (11): every consumer-service response the gateway parses
is recorded from the real `ConsumerRoutes` through the Tapir stub interpreter, and the gateway's own
client decodes those exact bytes. Nine documents plus two error envelopes. Each test asserts the
decoded value, not merely that decoding did not throw — **because M1's defect 2 decoded successfully
into zero rows**.

**S2 — `GatewayBrowserSeamSuite` (9) and `BrowserSeamSuite` (9)**: the same nine documents as the
gateway emits them, recorded on the JVM side and decoded on the JS side by
`ConsumerClients`' own response types. The two suites have the same nine names, and a helper asserts
that the two lists are equal — so a document added on one side and not the other fails rather than
being quietly untested.

Three assertions in `BrowserSeamSuite` are the specific shape of M1's defect:

- `everyRecordedDocumentDecodesToANonEmptyValue` — a page decoding to zero rows from a non-empty
  recording fails.
- `aDocumentWithTheWrongTopLevelFieldFailsToDecode` — `{"items": …}` where `{"groups": …}` is
  expected must be a decode error, not a default.
- `noResponseTypeInTheBrowserIsDeclaredLocally` — GRP-030's assertion, repeated here because this is
  the suite a reviewer will read.

**S3 — `ProfileSeamSuite`** (6): the cluster service's real `ProfileRoutes` produce the profile
document; the consumer service's `HttpClusterProfileSource` decodes it; the 304 path; the SSE change
event's exact bytes; the `Cache-Control: no-store` header; and the assertion that the decoded profile
yields a `ClusterConnection` a Kafka client can actually be built from — which is precondition P1's
whole question, answered by a test rather than by a document.

**S4 — `ConfigReachesComponentsSuite`** (1): the field sweep, over the composed all-in-one graph.
Build the graph with a distinctive value in **every** field of every service section, and assert each
value is observable in the built components. Any field that cannot be accounted for is listed **by
name** in the failure. This is M1's defect 1, made impossible for the whole application rather than
one service.
