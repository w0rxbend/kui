# GRP-039 — All-in-one, Compose and quickstart: the consumer service and seeded groups

- **ID:** GRP-039
- **Title:** All-in-one, Compose and quickstart: the consumer service and seeded groups
- **Milestone / Feature:** M4 / CG-001 … CG-006
- **Owner role:** Infrastructure Lead
- **Context / modules:** `apps/allinone`, `deployment/{docker,compose,quickstart}`
- **Size:** M
- **Dependencies / blocked by:** GRP-028, GRP-029

## Goal (user value)

A developer runs one command and sees the Consumers screen with real groups on it — one stable, one
empty, one behind — and can reset one of them. Without seeded groups the screen is an empty table and
nobody can tell whether the milestone works.

## Scope

1. `apps/allinone`: the consumer service's graph in the composition root, with the profile source
   wired **in process** rather than over HTTP.
2. `deployment/docker`: the `kui-consumer` image.
3. `deployment/compose`: the service, its configuration, its health check and its dependency order.
4. `deployment/quickstart`: three consumer groups seeded against the existing eight topics and 111
   messages, in the three states the screen needs to be worth looking at.
5. `README.md`'s quickstart section gains the Consumers screen.

## Non-goals

- **No second Kafka.** The quickstart's broker is the one that already exists.
- **No new seeded topics.** The quickstart already seeds eight; the groups consume those.
- **No Helm chart.** M8.
- **No production defaults changed.** The Compose configuration is a development configuration and
  says so.

## The in-process profile source

In the all-in-one, `kui-consumer` and `kui-cluster` are the same process. Making the consumer half
call the cluster half over HTTP would add a socket, a timeout and a failure mode to a deployment that
has none of those, and it would make the all-in-one's start-up depend on its own listener being up.

**Decision: the all-in-one wires `ClusterProfileSource` directly to the cluster service's
application-layer registry**, behind the same port. `clusterServiceBaseUrl` is unused there and the
configuration documents that. The distributed deployment uses the HTTP client (GRP-022).

This is ADR-005's whole premise — one process, the same graph, no network between the halves — and
it is why the port exists. The all-in-one's integration suite runs the *same* assertions against the
in-process source that `ProfileSeamSuite` runs against the HTTP one, so the two implementations
cannot diverge.

**`AllInOneConfig` is the file M1's defect 1 was in.** It carried three sections and handed the
cluster service a default, so the configured cluster list was parsed, validated and discarded, and
the log said "resolved 0 configured cluster(s)" against a file naming one. Adding a fourth section
to that file is exactly the moment to repeat it. GRP-037's `ConfigReachesComponentsSuite` is the
guard, and this task must not land before it passes.

## The seeded groups

| Group | State | What it makes visible |
| --- | --- | --- |
| `orders-processor` | `STABLE`, one live member on `orders` | the normal case: members, assignments, a small moving lag |
| `analytics-batch` | `EMPTY`, committed at roughly half of `orders` | the resettable case, and a large visible lag |
| `legacy-reader` | `EMPTY`, committed on one partition of `payments` only | the honest-`—` case: partitions with no committed offset, an excluded-partition footnote, and a total that is not the whole story |

`orders-processor` runs as a long-lived container so the group stays `STABLE`; the other two are
seeded by a script that commits and exits, which is what leaves them `EMPTY` rather than `DEAD`.

## Tests required

`ConsumerAllInOneSuite` (MUnit + `munit-cats-effect` + Testcontainers, the whole graph against one
broker):

1. `theGraphBootsWithBothServices`.
2. `theConsumerServiceResolvesProfilesInProcess` — asserted on the wiring: no HTTP client is
   constructed for it.
3. `theInProcessSourceSatisfiesTheSameContract` — the assertions from `ProfileSeamSuite`, run against
   this implementation. **The two-implementations-one-contract rule**, without which the all-in-one
   silently diverges.
4. `groupsAreListedThroughTheGateway` — a full request path, in one process.
5. `theConsumerConfigSectionReachesTheConsumerComponents` — the field sweep, narrowed to this
   section, so this suite fails fast if `AllInOneConfig` drops it (defect 1).
6. `readinessFlipsWithoutWaitingForTheFirstSnapshot`.
7. `shutdownReleasesBothServicesInOrder` — the named shutdown test for the composed graph.

Plus, in `deployment`: a shell-level check in `quickstart.sh` that the three groups exist before it
prints its URL, with a clear message if seeding failed. A quickstart that prints a URL to a page
with nothing on it is worse than one that says what went wrong.

## Observability

The Compose stack's `kui-consumer` gets the same log configuration, OTLP exporter and Prometheus
endpoint as the other services. Its health check is `/health/ready`, with a start period long enough
to cover the startup grace (GRP-028) so that a slow cluster service does not restart-loop the
consumer container.

## Degraded behavior

| Condition | Behaviour |
| --- | --- |
| `kui-cluster` not yet up when `kui-consumer` starts | The consumer starts, serves, reports its capability as unavailable with the reason, and recovers when the cluster service appears. **No `depends_on: condition: service_healthy` ordering is used for this**, because a service that cannot start without another is the coupling this architecture exists to avoid, and Compose ordering would hide it |
| Seeding fails | `quickstart.sh` says which group failed and exits non-zero, rather than opening a browser onto an empty screen |
| `orders-processor` container dies | The group becomes `EMPTY` within the session timeout; the screen shows it, which is correct behaviour and worth seeing |
