# GRP-017 — `GroupsForTopicUseCase`: the topic page's Consumers tab data

- **ID:** GRP-017
- **Title:** `GroupsForTopicUseCase`: the topic page's Consumers tab data
- **Milestone / Feature:** M4 / TP-015, KU-011
- **Owner role:** Domain Architect (Consumer Group Management context)
- **Context / module:** `services/consumer/application`
- **Size:** M
- **Dependencies / blocked by:** GRP-013

## Goal (user value)

Standing on a topic page and seeing who reads it, how many consumers each group has, how far behind
they are on **this topic** — not on everything they consume — and which coordinator owns them. It is
the question an operator asks before changing a topic's retention or partition count, and answering
it anywhere else means opening the Consumers screen and reading four thousand rows.

## Scope

1. `GroupsForTopicUseCase[F]`: `forTopic(cluster, topic)`.
2. The membership rule: a group belongs to a topic when it has a **member assigned** to a partition
   of that topic **or** a **committed offset** on one. The second half is what includes the empty
   and dead groups that still hold offsets — which are precisely the groups an operator is about to
   be surprised by.
3. Per-topic lag: the group's lag restricted to that topic's partitions, with the same
   skip-and-report totalling rule.

## Non-goals

- **No describe on the request path.** Answered entirely from the snapshot, because this endpoint is
  a *section of another page's aggregation* and a section that takes a second makes the topic page
  take a second (ADR-037).
- **No topic metadata.** Partition counts, configs and sizes are the topic service's; this returns
  group rows.
- **No mutation entry points.** The tab links to the group page; delete and reset live there.

## Design references

- `research/kafka/admin-capabilities.md` §3, row "Groups for a topic": *describe all groups → keep
  those with a member assigned to the topic **or** a committed offset on it*, and the note that the
  reference needs cached committed offsets for `EMPTY`/`DEAD` groups because describing every group
  is expensive. KUI has that cache: it is the snapshot.
- `research/kafbat/ui-analysis.md` "Consumers tab (`consumer-groups`)": the four columns — Consumer
  Group ID (link), Active Consumers, Consumer Lag (for this topic), Coordinator, State — and the
  empty message "No active consumer groups".
- DEVPLAN §10 D13 — this data reaches the browser as a section of the gateway's topic-overview
  aggregation, rendered in a `FeaturePanel`. This use case does not know that.
- KU-011, KU-013, DC-H6.

## Public Scala signatures to implement

```scala
package kui.consumer.application

import kui.kernel.{ClusterId, TopicName}
import kui.consumer.domain.{GroupSummary, LagMath}

final case class TopicConsumerRow(
    summary: GroupSummary,
    /** Lag on **this topic only**. The group's own total is on `summary`; showing the wrong one is
      * the mistake this second field exists to make impossible. */
    topicLag: LagMath.LagTotal,
    /** Partitions of this topic this group holds an assignment or a commit on. */
    partitionCount: Int,
    /** True when the group has offsets here but no member — the case an operator most needs to see
      * before deleting a topic. */
    isDormant: Boolean
)

final case class TopicConsumersView(
    rows: List[TopicConsumerRow],
    freshness: SnapshotFreshness
)

trait GroupsForTopicUseCase[F[_]]:
  /** Never fails for a configured cluster. A topic no group consumes returns an empty list, which
    * is a fact and not an error — the topic service already answered whether the topic exists. */
  def forTopic(cluster: ClusterId, topic: TopicName): F[Either[KuiError, TopicConsumersView]]

object GroupsForTopicUseCase:
  val Operation: String = "kui.consumer.forTopic"
  def make[F[_]: Temporal](snapshots: GroupSnapshots[F]): GroupsForTopicUseCase[F]

  /** Pure. The membership rule and the per-topic restriction, asserted directly. */
  def rowsFor(snapshot: GroupSnapshot, topic: TopicName): List[TopicConsumerRow]
```

Rows are sorted by `topicLag` descending with undefined last, then by group id — the operator is
looking for the one that is behind, and putting it first is the whole value of the tab.

## Tests required

`GroupsForTopicUseCaseSuite`:

1. `includesAGroupWithAnAssignedMember`.
2. `includesADormantGroupWithOnlyCommittedOffsets` — **the half the naive implementation misses**,
   and the reason the research note exists.
3. `excludesAGroupWithNeither`.
4. `topicLagExcludesOtherTopics` — a group consuming two topics: the row's lag is this topic's, and
   it differs from `summary.totalLag`.
5. `topicLagSkipsUndefinedAndReports`.
6. `partitionCountIsThisTopicsPartitionsOnly`.
7. `isDormantIsTrueWithNoMembers`.
8. `rowsAreSortedByTopicLagDescendingUndefinedLast`.
9. `aTopicNobodyConsumesIsAnEmptyList` — `Right(Nil)`, not `Left`.
10. `makesNoPortCall` — asserted on the fake's call log. A section of another page's aggregation
    that called a broker would break ADR-037's bound for the whole topic page.

## Degraded behavior

| Condition | Behaviour |
| --- | --- |
| Snapshot stale | Rows served with `Stale` freshness; the gateway wraps them as `Section.Stale` and the tab greys with a timestamp |
| Snapshot absent | `Unavailable`; the gateway renders the section as `Section.Unavailable` and the tab shows the fallback card — the topic page's other sections are untouched (exit criterion 5) |
| Consumer service down | The gateway never calls this; the section is `Unavailable` at the aggregation layer (GRP-029) |
